# Coding Standards

Read at review time. Rules a tool enforces live in that tool's config and are not repeated here. A rule in a domain section overrides the Baseline.

Domain words follow the glossary, `docs/vision/03-conceitos.md`: workflow, run, execution, job, step, role, journal, event log, location, frozen, ended. A rule tagged `[check candidate]` is mechanical: it stays here until a check enforces it.

## Documentation and agent-facing text

Enforced by tooling: `scripts/check-docs.ts` run by `test/docs-check.test.ts` (relative links and anchors resolve, every chapter is in `docs/README.md`, the H1 equals the index label `part.position · Title`, the prev/index/next footer is the expected one); `test/book-layout.test.ts` (chapters cite each other by number, a runtime `warning` the book quotes exists verbatim in the code, every Mermaid `classDef` sets `fill`, `stroke` and `color`, no `stateDiagram` v1); `test/config-reference.test.ts` and `test/events-reference.test.ts` (`docs/reference/config.md` and `docs/reference/events.md` match their sources, so they are never edited by hand); `test/vision-and-adrs.test.ts` (ADR title, status line, sections, English, supersede chain); `test/repo-layout.test.ts` (each skill is self-contained, a reference two skills share is byte-identical in both, `CLAUDE.md` is English); `test/install-guide.test.ts` (`INSTALL-AGENT.md` and the pointers the kit writes pin the version tag, and `INSTALL-AGENT.md` links to no other document); `packages/runtime/test/messages-english.test.ts` (every string literal in `packages/runtime/src`, `packages/runtime/workflows`, `scripts/verify`, `scripts/probe-sdk.ts` and the agent-run shell scripts is English); the `mermaid` job in `.github/workflows/ci.yml` (every Mermaid block renders).

- **A behaviour change updates every text that describes it, in the same change.** Before calling a behaviour change done, search every surface that can describe it: the book (`docs/`), the skills (both copies of a shared reference), the accepted ADRs, the CHANGELOG `## Não lançado` section, code comments and module cost tables, the sources of `docs/reference` (`packages/runtime/schema/config.schema.json` descriptions, the JSDoc in `packages/runtime/src/runtime/events.ts`, `scripts/config-reference.ts`), `INSTALL-AGENT.md`, `SECURITY.md`, `README.md` and `README.en.md`, MCP tool descriptions, CLI usage lines, and test titles. A doc the change makes untrue is a **blocking** review finding. When the change contradicts an accepted ADR, write a new ADR that supersedes it (the old one keeps its text; only its status line becomes `superseded by ADR-NNNN`) and repoint every citation; an accepted ADR is edited in place only for a clarification that keeps the decision, under a dated `**Amended:** YYYY-MM-DD: ...` line. _Why:_ the four review rounds over specs #2 to #5 found 20, 10, 4 and 1 blocking findings, then 5 more in the final read, and most were docs a code change had made untrue; an ADR rewritten in place erases why the old decision was taken. _See:_ `docs/contributing/02-convencoes-do-livro.md:71`, `docs/adr/0006-cloud-steps-as-built.md:3`.
- **Write each text in its reader's language.** The book (`docs/`), `README.md` and `CHANGELOG.md` are pt-BR; ADRs and `README.en.md` are English; so is every agent-facing surface no check reads (a template, a skill's prose, a fixture outside `scripts/verify`). _Why:_ agents act on what they read and the owner fixed English as their language (a pt-BR prompt also changes what a measurement measures), while the book is written for pt-BR readers. _See:_ `docs/contributing/02-convencoes-do-livro.md:63`.
- **Cite the ADR in force.** Name a superseded ADR only next to its successor ("ADR-0006, substituído pelo ADR-0007"), and repoint code comments and chapters when a supersession lands. _Why:_ a pointer to a superseded ADR sends the reader to a decision that no longer holds. _See:_ `docs/vision/03-conceitos.md:97`.
- **Use the glossary's nouns, one per concept.** Write workflow, run, execution, job, step, role, journal, event log, location, frozen and ended as `docs/vision/03-conceitos.md` defines them; in pt-BR prose a step is "etapa", the event log is "log de eventos", frozen is "travado", ended is "terminado", and run, job, role, location and journal stay English. Never use a synonym the glossary lists under _Evite_. A resume is a new execution and a new job of the same run; only a job whose own process is alive, holds `run.lock` and stopped heartbeating is frozen. _Why:_ run, execution and job name different things (spend counts per execution, status and caps per run), and cancel and resume branch on frozen versus ended, so a loose word makes the cancel and resume docs wrong. _See:_ `docs/vision/03-conceitos.md:53`, `docs/vision/03-conceitos.md:68`.
- **Keep role and tier, cap and limit apart.** A role is the config-facing name of a step's function (`classify`, `review`, `implement.*`); a tier (LOW/MED/HIGH) is `implement-issue`'s issue complexity, mapped to a role in code. A cap ("teto") is a global ceiling that only tightens; a limit is a tunable a cap clamps. _Why:_ config keys (`roles.*`, `caps`, `limits`) and the docs must use the same word for the same knob, or users loosen the wrong one. _See:_ `docs/vision/03-conceitos.md:44`.
- **Quote a runtime message verbatim where an agent branches on it.** A skill that tells the agent how to react to a runtime outcome quotes the message, or its fixed prefix, in a code span exactly as the code emits it. Rewording such a message is an interface change: update every skill and dashboard reader of that prefix in the same change. _Why:_ agents branch on these prefixes (`no heartbeat` means a frozen job that a cancel must kill), and a reworded message silently sends them down the wrong path. _See:_ `skills/run-workflow/SKILL.md:81`, `packages/runtime/src/runtime/job-state.ts:185`.
- **A skill says when to load it, and each step says when it is done.** The frontmatter `description` starts with when to use the skill ("Use before ..."), and each numbered step ends with a "Done when ..." criterion. _Why:_ the description is what triggers the skill, and the criterion tells the agent when a step is complete. _See:_ `skills/cursor-workflow-authoring/SKILL.md:15`.
- **Research reports are dated evidence.** Never rewrite a measured row of a Part 8 report: add a `> **Nota (YYYY-MM-DD, #issue):**` saying what changed since and that the rows stay as measured. When moving or rewriting any chapter, keep its dated measurements and `[DOC](url)` citations; update only paths and cross-references. _Why:_ the book's claims about Cursor rest on dated measurements, and a silently updated row destroys the evidence trail. _See:_ `docs/research/verificacoes-locais.md:89`.
- **A CHANGELOG entry states the change as the code now has it.** It goes under `## Não lançado` and `### Adicionado|Mudado|Corrigido`, as a pt-BR bullet that opens with a bold one-sentence summary of the user-visible change. _Why:_ the changelog is read as release notes, and an entry that keeps the pre-fix wording is a stale doc. _See:_ `CHANGELOG.md:7`.
- **A diagram carries one idea.** Keep a Mermaid diagram to about 15 nodes (split it past that), use `LR` for flows read as a sentence and `TB` for layers, write labels in pt-BR (English in `README.en.md` and ADRs) with code identifiers verbatim, and never carry information by colour alone. _Why:_ GitHub picks the reader's theme and renders at reading width, so a crowded or colour-coded diagram is unreadable for some readers. _Detail:_ `docs/contributing/03-diagramas.md`, read when adding or changing a Mermaid diagram. _See:_ `docs/contributing/03-diagramas.md:60`.

## Code documentation

Enforced by tooling: `test/coding-standards.test.ts` (every `.ts`, `.tsx` and `.mjs` file under `packages/`, `scripts/` and `test/` opens with a comment, after a shebang); the `WHAT:`/`WHY:`/`WHEN:`/`HOW:` header of a script is checked under Maintainer scripts and Bash.

- **A source file's header comment states its contract.** Say what the module is for and why: its role, its guarantees, and what it deliberately does not do; cite the ADR or chapter that holds the longer rationale. _Why:_ the header is where a reader learns a module's contract before reading code, and where a reviewer checks a change against it. _See:_ `packages/runtime/src/runtime/cloud-cancel.ts:1`.
- **New comments are English.** Every new comment is English, even in a file whose older comments are pt-BR; the older comments are not translated. Sources the book renders stay pt-BR: the field JSDoc of `packages/runtime/src/runtime/events.ts` and the `description`s of `packages/runtime/schema/config.schema.json`. _Why:_ comments are agent-facing text, while those two sources become book chapters 6.1 and 6.2. _See:_ `packages/runtime/test/messages-english.test.ts:5`.

## Testing

Enforced by tooling: `packages/runtime/tsconfig.test.json` with the `tsx --test --tsconfig` scripts in `packages/runtime/package.json` and `packages/dashboard/package.json` (`@cursor/sdk` resolves to `packages/runtime/test/fake-sdk.ts`, so no test reaches the Cursor API); `test/repo-layout.test.ts` (dashboard tests never import runtime sources, except the `engine-log.test.ts` contract); `test/fixed-waits.test.ts` (no test sleeps a fixed time and then asserts, unless the wait carries a `fixed-wait-ok:` reason; tests poll with `waitFor`); `test/coding-standards.test.ts` (a test file that calls `runWorkflow` isolates the home, through `./isolate-home.js` or `WF_HOME`, itself or through a fixture; no manifest or import brings in jsdom; tests import no `describe`, `it`, `suite` or `mock` from `node:test`, and `assert` only from `node:assert/strict`; no test times a bound or a deadline with `Date.now()`: it uses `performance.now()`; `Date.now()` stays only to build a timestamp, as in `new Date(Date.now() - ms)`, or on a line with a `wall-clock-ok:` reason).

- **Every test file opens with `// Seam: <the seam, in words>`.** Name the interface the file asserts at and say what is real and what is a stand-in; no seam numbers. _Why:_ the header is the only place that tells a reviewer at which interface the file asserts, so a test that reaches past its seam shows against it. _See:_ `test/scripts-conventions.test.ts:1`. [check candidate]
- **Replace outside systems only at the process boundary.** `@cursor/sdk` becomes `test/fake-sdk.ts` through the tsconfig path swap; `gh`, `wf`, `wslview` and `node` become stand-in executables on `PATH`; the Mermaid renderer becomes `MERMAID_CLI`. Git, the filesystem, child processes and `node:sqlite` stay real, and no test uses `node:test` mocks or module mocking. _Why:_ tests stay offline while the code under test makes its real calls, and a module mock would hide the contract the fakes pin down. _See:_ `packages/runtime/test/doctor.process.test.ts:43`.
- **Assert on outcomes.** Drive a workflow through `runWorkflow(def, args, { cwd })` or the CLI/MCP process, and assert on the result status and fields, the replayed event log, the files written and the options the fake SDK received, never on internal calls. _Why:_ outcome assertions survive engine refactors and test what a user or agent observes. _See:_ `packages/runtime/test/smoke.test.ts:37`.
- **Turn metrics off in a workflow test that does not test them.** Set `process.env.WF_METRICS = "off"` before the modules under test (or get it from a fixture); a child process gets `WF_METRICS: "off"` and its own `WF_HOME`. _Why:_ with metrics on, every run loads `node:sqlite` and records rows the test never reads, and a child process started with its own `env` gets neither switch unless it is passed. _See:_ `packages/runtime/test/smoke.test.ts:4`.
- **Reset every fake-SDK export the file uses.** In `afterEach`, directly or through the fixture teardown, reset `script`, `calls`, `stats`, `costConfig` and the cloud state (`resetCloud`) when the file uses them. _Why:_ the fake is module-level state shared by the tests of one file, so a leftover script entry or call count makes the next test pass or fail for the wrong reason. _See:_ `packages/runtime/test/engine.test.ts:20`.
- **Name a test `<area>.process.test.ts` when it spawns the product.** That is the `wf` CLI, the MCP server, the dashboard or the installer as a child process; a test that only needs a helper child keeps `.test.ts`. _Why:_ the suffix tells a reviewer the file is slow and asserts at the process seam. _See:_ `packages/runtime/test/job-not-found.process.test.ts:1`.
- **A test helper names its users.** Open every non-test file in a test folder with `Shared by the <x> tests: ...`, `Child process of <file>.test.ts: ...` or `Imported by ...`. _Why:_ helpers are not typechecked and have no test of their own, so the header is how a reviewer knows who breaks when a helper changes. _See:_ `packages/runtime/test/hold-run.ts:1`.
- **Title a test with the behaviour it pins.** Each `test()` title is an English sentence stating the observable behaviour, not `should ...` or a function name. _Why:_ `node:test` prints only the title on a failure, and the title is the specification the reviewer checks the assertions against. _See:_ `packages/runtime/test/smoke.test.ts:33`.
- **Fix a defect test-first, with its own red commit.** Commit the failing test (`test(<scope>): ... (red)`), then the fix that turns it green. _Why:_ the red commit proves the test reproduces the defect on the old code; a test written after the fix may pass on both. _See:_ `skills/cursor-workflow-authoring/references/testing.md:48`.
- **Enforce a repo convention with a `node:test` that reads the files.** Read them the way an agent or installer would (plain text, Markdown through `scripts/lib/markdown.ts`, or the TypeScript AST), and make the failure name the file and the fix. _Why:_ these tests are the repo's only style and boundary enforcement, so a convention without one is not enforced. _See:_ `test/scripts-conventions.test.ts:48`.
- **Test dashboard components as static markup.** Render a component to HTML in Node through `packages/dashboard/test/render.ts` (`renderToStaticMarkup`, data as props); test the rest of the dashboard as pure functions or over real HTTP on a loopback port. _Why:_ there is no DOM test environment, and static markup is what the page first paints. _See:_ `packages/dashboard/test/render.ts:1`.
- **A TypeScript child process keeps the fake SDK.** Start it as `spawn(process.execPath, ["--import", import.meta.resolve("tsx"), file, ...])`, or the MCP stdio client, with `TSX_TSCONFIG_PATH` pointing at a `tsconfig.test.json`. _Why:_ a child started without it loads the real `@cursor/sdk` and reaches the network. _See:_ `packages/runtime/test/run-lock.test.ts:29`.
- **Give every test its own directories.** Write only under `mkdtempSync(tmpdir())` or `test/.tmp/<name>-${process.pid}`, remove it in `afterEach`/`after`, and point `WF_HOME` at a throwaway home. _Why:_ `tsx --test` runs files concurrently, so a shared fixed path lets two files corrupt each other. _See:_ `packages/runtime/test/engine.test.ts:12`.

## TypeScript

Enforced by tooling: `npm run typecheck` in `npm run check` (`tsc --noEmit` with `strict` and `verbatimModuleSyntax`, so a type imported without `type` fails, from `packages/runtime/tsconfig.json`, over the runtime and dashboard sources, the workflows, `scripts/` and both browser pages; test files are not typechecked); `test/coding-standards.test.ts` (Node built-ins are imported with the `node:` prefix; an import of types only is written `import type`; the one default export is a workflow definition, and a PascalCase `.tsx` file exports the component it is named after).

- **Declare object shapes with `interface`.** Keep `type` for unions, discriminated results, mapped and utility types. _Why:_ a reader of `type X = {...}` expects a union or a computed type. _See:_ `packages/runtime/src/runtime/command-runner.ts:16`. [check candidate]
- **Put the unit in a quantity's name.** Use `Ms`/`_MS`, `Sec`/`_SEC`, `Hours`, `Days`, `Cents`, `Chars`, `Bytes` (`timeoutMs`, `CANCEL_GRACE_MS`, `maxCents`). _Why:_ timeouts, budgets and caps cross flags, config, env vars and events, and a unitless `timeout` invites a seconds/milliseconds bug. _See:_ `packages/runtime/src/runtime/command-runner.ts:9`.
- **Name module constants in UPPER_SNAKE_CASE and module state in camelCase.** Fixed numbers, strings, sets and schemas are UPPER_SNAKE_CASE; process-wide mutable maps, sets and singletons are camelCase. _Why:_ the case tells the reader whether a binding needs care across concurrent calls. _See:_ `packages/runtime/src/runtime/run-store.ts:56`.
- **Use `unknown` and narrow it, not `any`.** The accepted `any` is the heterogeneous `WorkflowDefinition<any, any>` boundary (registry, source fingerprints) and the untyped stage chain of `ctx.pipeline`. _Why:_ `tsc --strict` is the only type enforcement, and an `any` switches it off silently. _See:_ `packages/runtime/src/runtime/state-files.ts:66`. [check candidate]

## Architecture

Enforced by tooling: `test/repo-layout.test.ts` (the dashboard reaches the runtime only through `@cursor-workflows/runtime/observe`; the runtime depends on no workspace package; web libraries live only in the dashboard manifest; `run-view/` imports no `node:*` and no runtime source, and `app/` imports `node:*`, runtime and server modules only through `import type`); `packages/dashboard/test/server.test.ts` (the dashboard process never loads `@cursor/sdk`); `packages/runtime/test/relocated-install.test.ts` (the runtime finds its own assets from its install location, never the cwd); `test/coding-standards.test.ts` (in the runtime and dashboard code, `Agent.create` and `Agent.resume` appear only in the `AgentBackend` adapters, and only they, the CLI and the doctor import `@cursor/sdk` as a value at load time; `scripts/probe-sdk.ts`, which measures the SDK itself, is outside the scan).

- **The engine reaches an agent only through `AgentBackend.run`.** A new place to run agents is a new adapter implementing `AgentBackend` (today `localBackend` and `createCloudBackend`). An adapter reports every way an attempt ends in its `AttemptResult` and rejects only on a bug; `engine.ts` imports SDK types only. _Why:_ budget, live caps, cancellation, retries, the journal and the event log stay in one place, and tests swap the backend or the SDK at this seam. _See:_ `packages/runtime/src/runtime/engine.ts:1064`.
- **The event log is the run's only source of progress.** Status, phase, recent lines, spend and result are computed on every read by the pure functions of `projection.ts`. The job record holds identity (jobId, runId, pid, heartbeat) plus only `start`, `refused` and `killedByCancel`; a new fact about progress goes into the log, and a new record field needs an ADR. _Why:_ two places holding run state disagree, and ADR-0008 keeps the record from growing a projection field. _See:_ `packages/runtime/src/runtime/job-state.ts:34`.
- **Durable run state has one door.** All per-run state goes through `RunStore` (`events.jsonl`, `journal.jsonl`, `run.lock`). Every event leaves through the engine's `stamp`: it adds `v`, `ts`, `runId` (in that order, before `type`) and redacts once, and the same event then goes to the log, the metrics recorder and the listeners. Step results are redacted before the journal and the memo store keep them. _Why:_ one door keeps the lock, the redaction and torn-line handling uniform; a second writer could skip redaction, and readers find content lines by that key prefix without parsing them. _See:_ `packages/runtime/src/runtime/engine.ts:331`.
- **Surfaces start, read and cancel; the job runs alone.** The CLI, the MCP server and the dashboard only start a job, read its state and ask it to cancel. A job always runs in its own detached process (`spawnJob`), and every cancel surface ends in the same `cancelJob`. _Why:_ a run must survive a restart of the server or the IDE, and cancel behaviour (a frozen job, left-over cloud agents) must not drift between surfaces. _See:_ `packages/runtime/src/mcp-server.ts:20`.
- **A new file goes where the canonical map puts it.** Engine and state modules in `packages/runtime/src/runtime/`, config in `src/config/`, SQLite code in `src/observability/`, built-in workflows in `packages/runtime/workflows/<name>.ts` with helpers in `workflows/<name>/`, the dashboard server in `packages/dashboard/src/`, browser pages in `app/` or `run-view/`, offline tests in each package's `test/`. _Why:_ the layout carries the dependency rules, and a file placed elsewhere escapes the convention tests that scan these folders. _Detail:_ `docs/contributing/01-contribuindo.md`, read when adding a file or a folder the map does not show yet. _See:_ `docs/contributing/01-contribuindo.md:55`.

## Dashboard (React)

Enforced by tooling: `packages/dashboard/test/numbers.test.ts` (numbers, costs, durations and dates are formatted only through `app/format.ts`, in en-US); `packages/dashboard/test/ui.test.ts` and `packages/dashboard/test/app.test.ts` (each page is one HTML shell with one hashed stylesheet and one hashed script, a self-only CSP, nothing inline or from another origin); `test/coding-standards.test.ts` (browser code builds per-run URLs only through `runHref` and `runApiPath`, and never writes an en dash).

- **Keep components thin; derive in pure modules.** Put derivation logic (graph, layout, framing, header status, node details, step log, resume command) in plain `.ts` modules with no DOM, clock or network access, say "Pure" in the header, and let the caller pass the clock or the pane size. Components call hooks, call these functions and render. _Why:_ the live view, the replay and the Node tests all call the same function, while logic inside a component is testable only through rendering and drifts from the replay path. _See:_ `packages/dashboard/run-view/run-graph.ts:1`.
- **Hold state in React's own hooks.** Use `useState`, `useRef`, `useMemo`, `useCallback` and small custom hooks, with server data from `usePoll` (app page) or the SSE hooks `useRunEvents` and `useStepLog` (Run view), and the URL hash as the menu; add no context, reducer, store or router library. _Why:_ every bundled package is a build input of both pages, and the pages are small enough for props plus hooks. _See:_ `packages/dashboard/app/usePoll.ts:12`.
- **Say why an effect's dependency list is narrow.** When the list deliberately leaves out a value the effect reads, put a comment next to it saying why. _Why:_ with no exhaustive-deps lint, the comment is the only record that the omission is intended and not a stale closure. _See:_ `packages/dashboard/run-view/RunView.tsx:45`.
- **Batch live events before React sees them.** Pass SSE streams to React through `batcher()` from `run-view/batch.ts` (`BATCH_MS` = 100), never one `setState` per event. _Why:_ replaying a long log or a command printing a thousand lines must cost a few renders, not one per line. _See:_ `packages/dashboard/run-view/use-run-events.ts:112`. [check candidate]
- **Use React Flow as a read-only viewer.** Set `nodesDraggable`, `nodesConnectable` and `nodesFocusable` to false, make edges and lanes unfocusable and unselectable, let the node component's own element be the keyboard control, set `colorMode="system"`, and theme it through its `--xy-*` variables mapped to tokens in `run-view.css`. _Why:_ the canvas shows a run, it is not an editor, and React Flow's focusable wrappers would add Tab stops that do nothing. _See:_ `packages/dashboard/run-view/RunView.tsx:88`.
- **Type a table keyed by a union as a total `Record`.** State glyphs, connection text, status text and page policies are `Record<Union, string>`. _Why:_ statuses grow from the runtime, and a total record turns a forgotten case into a `tsc` error instead of a blank on screen. _See:_ `packages/dashboard/run-view/run-status.ts:10`.
- **Every polled view renders through `Loaded` and `PageHeader`.** `Loaded` shows "Loading …" (`role="status"`) before the first answer and the error (`role="alert"`); a later failure keeps the last answer on screen with a banner; a view with no data renders `Empty` with a title and a sentence on how to get data. _Why:_ a polling dashboard must never go blank on a failed poll, and every view must say loading, broken and empty the same way. _See:_ `packages/dashboard/app/Loaded.tsx:31`.
- **Mark live messages with ARIA roles.** Errors and failures get `role="alert"`; loading text and confirmed outcomes ("Copied.", a cancel result) get `role="status"`; the streaming step log is `role="log"` with `aria-live="off"`. _Why:_ screen-reader users must hear a failure and a confirmation, while an announced tail of many lines a second would drown them. _See:_ `packages/dashboard/run-view/StepLogPanel.tsx:155`.
- **Hide glyphs from screen readers and say the same thing in words.** Decorative glyphs and icons (status glyphs, ▶ ☁ ↗ ×, the logo, legend swatches) get `aria-hidden="true"`, with a visible label or an `aria-label` carrying the meaning; an icon-only button gets an `aria-label`. _Why:_ glyphs such as ✓ ✗ ‖ are read as noise or not at all, so the state must live in the accessible name. _See:_ `packages/dashboard/run-view/nodes.tsx:54`.
- **Keyboard focus follows what is visible.** Elements with no action (edges, lanes, links inside a hover tooltip, a canvas hidden under the log) leave the Tab order; custom controls are `role="button"` with `tabIndex=0` and handle Enter and Space; a focused node is panned into view; opening the log moves focus to its Close button and closing it returns focus to the node; Escape is handled only by its innermost owner. _Why:_ the Run view is a canvas under an overlay, and without these rules a keyboard user tabs into invisible nodes or loses focus to the body. _See:_ `packages/dashboard/run-view/log-focus.ts:16`.
- **Show information as text, never only in a tooltip.** Use `title` only for the full form of truncated text; on phones every table cell names its column through `data-label`. _Why:_ touch and keyboard users never see `title` tooltips, and stacked tables lose their header row. _See:_ `packages/dashboard/app/RunsView.tsx:59`.
- **Write a missing value as an em dash.** A missing or unknown value is `—` in a `span` with class `none`, with a `title` when the reason is worth saying. _Why:_ one glyph for "no value" lets a reader tell none from zero on every page. _See:_ `packages/dashboard/app/RunsView.tsx:79`.
- **Draw charts as hand-written SVG.** Draw them 1:1 at their measured width (`Measured`/`useWidth`), give each chart `role="img"` and an `aria-label`, each mark a `<title>` with its value from `format.ts`, a visible legend with `aria-hidden` swatches, series colours from the `--chart-N` tokens through `SERIES`, and a dashed second series so colour is not the only cue. _Why:_ viewBox scaling shrinks labels on phones, and a chart library would be another bundled dependency. _See:_ `packages/dashboard/app/MetricsView.tsx:94`.
- **A new page, bundled package or build option updates the bundle's inputs.** A new page needs an entry in `PAGES` (`src/web-bundle.ts`) and a policy in `PAGE_POLICY` (`src/pages.ts`); a new package bundled into the browser goes into `BUNDLED`; a change to the esbuild options bumps `BUILD_RECIPE`. _Why:_ the content-hash cache is invalidated only by sources, `BUNDLED` versions and `BUILD_RECIPE`, so a missed bump serves a stale bundle. _See:_ `packages/dashboard/src/web-bundle.ts:26`.

## Dashboard CSS

Enforced by tooling: `packages/dashboard/test/tokens.test.ts` (colours are written only in `app/tokens.css`, as hex values defined for light and dark, and text, status and chart colours meet their WCAG contrast ratios on every surface); `test/coding-standards.test.ts` (the app page has no `style=` attribute; its CSP has no `style-src-attr`).

- **Take every size from the token scales.** Use `--space-1…6` for gap, padding and margin, `--text-xs…2xl` for font sizes, `--radius-*` and `--shadow-*`; raw `px` only for 1–2px hairlines and offsets and for the size of dots and spinners. _Why:_ the scales keep the two pages consistent, and off-scale values creep in because nothing checks them. _See:_ `packages/dashboard/app/styles.css:7`. [check candidate]
- **Pair every animation with a reduced-motion rule.** Each `animation` or `transition` has a `@media (prefers-reduced-motion: reduce)` rule in the same file that sets it to none. _Why:_ pulsing status dots and glowing running nodes repeat forever, and users who ask for reduced motion must get a still page. _See:_ `packages/dashboard/app/tokens.css:151`. [check candidate]

## Workflow authoring

Enforced by tooling: `test/workflow-lint.test.ts` (every command in `packages/runtime/workflows`, `.agents/workflows` and `scripts/verify/verify-*.ts` runs through `ctx.exec`, never `execSync`, `execFileSync` or `spawnSync`); the engine refuses `memo: true` on a step whose tools can write (`packages/runtime/src/runtime/engine.ts:854`); `test/coding-standards.test.ts` (every `ctx.metric` name in a workflow is snake_case).

- **Declare every `ctx.agent` step in full.** Each step sets `label`, `role`, `tools` and `settingSources` (directly or through the role), plus a `schema` when code reads its result; read-only steps add `memo: true`; write steps never memo and take `revertOnRetry`. _Why:_ the label is the per-step key in the event log, the dashboard and the metrics (without it the runtime falls back to `step-<promptHash>`), and memo on a write step would skip its effect on resume. _Detail:_ `skills/cursor-workflow-authoring/` (`SKILL.md` and `references/`), read when creating or editing a workflow, including a `scripts/verify/verify-*.ts` one. _See:_ `packages/runtime/workflows/smoke.ts:43`.
- **Build a prompt as a fixed constant followed by deterministic data.** Fixed instructions are English constants in a prompts module, placed first; variable data goes last; nothing volatile (dates, `Date.now()`) enters a prompt; a rule only the prompt states carries a comment saying it is a request, not a lock. _Why:_ prompt plus options is the journal and memo key and the provider-cache prefix, so volatile text breaks resume and the cache. _See:_ `packages/runtime/workflows/implement-issue.ts:587`.
- **Every return path returns an explicit status.** `done` (or `ok`) when delivered, otherwise a kebab-case failure or pending status (`review-failed`, `secret-blocked` naming only the rule); a status that waits for a person is listed in `outcome.ts` `PENDING`; a required `ctx.parallel`/`ctx.pipeline` result is checked for `null` and turned into a failure status; loops are capped by settings; throw only for unexpected infrastructure errors. _Why:_ `outcomeClass` reads this field for the metrics and `wf gc`, an unknown status counts as a failure, and a missing null check turns a failed mandatory review into "no findings". _See:_ `packages/runtime/src/runtime/outcome.ts:7`.
- **External effects are idempotent and run in code.** Commit only when `git diff --cached --quiet` says there are changes, look a branch's PR up before opening one (`forge.prUrl` before `forge.openPr`, which is `gh pr view` before `gh pr create` on GitHub), and run a secrets guard before any outbound text. _Why:_ resume re-runs delivery, and a second PR or an empty commit is a visible defect. _See:_ `packages/runtime/workflows/implement-issue.ts:1077`.
- **Choose the model in code and declare the cost up front.** Use named `ModelSelection` constants, map a tier to a role in code, give each role a default in `meta.roles`, and open the module with a per-path cost table (step, model, tools, settingSources, memo, typical and worst-case agents, measured tokens with date) that matches the step labels and models in code. _Why:_ cost and model choice are reviewable only when declared up front, and a stale table misleads the cost report. _See:_ `packages/runtime/workflows/smoke.ts:10`.
- **A workflow's `meta` is its public contract.** `meta.name` is the stable name for `start_workflow` and `wf run`; `meta.argsSchema` is checked with Ajv before the run (a shipped workflow sets `additionalProperties: false`); `meta.roles` and `meta.settings` are the only names config files may use. Renaming a role or a setting breaks every config that uses it. _Why:_ config files in user repos key off these names, so a mismatch would silently ignore the user's caps or models. _See:_ `packages/runtime/src/runtime/workflow.ts:50`.
- **Steps that run at the same time write different files.** Parallel steps are read-only (`memo: true`, read-only tools), or each writes in its own `git worktree` passed as `cwd`. _Why:_ two writing agents in one tree corrupt each other's work, and revert-on-cancel cannot undo it. _See:_ `packages/runtime/workflows/implement-issue.ts:606`.
- **Record a metric's difficulty covariate.** Next to a signal such as `slices_planned`, record what makes the run hard (`tier`). _Why:_ metric names become rows compared across workflows and models, and without the covariate a hard issue reads as a bad model. _See:_ `packages/runtime/workflows/implement-issue.ts:557`.

## API and contracts

Enforced by tooling: `test/events-reference.test.ts` (each event is one `interface` extending `EventBase` with a literal `type`, and `docs/reference/events.md` is regenerated from it). Pinned by a behaviour test, which does not fire on a new site: `packages/runtime/test/content-log.test.ts` (step content stays in the event log and never reaches the metrics DB, its exports or the run's listeners).

- **The event schema grows additively.** A new field is optional and documented as absent in older logs; bump `EVENT_SCHEMA_VERSION` only when a field changes meaning or is removed; readers treat an unknown `type` or a higher `v` as opaque. _Why:_ logs outlive kit versions (a resume appends to an old log, the dashboard reads every repo's history), so a required new field or a strict reader breaks old runs. _See:_ `packages/runtime/src/runtime/events.ts:21`.
- **Step content travels only in `content` events of the local event log.** Prompts, agent text, tool calls and command output go there, redacted and cut; every other event, the metrics DB, `onEvent` listeners, `wait_workflow` and `wf status` carry only hashes, sizes and one-line summaries, and prompts reach the DB only as hash and size. _Why:_ polling from the chat must never push prompts or secrets into context, and the DB and its exports are what users may share. _See:_ `packages/runtime/src/observability/recorder.ts:7`.
- **The dashboard's JSON API answers through `send()`.** Every response has `cache-control: no-store` and `nosniff`; errors are `{ error: "<sentence>" }` with 400, 403, 404, 405, 409 or 500; lists are wrapped in a named key (`{ runs }`); a machine with no history gets empty states, not errors; routes are unversioned because dashboard and runtime ship in lockstep. _Why:_ the pages and tests rely on one error and empty-state shape. _See:_ `packages/dashboard/src/server.ts:71`.
- **The dashboard API is read-only except one gated action.** `POST /api/runs/<runId>/cancel` requires the per-process CSRF token in `X-CSRF-Token` and a same-origin request; the server binds 127.0.0.1, refuses non-loopback `Host` headers and sends no CORS headers; a new write endpoint goes behind the same gate. _Why:_ the dashboard can kill jobs on the user's machine, so DNS rebinding or a cross-site form must not reach it. _See:_ `packages/dashboard/src/server.ts:188`.
- **A live run streams as Server-Sent Events keyed by log position.** Each log line is one event with `id: <line position>`; a reconnect resumes from `Last-Event-ID` (or `?lastEventId`), and a non-integer id is a 400; `?content=false` and `?stepId=` narrow the stream. _Why:_ EventSource reconnects on its own, and position ids make the replay exact and duplicate-free. _See:_ `packages/dashboard/src/server.ts:143`.
- **Absent is omitted; `null` carries a documented meaning.** A field that does not apply is left out (`...(xs.length ? { xs } : {})`), an absent value is `undefined`, and `null` appears only where the type documents it: no limit in config and caps, a failed `ctx.parallel` branch, a killed process's exit code, no parent or group in `StepRef`. Defaults use `??` and `=== undefined`, never `||`, so 0 stays a value. _Why:_ config resolution reads absent as inherit and `null` as unlimited, so mixing them silently removes or restores a cap. _See:_ `packages/runtime/src/config/resolve.ts:326`.

## Error handling

Enforced by tooling: none.

- **Turn a caught value into text with `errorText(err)`.** Use the helper in `packages/runtime/src/runtime/error-text.ts`, not an inline `err instanceof Error ? err.message : String(err)` or another local `messageOf`. _Why:_ a review round consolidated this expression into one helper, and new copies fragment it again. _See:_ `packages/runtime/src/runtime/backend.ts:171`. [check candidate]
- **Classify a thrown error by the engine's hierarchy.** An error that must end the whole run (cost or token cap, account without access, cancellation) extends `FatalRunError`; one that fails one step extends `StepFailedError`; `ctx.parallel`/`ctx.pipeline` rethrow `FatalRunError` and turn anything else into `null` plus a warning. _Why:_ the class decides whether a failure stops the run or one branch, and a plain `Error` for a run-ending condition is swallowed by a parallel branch. _See:_ `packages/runtime/src/runtime/engine.ts:41`.
- **Catch narrowly and rethrow the rest.** Test the specific class (`instanceof CommandError`, `ConfigError`, `RunLockedError`) or `err.code` (`ENOENT`, `EEXIST`) and rethrow everything else; in a workflow a `CommandError` with a null exit code (timeout, kill, cancel) is never an answer. _Why:_ a broad catch in a workflow turns a cancel or a budget stop into a wrong answer or a counted crash. _See:_ `packages/runtime/src/runtime/engine.ts:540`.
- **Report an expected failure at a seam as data.** Return a discriminated result: `AttemptResult` from a backend, `CommandOutcome` from `runCommand` (which never rejects), `Parsed` from structured parsing, `RunOutcome` with `status: "failed"` and `refused` from `runWorkflow`, `{ failed: [...] }` lists from cancel and retention. _Why:_ the engine treats a backend throw as a bug (the attempt fails uncharged), so an adapter that throws breaks accounting and retries. _See:_ `packages/runtime/src/runtime/command-runner.ts:70`.
- **Report a failure that must not end the run as a warning.** The runtime emits a `warning` event and a workflow calls `ctx.log`, naming what was not done and why (`could not <action> ...: <reason>`), plus what to do by hand when relevant. _Why:_ these warnings are the only trace of degraded behaviour, and both swallowing and throwing lose it. _See:_ `packages/runtime/src/runtime/engine.ts:258`.
- **Write an error message subject first, ending with the remedy.** English, starting lowercase with the subject (`step "<label>": ...`, `<file>: ...`, `--flag must ...`), and ending with what to do when the user can act ("Use `wf list`."). _Why:_ agents read these messages through MCP and act on the remedy, and a fixed shape keeps them greppable and quotable in the book. _See:_ `packages/runtime/src/runtime/run-store.ts:138`.
- **Translate errors only at process and transport boundaries.** The CLI `main` prints `err.message` (no stack) to stderr and exits 1 (2 for usage); an MCP tool returns `isError` with `{ error }`; a dashboard route answers 500 `{ error }`; a job process installs crash handlers that end its open runs in the event log with a resume hint. Inner code throws. _Why:_ these four boundaries are the only places that print or format, and a catch-and-print deeper down duplicates output and can corrupt MCP stdout. _See:_ `packages/runtime/src/cli.ts:55`.
- **A catch that swallows says why it is safe.** Put the reason in the catch (`/* already gone */`) or in the function's doc comment ("Undefined when the file is not there"). _Why:_ the stated reason lets a reviewer check that the swallowed case is the only one that can occur. _See:_ `packages/runtime/src/runtime/command-runner.ts:65`.

## Concurrency

Enforced by tooling: none here; synchronous process calls in workflows are under Workflow authoring.

- **Keep the run path free of synchronous child processes.** Engine and backend code runs a command through `runCommand` or `execFileAsync` with a timeout; `execFileSync` and `spawnSync` appear only in one-shot CLI commands (`wf doctor`, `wf upgrade`) and in bounded, once-per-repo probes. _Why:_ a synchronous call freezes status queries, cancellation and the main-thread heartbeat; the heartbeat worker exists only as a fallback for it. _See:_ `packages/runtime/src/runtime/workflow.ts:249`.
- **Cancellation is one `AbortSignal` per run, aborted with a typed reason.** Thread it into every async operation (`backend.run`, `runCommand`, the cloud snapshot, `within`); each cause aborts with its own Error (`RunCancelledError`, `StepTimeoutError`, `StepBudgetError`), and code tells causes apart by `instanceof` on `signal.reason`. _Why:_ cancel, timeout and the token caps share one path, so an operation that ignores the signal makes `wf cancel` hang. _See:_ `packages/runtime/src/runtime/engine.ts:989`.
- **Check `aborted`, subscribe once, clean up in `finally`.** Before subscribing to a signal check `signal.aborted`, subscribe with `{ once: true }`, and remove listeners and clear timers in `finally` when the operation lives shorter than the signal. _Why:_ otherwise every attempt leaks a listener on the run's long-lived signal, and an already-cancelled run waits forever. _See:_ `packages/runtime/src/runtime/command-runner.ts:100`.
- **Mark a race promise handled; prefix fire-and-forget with `void`.** A promise kept only to race others gets `p.catch(() => {})` at creation; a deliberately unawaited call is prefixed with `void` and cannot reject. _Why:_ an unmarked race promise prints noise inside a job and crashes the process outside one. _See:_ `packages/runtime/src/runtime/engine.ts:672`.
- **Bound every fan-out.** Agent steps acquire the engine's `Semaphore(limits.concurrency)`; background external calls use a fixed cap (`MAX_PARALLEL`); workflows fan out only through `ctx.parallel`/`ctx.pipeline`, never `Promise.all`. _Why:_ an unbounded fan-out bypasses the `maxConcurrency` cap and can flood `gh` or the Cursor API. _See:_ `packages/runtime/src/runtime/engine.ts:591`.
- **Concurrent branches share no state through closures.** Per-branch context goes through `AsyncLocalStorage` (the engine's `flows`), and operations that must not overlap on one resource are serialized on a promise chain (`RevertQueue`). _Why:_ branches interleave at every await, so a shared "current" variable mis-attributes steps and simultaneous reverts of one directory corrupt it. _See:_ `packages/runtime/src/runtime/engine.ts:603`.
- **Background handles never keep the process alive.** `unref()` heartbeat timers, the heartbeat worker and detached job and dashboard children; a process-wide registry (held locks, running command trees) installs one `exit` hook, guarded by an `exitHookInstalled` flag, to release or kill what is still held. _Why:_ without `unref` the CLI never exits after starting a job, and without the hook a crashed process leaves locks held and process groups running. _See:_ `packages/runtime/src/runtime/command-runner.ts:87`.

Enforced by tooling: `packages/dashboard/test/ui.test.ts` (every page carries the self-only CSP); `test/coding-standards.test.ts` (the dashboard uses no `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `dangerouslySetInnerHTML`). - **Never print, log or return the Cursor API key; report auth state by email, expiry or key name.** Leave key resolution to the SDK (the `apiKey` option, then `CURSOR_API_KEY`, then the saved `wf login` key); where the kit reads the saved key, it keeps it in memory only, to compare it against outbound text, and hands it to `RunStore` as a secret so every event is redacted. _Why:_ CLI and MCP output lands in chat transcripts and PRs, and one printed key is a leaked 90-day credential. _See:_ `packages/runtime/src/cli.ts:164`.
- **Guard every effect that carries text off the machine.** In workflow code, before commit/push reset agent commits to the base and scan the staged files and added lines; before publishing a PR body or a comment scan the text, with the redactor's credential formats. A hit stops exactly that effect, and the run returns `status: "secret-blocked"` with a `reason` that names only the rule, never the snippet. _Why:_ a prompt-injected issue can make a step copy `~/.cursor/sdk/auth.json` into the worktree, and the code guard is the only hard stop. _See:_ `packages/runtime/workflows/implement-issue.ts:409`.
- **Sanitize model text bound for a forge.** Pass it through `sanitizeModelText` (it neutralises closing keywords that cite another issue, @mentions and `<!--`, and for GitLab a quick action at the start of a line and the `!12`, `~label` and `%milestone` references); test output gets `redactPaths` and goes inside a fence with backticks neutralised; enumerated model fields are constrained by schema enums. _Why:_ unsanitized model text in a public PR or comment can close the wrong issue, ping people, hide content, run a GitLab quick action as the account that posted it, or leak local paths and the username. _See:_ `packages/runtime/workflows/implement-issue/pr-body.ts:72`.
- **Validate external input at the boundary, with schemas.** Workflow args go through Ajv against `meta.argsSchema` before anything is written; config files are validated against the shipped JSON Schema with errors naming the field path; MCP overrides are shape-checked against the known limit fields; dashboard query parameters are clamped or regex-checked; CLI flags have one parser that fails with a usage line. _Why:_ args, config and MCP input come from chat agents, PRs and other processes, and unvalidated input reaches shell commands, paths and budgets. _See:_ `packages/runtime/src/runtime/engine.ts:532`.
- **Check an outside id as a plain name before it becomes a path.** A jobId or runId from an MCP argument, a CLI flag or a dashboard URL matches `/^[A-Za-z0-9_-]+$/` (`isPlainName`), or is resolved through the runs index, before it is joined into a path. _Why:_ a raw `../` reads or creates files outside `.workflows/`. _See:_ `packages/runtime/src/runtime/state.ts:47`.
- **Treat a URL from run data as untrusted.** Card and row links must be `http(s)` and open with `rel="noreferrer noopener"`; only the exact `https://github.com/<owner>/<repo>/pull/<n>` URL, or `https://<host>/<namespace>/-/merge_requests/<n>` on gitlab.com or a host of glab's own config (host names only, never its tokens), reaches `gh` or `glab`, through `execFile` with a fixed argv, never a shell. _Why:_ the event log holds whatever an agent or issue wrote, and a `javascript:` link, a shell-expanded URL or a link to another host (which `glab` would send the user's token to) turns that into code execution or a leak. _See:_ `packages/runtime/src/runtime/pr-by-url.ts:37`.
- **Render log and agent content as text.** Use React text nodes, and escape interpolated text in server-built HTML. _Why:_ the event log holds prompt-injectable text, and rendering it as HTML would turn an injection into XSS against the cancel action. _See:_ `packages/dashboard/src/pages.ts:5`.
- **Keep personal data out of the repository and the tracker.** Commit under the GitHub noreply identity; fixtures use `example.com` addresses and fake keys; screenshots show only fixture data; reports, issues and PR bodies carry no home paths, usernames or hostnames. _Why:_ the repository is public, and anything in commits, fixtures, issues or PR bodies is published permanently. _See:_ `test/validation-report.test.ts:209`.

## Observability

Enforced by tooling: none. Pinned by behaviour tests, which do not fire on a new site: `packages/runtime/test/retention.test.ts` (content pruning keeps every other event byte for byte); `packages/runtime/test/observability.test.ts` (exports are anonymised by default).

- **Emit typed events, not log lines.** The runtime has no leveled logger: a new fact is an event `interface` in `events.ts` with a literal `type` and doc comments, written through the event log. _Why:_ status, resume, the dashboard graph and the reference doc are all projections of this log, and an untyped line breaks its readers. _See:_ `packages/runtime/src/runtime/events.ts:46`.
- **Bound step content.** Cut each content text at `CONTENT_MAX_CHARS` after redaction, with `truncated` set; when a run starts, prune the content `text` of the repo's other runs beyond the last 30 runs or older than 14 days (`DEFAULT_RETENTION`). _Why:_ content grows without bound and can hold private data, while run history (what ran, cost, duration) must survive pruning. _See:_ `packages/runtime/src/runtime/retention.ts:26`.
- **Metrics exports are anonymised by default.** `repo_name`, `agent_id` and `prompt_text` are nulled and `error` becomes `"[redacted]"`; only an explicit `--no-anonymize` keeps them. _Why:_ the raw DB and a non-anonymised export identify repos, accounts and agents. _See:_ `packages/runtime/src/observability/queries.ts:70`.
- **The recorder only inserts.** Attempt rows are inserted, never updated by summing; a resume of the same `run_id` is a new execution (`exec_id`); journal and memo hits are zero-cost attempts with `cached` set. _Why:_ summing on resume would double-count tokens and cost. _See:_ `packages/runtime/src/observability/recorder.ts:4`.

## Configuration

Enforced by tooling: `packages/runtime/test/limits.test.ts` (every per-run limit is one row of the `LIMITS` table with its global cap, and the resolver and the MCP `overrides` schema read from it); `test/config-reference.test.ts` and `test/repo-layout.test.ts` (a schema change comes with a description per field, the regenerated `docs/reference/config.md` and the setup skill's key list).

- **Config resolves in fixed layers, and caps only tighten.** Precedence is code defaults < global file < repo file < env < flag < MCP override; the global caps then clamp the result (numbers take the minimum, allowlists intersect). Chat overrides can only lower a limit; flags may loosen the repo file but never a global cap; `caps.requireSandbox: true` forces the sandbox on every step. A new config value enters as a layer entry, not a special case. _Why:_ this is ADR-0001's contract, and a PR, a workflow edit or a chat agent must not raise spend, enable cloud steps or turn sandboxing off. _See:_ `packages/runtime/src/config/resolve.ts:4`.
- **A request that would loosen a cap is a violation, not an error.** It becomes a `ConfigViolation` `{ layer, ref, path, requested, applied, message }` that has no effect and is returned to the caller; an invalid value is a `ConfigError`. _Why:_ spending protection must not depend on whether a request is well-formed, and the caller still sees exactly what was ignored. _See:_ `packages/runtime/src/config/resolve.ts:405`.
- **Caps live only in the global file, and cloud is off by default.** Caps and dashboard preferences are honoured only in `~/.cursor-workflows/config.json`; in a repo file they are a violation and ignored; without `caps.allowedLocations` only `local` is allowed. _Why:_ sending code to the cloud and raising spend are the machine owner's decisions, never a PR's. _See:_ `packages/runtime/src/config/resolve.ts:362`.
- **Every effective value carries its provenance.** Key it by a JSON pointer into the effective config (`/limits/maxTokens`), and record config, provenance and violations in the `run-start` event. _Why:_ "why did this run use that model?" is answered from the log and `wf config show`. _See:_ `packages/runtime/src/config/resolve.ts:516`.
- **Collect config errors; never stop at the first.** Validate both files with Ajv (`allErrors`), report every issue in one `ConfigError` with its ref (file, env var or option) and a JSON pointer, and treat unknown keys as errors (`additionalProperties: false`). _Why:_ the user fixes everything in one pass, and a typo never silently drops a setting. _See:_ `packages/runtime/src/config/file.ts:107`.
- **Read config afresh on every use.** Run start, resume, `start_workflow` and `wf config show` load it again, and `start_workflow` loads it before spawning. _Why:_ edits take effect without a server restart, and a broken config is refused before a job exists. _See:_ `packages/runtime/src/mcp-server.ts:137`.
- **Env vars enter config only as the `env` layer.** Config-changing variables (`WF_MAX_TOKENS`, `WF_MAX_CENTS`, `WF_MODEL_<ROLE>`) reach the pure resolver as the `env` layer; operational switches (`WF_HOME`, `WF_METRICS`, `WF_DASH_PORT`, …) are read in one named accessor with a default, next to their use. _Why:_ limits and models need provenance, which only the env layer records, and a scattered `process.env` read cannot be overridden in tests or seen in `wf config show`. _See:_ `packages/runtime/src/runtime/state.ts:10`.
- **A workflow's settings layer only through files.** `meta.settings` resolve as code default < global file < repo file; no env var, flag or chat override reaches them, and no cap clamps them; the workflow reads them from `ctx.settings`. _Why:_ settings are tuning, not spending or reach, so caps and chat overrides must not hit them by name. _See:_ `packages/runtime/src/config/resolve.ts:384`.
- **`forges` layers host by host, through the two files only, and apart from the cells.** The global file, then the repo file, decide each host on their own (a host only the global file names stays); no env var, flag, chat override or cap reaches the map, a host named like a limit (`concurrency`) never meets a cap rule, and an entry that gives `github.com` or `gitlab.com` the other forge is a `ConfigError`, never silently ignored. _Why:_ the forge picks the CLI that acts on the user's issues and PRs, so it is a preference to declare once per host, and a declaration that cannot take effect must say so. _See:_ `packages/runtime/src/config/resolve.ts:393`.

## Baseline

The literature baseline a reviewer applies when this file says nothing on the point. Each item is a labelled heuristic ("possible Feature Envy"), always a judgement call.

### Code smells

From Martin Fowler, _Refactoring_ (2nd ed., ch. 3).

- **Mysterious Name**: a name that does not reveal what the thing does or holds. Rename it; if no honest name comes, the design is murky.
- **Duplicated Code**: the same logic shape in more than one place. Extract the shared shape and call it from both.
- **Feature Envy**: a method that uses another object's data more than its own. Move the method to the data it envies.
- **Data Clumps**: the same few fields or parameters travelling together. Bundle them into one type.
- **Primitive Obsession**: a primitive or string standing in for a domain concept. Give the concept its own small type.
- **Repeated Switches**: the same branch on the same type in several places. Replace with polymorphism or one shared map.
- **Shotgun Surgery**: one logical change forcing edits across many files. Gather what changes together into one module.
- **Divergent Change**: one module edited for several unrelated reasons. Split it so each module changes for one reason.
- **Speculative Generality**: abstraction, parameters, or hooks added for needs nobody has. Delete it and inline until a real need shows.
- **Message Chains**: long `a.b().c().d()` navigation the caller depends on. Hide the walk behind one method on the first object.
- **Middle Man**: a class or function that mostly delegates onward. Remove it and call the real target.
- **Refused Bequest**: a subtype that ignores or overrides most of what it inherits. Replace inheritance with composition.

### Module design

From John Ousterhout, _A Philosophy of Software Design_, and Michael Feathers, _Working Effectively with Legacy Code_.

- **Prefer deep modules.** A new module puts a lot of behaviour behind a small interface. A module whose interface is nearly as complex as its implementation is shallow.
- **The deletion test.** Imagine deleting the module. If the complexity vanishes, it was a pass-through; if it reappears across its callers, it earns its place.
- **The interface is the test surface.** Callers and tests cross the same seam. Needing to test past the interface means the module has the wrong shape.
- **A seam needs two adapters.** Introduce an interface at a seam when something actually varies across it. One implementation is a hypothetical seam.
- **Accept dependencies, return results.** A module receives its collaborators and returns values, so it can be tested through its interface.

### Tests

- **Independent expected values.** The expected value is a known literal or a worked example, never recomputed the way the code computes it.
- **Vertical slices.** One test, then the code that passes it. Tests written in bulk ahead of the code verify imagined behaviour.
### React

- **Effects clean up after themselves.** An effect that starts a timer, listener, observer, fetch or stream returns a cleanup that stops it, and an awaiting effect checks a stale flag before it sets state.
