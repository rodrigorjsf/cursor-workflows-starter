## What was built
- The dashboard is its own workspace package, `packages/dashboard` (`@cursor-workflows/dashboard`). The old `observability/dashboard.ts` moved there (the metrics page is now `src/metrics-page.ts`, still served at `/`). `npm run dash` runs `packages/dashboard/src/main.ts`.
- A read-only JSON API over every repo: `GET /api/runs?limit=` (runs from the global runs index, newest first, status from each run's event log), `GET /api/runs/<runId>` (progress lines, result, token usage), `GET /api/summary?days=` (the existing metrics summary), `GET /api/health` (`{app, pid}`).
- It starts on a machine with no history: no runs index and no metrics database give empty lists, and the database is opened the first time it exists, without a restart (the old dashboard exited with "banco de métricas não encontrado").
- It listens on 127.0.0.1 only, refuses any Host that is not `127.0.0.1` or `localhost` (403), accepts only GET/HEAD, sends no CORS headers.
- `start_workflow` makes sure the dashboard runs (probe of `/api/health` on `WF_DASH_PORT`, default 4317, plus a pid file; detached spawn when nothing answers; one instance) and returns `dashboardUrl` (`http://127.0.0.1:<port>`) next to `jobId`/`runId`; when it cannot start, `dashboardWarning` carries the reason and the job starts anyway.
- The switch: `dashboard.autoStart: false` in the global config file (a `dashboard` key in the repo file is a violation with no effect) or `WF_DASH_AUTOSTART=off`. A dashboard already up is still reported when the switch is off.
- The `run-workflow` skill (step 2) opens `dashboardUrl` in Cursor's built-in browser, once per conversation, and relays `dashboardWarning`.

## Decisions & deviations
- **Link form: `http://127.0.0.1:<port>`** (spec allowed this or listening on both loopbacks). The server binds IPv4 loopback only; a test asserts `::1` is refused. The Host check accepts `127.0.0.1` and `localhost`.
- **Not verified inside Cursor's built-in browser.** The spec asks to verify the chosen form there too. That needs the Cursor IDE; this run could drive only Windows Chrome and Windows curl. It belongs to the dashboard validation of ticket #32 (wizard scenario 7). Cursor's docs only show `localhost` URLs for the built-in browser; if `127.0.0.1` is refused there, the fix is to also listen on `::1` (the Host check already accepts `localhost`).
- **"Metrics summary" per run**: the ticket sentence "serves each run's projection and metrics summary" is read as the run projection (which carries the run's spend and token usage replayed from its log) plus the global `/api/summary`. No per-run query against the metrics database was added; the spec does not describe one.
- **Run status**: `running | finished | failed | cancelled | missing`. A run whose latest execution never wrote `run-end` is `running` only while a process holds its run lock; otherwise `failed` with the `resumeRunId` hint, the same rule a job follows. `missing` is a run in the index whose log cannot be read (repo or run directory gone). Reading never creates a directory in a repo (tested).
- **Config switch lives in the global file only** (`dashboard.autoStart`), because the dashboard is one per user; a repo-file `dashboard` key is a `violation` like `caps`. Plus env `WF_DASH_AUTOSTART=off` (also what the tests use). `docs/reference/config.md` is regenerated.
- **One instance**: the OS port bind is the real guarantee; the pid file (`<WF_HOME>/dashboard.pid`) is created atomically (write aside + hard link) by the caller that starts the process, so overlapping callers start one process between them. A live dashboard whose probe times out is waited for, never replaced. Known limit (documented in the code): two callers finding the same stale record at the same instant can both spawn; the loser exits 0 and the answering dashboard corrects the pid file.
- **The runtime launches the dashboard by file path** (`packages/dashboard/src/main.ts` next to the runtime), like `spawnJob` finds `cli.ts`. It is a file to run, not an import, so ADR-0004's dependency direction (dashboard to runtime only, through `@cursor-workflows/runtime/observe`) holds. An install that lacks the package (the relocated-kit tests copy only the runtime) gets `dashboardWarning`, not a failure.
- **`start_workflow` waits for the dashboard to answer** (default 10 s, `WF_DASH_START_TIMEOUT_MS` for tests) so the link is live when the chat has it; the job is spawned before the wait. A start still in progress at the end is reported with its link.
- The dashboard child gets the caller's environment minus `CURSOR_API_KEY`, and its output goes to `<WF_HOME>/dashboard.log`.
- Scope the reviewers called extra, kept: `?limit=` (bounds how many logs a request reads), the 405 gate (the dashboard is read-only), the `missing` status (an index entry can outlive its repo).
- `docs/adr/0004-…` sentence "A dashboard package is reserved for a later spec" now says the package exists. CHANGELOG, `docs/operating/03-observabilidade.md` §5, `docs/usage/03-invocacao-no-cursor-ide.md`, `docs/contributing/01-contribuindo.md` updated.

## Learnings
- Applied Learning in `CLAUDE.md` says "Windows Chrome → WSL dashboard: use `127.0.0.1:4317`; `localhost` is refused". On 2026-11-12 (NAT mode) Windows Chrome and `curl.exe` also reached `localhost`; `127.0.0.1` worked every time. Keep the bullet's advice, but the "refused" part is not reproducible. I could not edit `CLAUDE.md`.
- `CLAUDE.md` "What this repo is" should list `packages/dashboard/` next to `packages/runtime/`.
- WSL2 NAT needs about 0.5 s to forward a newly bound port to Windows: the first request in that window is refused. The skill tells the agent to reload.
- `tsx --tsconfig <relative>` reaches a spawned child through the environment/exec args as a relative path: a child started with a different `cwd` fails with "Cannot resolve tsconfig". The dashboard child therefore inherits the caller's `cwd`.
- `pkill -f '<pattern>'` kills the calling shell when the pattern appears in the command line; use the `[d]ashboard` bracket trick with `pgrep`.
- `import "@cursor/sdk"` costs about 230 MB resident and 0.6 s: keep it out of long-lived helper processes.
- `npm`/`node` on this machine: `mise exec node@22.23.4 -- npm ci`.

- Tests of any MCP server that calls `start_workflow` must set `WF_DASH_AUTOSTART=off` (or a free `WF_DASH_PORT` and clean up the pid in `dashboard.pid`).
