## What was built
- `GET /api/runs/<runId>/events` is a Server-Sent Events stream of the run's event log. It replays what the log holds, then sends each event as the run appends it (the server looks at the file every 200 ms). Each message is the event exactly as the log has it; its `id` is the event's **line number in the log, from 1**.
- Resume: the `Last-Event-ID` header (what a browser's `EventSource` sends when it reconnects) or `?lastEventId=<n>` (the header wins). The stream continues on the next line. A value that is not a whole number is a 400.
- `?content=false` leaves `content` events out (the bulk of a log). `?stepId=<id>` keeps only the events of one step (an `agent()` call or a `ctx.exec` command).
- `GET /api/runs/<runId>/steps/<stepId>/content` returns `{runId, stepId, lastEventId, content}`: every `content` event of the step (prompt, agent messages, tool calls, command output) in log order across attempts, each with its `id` and `attemptId`. Text is returned as the log holds it, already redacted at write time. `lastEventId` is where the log stood, so `events?stepId=…&lastEventId=…` continues the step's live log with no gap and no repeat.
- Events of other schema versions (`v` 0, 2, 7, no `v`) and unknown types pass through untouched; blank and damaged lines use up an id and are not sent. A line is sent only when complete (half-written lines wait for their newline).
- A log the projection cannot digest used to make `GET /api/runs` answer 500 for every run; now only that run is listed, as `missing` with the reason.
- Docs: `docs/operating/03-observabilidade.md` §5 ("Acompanhar um run ao vivo"), contributor tree, CHANGELOG.

## Decisions & deviations
- **Event id = line number (1-based)**, not byte offset: retention rewrites a log by replacing the file, keeping every line but removing `text`, so byte offsets would shift while line numbers do not (`retention.ts` `withoutContentText`). The tail remembers the inode: when the file is replaced it recomputes its byte offset from the line count (test: "a stream stays right when the retention pass rewrites the log under it").
- **The stream never ends by itself.** A resumed run appends to the same log, and a client may open the stream before the run's first event. The client decides when to stop (a `run-end` is in the data). Cost: one `stat` per 200 ms per open stream. Reviewer suggested slowing or ending it after `run-end`; dismissed, see Code review.
- **Polling, not `fs.watch`:** the repo may live on a filesystem (WSL `/mnt/c`) that does not report changes.
- **`Last-Event-ID` header wins over `?lastEventId=`** (a reconnect has progressed past the first URL).
- **Step content 404 text is `run or step not found`** (one answer for an unknown run and an unseen step). A step with events but no content (served from the journal) is 200 with `content: []`.
- **No re-redaction at read time.** The log's `text` is redacted before it is written (`prepareContent`, then `redact`), which ADR-0002 makes the rule. Redacting again with the dashboard's own environment would not match the run's environment, and could mangle text with env values.
- **`missing` now also means "could not be projected"** (it meant "log gone"). The `error` names the log. I did not filter events by `v` before projecting: only schema version 1 has ever existed (the event log landed in `cc01118` at v1), so "older" shapes are synthetic, and ignoring a newer `run-end` would give a wrong status. The guarantee is containment per run; stream and step content do not project at all.
- Small supporting changes in the runtime: `isEvent` exported from `run-store.ts`, `parseJsonlLine` added to `state-files.ts` (shared by `readJsonl` and the tail), `eventLogOf`/`indexedRun`/`logOf` in `run-view.ts`.

Dismissed:

- Spec, "large logs are read whole": measured on a 48 MB log of 1500 32 KB content events: replay read+parse 121 ms, `JSON.stringify` of the replay 428 ms, about 200 MB transient, 100 idle polls under 1 ms. The existing `listRuns` takes 294 ms on the same file. Same order as every reader here, bounded by the retention (30 runs, 14 days), paid once per connection; incremental polls read only the new bytes. Chunking would need backpressure and handling of a line longer than a chunk, for no measured need.
- Spec, "streams of finished runs poll forever / a deleted run directory leaves an empty stream open": a recorded decision (client closes; a resumed run continues in the same stream); the cost is a `stat` per 200 ms.
- Spec, redaction: the reviewer agreed returning the log's text satisfies the criterion.

## Learnings
- `http()` in `test/support.ts` waits for the body to end, so a GET on an SSE route hangs the test forever; use `openStream`. Run node:test files with `--test-timeout=8000` when writing stream tests, or a hang looks like a stuck tool call.
- `tsx` is not resolvable from outside the worktree: to run a throwaway `.mts` from the scratchpad, `node --import <worktree>/node_modules/tsx/dist/loader.mjs file.mts`. A child spawned with `--import tsx` needs the worktree as its `cwd`.
- A real `EventSource` is available in Node 22.23 behind `NODE_OPTIONS=--experimental-eventsource`; it is enough to check ids and `Last-Event-ID` reconnect without a browser.
- `pkill -f '[t]est/stream.test.ts'` (bracket trick) cleans a hung test run; `npx tsx` leaves grandchildren, so check `pgrep` afterwards.

## Notes for dependent tickets
- **Runtime entry point** (`@cursor-workflows/runtime/observe`): `tailRun(runId, {after?, content?, stepId?})` returns `{poll(): {id, event}[], lastId}` (undefined for a run the index does not know); `readStepContent(runId, stepId)` returns `{runId, stepId, lastEventId, content: (ContentEvent & {id})[]}` or undefined. Types: `LoggedEvent`, `RunTail`, `StepContent`, `StepContentItem`, `TailOptions`.
- **For the DAG (#31):** open `events?content=false` once per run view; ids are line numbers; on `EventSource` reconnect the browser sends `Last-Event-ID` itself. Close the `EventSource` yourself when the latest execution's `run-end` has arrived (the server never ends the stream). A resumed run adds a new `run-start` to the same stream.
- **For the step log (#31):** `GET …/steps/<stepId>/content`, then `EventSource('…/events?stepId=<stepId>&lastEventId=<lastEventId>')` (the stream also carries the step's `step-start`, `turn`, `exec-*`, `step-end`). `text` may be absent when retention pruned it (`chars` stays). Step ids of `ctx.exec` commands start with `x-`, agent steps with `s-`.
- **A browser `EventSource` does not retry after a non-200 reply** (it stays CLOSED). `start_workflow` returns the run id before the run process registers the run in the index (it does so after writing `run-start`), so the stream route can answer 404 for a few hundred ms: wait for `GET /api/runs/<id>` to be 200 before opening the stream.
- **Unknown or old events reach the browser as they are** (`v` is in every event). The projection used by `/api/runs` ignores unknown types; a run it cannot project shows as `missing` with the reason.
- **Routes** are the `default` branch of the `switch` in `route()` (`packages/dashboard/src/server.ts`), after the Host and method checks, so new routes inherit both. CSRF for cancel (#32) is still not there; a POST gets 405.
- **Test helpers** for stream tests: `openStream`, `appendLog`, `eventLine`, `logPath` in `packages/dashboard/test/support.ts`.
- Tests that start a dashboard on a port must close it; an open stream keeps nothing alive after `close()` (it calls `closeAllConnections()`), but a test that forgets `close()` hangs the runner.
