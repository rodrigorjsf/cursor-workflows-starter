## What was built
- `scripts/install.sh` and `wf upgrade` (`packages/runtime/src/upgrade.ts`) no longer fetch tags with `--force`. A tag that exists in the clone and moved upstream fails the fetch, and the message says `moved upstream ... Do not install/upgrade until the repository owner explains the move`. The kit stays where it was.
- Before any checkout, both read `https://api.github.com/repos/rodrigorjsf/cursor-workflows-starter/releases/tags/<tag>` (no token) and stop unless `immutable` is `true`. A missing release (`has no release for tag`), a release that is not immutable (`is not immutable`) and a failed call (`could not read the release of`) are all errors, never a skip.
- `--allow-mutable-tag` (`install.sh --tag ...`, `wf upgrade`) skips only that lookup, for a fork given with `--repo`. The lookup covers only the official repository, so a kit whose origin is another repository is refused without the flag.
- `WF_GITHUB_API_URL` (tests only) replaces `https://api.github.com`, so a fake server can answer.
- Docs updated: INSTALL-AGENT.md, book 2.1 (new section "Tag movida e release que não é imutável"), SECURITY.md, CHANGELOG, maintainer scripts chapter 9.4, setup skill, CLI usage line.

## Decisions & deviations
- **The release check covers only the official repository.** The ticket writes `<KIT_REPO>`; I read it as: the answer for a tag of the same name in the official repo says nothing about a fork's, so an origin that is not `https://github.com/rodrigorjsf/cursor-workflows-starter(.git)` is refused unless `--allow-mutable-tag`. `install.sh` derives the slug from its `default_repo`; `upgrade.ts` uses `KIT_REPO`.
- **The origin is read as configured** (`git config --get remote.origin.url`), not with `git remote get-url`, which expands a user's `url.<base>.insteadOf` (common: https to ssh) and would make an official clone look foreign. Comparison strips a trailing `/` and `.git` on both sides, in bash and TS alike. An SSH or differently-cased origin of the official repo is refused (fail closed) and the message names the flag.
- **`WF_GITHUB_API_URL` only swaps the API base.** A first version also skipped the origin check when it was set; both reviewers flagged it as a hidden test-only branch weakening a security check, so it was removed and the tests use the `insteadOf` redirect instead.
- **Order in `install.sh` for an existing clone:** the origin and release checks run before `remote set-url` and before the fetch, so a refusal leaves the clone's origin and tags alone (a moved tag still fails at the fetch, after `--repo` replaced the origin, as before). `wf upgrade` checks the origin before the fetch, and the release after it (it needs the newest tag).
- **`git fetch --tags` without `--quiet`, with `LC_ALL=C`:** `--quiet` hides the `! [rejected] ... (would clobber existing tag)` line, and a translated git would not match it. The output is captured and shown only on failure. In `upgrade.ts` every git call runs with `LC_ALL=C`.
- **`upgradeKit` is async** (`fetch`) and takes `UpgradeOptions { allowMutableTag }`; `wf upgrade --allow-mutable-tag` is a flag of the CLI's shared `FLAGS` table, like `--dry-run`, which other commands accept and ignore. The installer rejects `--allow-mutable-tag` with `--dev` or `--refresh` (exit 2).
- **`install.sh` does the HTTP call with `node -e`** (global `fetch`, `JSON.parse`): node is a required tool anyway, no `curl`/`jq` added. A Node without `fetch` gets its own message. The tag must match `[A-Za-z0-9._-]+` to be put in the URL.
- **Existing tests changed:** "`--repo` given again" used two unrelated repositories that share the tag name `v0.3.0` (different commits), which the moved-tag protection rightly refuses; it now uses a real fork and `--allow-mutable-tag`. The old-Node fake now delegates everything but `--version` to the real node, because the release lookup runs a script on it.
- **New recorder** `scripts/verify/record-release-fixtures.ts` (with a 9.4 table row and a CHANGELOG entry): the repo's Testing rule says a fake of an external service answers from a recording, never from hand-written output. It scrubs repository, owner, release notes and the author's profile. Real calls: 4 unauthenticated GETs to api.github.com (recording twice, two manual probes), no cost, no cap needed.
- `upgrade.ts`: the local `messageOf` became `errorText` (Error handling standard).
- No `CLAUDE.md` or `AGENTS.md` edited.
- INSTALL-AGENT.md is pinned to `v0.4.0` and now describes the check, which the `v0.4.0` installer does not have: like the rest of the unreleased docs on main, it becomes true with the next release (the `v0.4.0` copy of the guide stays the old text).

## Learnings
- `git fetch --quiet` hides the `! [rejected] ... (would clobber existing tag)` line: capture the output without `--quiet`, and run git with `LC_ALL=C` before matching its words.
- `git remote get-url` expands `url.<base>.insteadOf`; read `git config --get remote.origin.url` for what the user configured. In tests, `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=url.<local>.insteadOf GIT_CONFIG_VALUE_0=<real url>` makes a real URL resolve to a local repository.
- Node's `fetch` refuses low ports (port 1 answers "bad port"): to test a refused connection, bind port 0, read the port, close it.
- `spawnSync` blocks the event loop, so an HTTP fake for a spawned product must be its own child process, steered through files.
- `npm run check` in a subshell `( ... ) &` plus `run_in_background` fires the completion notice at once while the check still runs: start it once with `run_in_background` and no subshell.
- `gh` token here has no `delete_repo` scope (from #62), irrelevant here but still true.
