## What was built
- The Run view of a `failed` or `cancelled` run has a **Resume run** button beside **Copy resume command**. It is hidden for a run that is running, finished, unreadable, or frozen (failed, but its process still holds the run).
- `POST /api/runs/<runId>/resume` (no body) sits behind the same CSRF token + origin `gate` as cancel and start. The server reads the run's latest job record (`JobStart`: args, `maxTokens`, `maxCents`, `overrides`) and starts a new job over the same run (`wf start --resume` semantics) through the same start path as `POST /api/start`. Answer: `202 {jobId, runId}` (+ `violations` when a global cap cut the request).
- Refusals are `{ error }` with a sentence: 403 gate, 404 unknown run, 409 for a run that is not stopped, frozen, outside the retention (journal emptied), without a job start (the sentence says to resume it from the terminal with the copied command), and for what the start path refuses (workflow no longer listed, args no longer valid, config unusable, kit out of range, the same job already running). `GET` on the address is 405 with `allow: POST`.
- After a 202 the page asks for the run's status every second (up to 30 s) until it shows `running`, then follows it like any running run.
- Runtime side: `resumeRun` (`observe`) in the new engine-free `run-resume.ts`; `startRun` and `resumeRun` now share `launchJob` (`run-start.ts`).

## Decisions & deviations
- **Caps and overrides are repeated exactly as recorded**, including no caps when the first start had none (a terminal `wf start` without flags). The config caps (global and repo) still apply on top. The ticket says "the args, caps and overrides of its latest start"; refusing a resume with no recorded caps would make the button useless for runs started from the terminal. The "both caps required" rule is the Start panel's.
- **A resume whose caps the run's budget already used up fails at once**: the budget accumulates across resumes (`budget-resume.test.ts`: a cap passed to a resume is the new total cap), and this button repeats the old cap. Documented in 5.3 (resume with the copied command and a larger `--max-cents`/`--max-tokens`). Not changed.
- **Status codes:** 202 on success (a job starts on its own, as with Start); 404 only for an unknown run; every state or content problem of an existing run is 409 (including the start path's `unknown-workflow` and `invalid-args`, which are 404/400 on Start because there the browser typed them).
- **The button shows for a failed/cancelled run with no job start** and refuses on click with the terminal sentence, as the ticket words it.
- **A tiny local type for the reply in `run-view/run-actions.ts`** (`{ jobId: string }`): the `run-view` tsconfig has `types: []` and must not import server code (importing `ResumedReply` from `src/` dragged the runtime sources into that project and failed `tsc`).
- **Heading unchanged:** the new Resume bullet sits under "Cancelar um run e copiar o comando de resume" in 5.3; renaming it would break four anchors and the `§` citation in chapter 1.
- No ADR, no `CLAUDE.md` edit: the existing sentence ("starts one in a repo the index names") still holds.
- Texts updated: `CODING_STANDARDS.md` (gated actions rule), `docs/operating/03-observabilidade.md` (API table, Resume bullet with the refusal table, CSRF and security lists), `docs/contributing/01-contribuindo.md` (file map), `SECURITY.md`, `CHANGELOG.md`, `packages/dashboard/package.json` description, header comments of `server.ts`, `observe.ts`, `run-start.ts`.

## Learnings
- `npm run check | tail` reports tail's exit code: redirect to a file and print `$?`, or a failing suite reads as green.
- A dashboard test may not import `packages/runtime/src` (only `engine-log.test.ts` may): `test/repo-layout.test.ts` fails the root suite; copy a tiny helper into `support.ts`.
- `run-view/` is typechecked with `types: []`: never import `src/` (server) modules from it, even type-only; declare the reply type locally.
- A fixture run held by the test process's own pid is not "running": `isHeld` ignores a lock the process did not take; hold the lock with a child process.
- The fake SDK charges 9 cents an attempt and a resume starts from the spent total: give process tests caps with room, or the resumed run fails at the cap check.

## Notes for dependent tickets
- **Approve/replace seams (#98):** add routes beside `resume` in `packages/dashboard/src/server.ts`, call `gate(req, res)` first, and put the reply mapping in a pure `src/<action>.ts` like `src/resume.ts`. `launchJob(repo, workflow, { args, maxTokens, maxCents, overrides, resumeRunId })` (`run-start.ts`) is the one start path: a resume with `approveSeams`/`seams` is a resume with other args, so it can call it with the recorded start plus the change. - `resumeRun(runId)` (observe) returns `ResumeRunOutcome`: `unknown-run | not-resumable | frozen | no-start | started | unknown-repo | unknown-workflow | invalid-args | refused`. It resumes only `failed` and `cancelled` runs, as this ticket says. A run that stopped at a checkpoint (the `implement-issue` run that proposed seams) is `finished` with outcome `pending` (`RunSummary.outcome`, classed by `runtime/outcome.ts`), so `resumeRun` refuses it (409 `the run is finished…`): #98 has to widen the check for `pending` (or add its own door over `launchJob`) and must not assume the Resume button covers it.
- Test helpers for a real resumable run: `RESUMABLE_WORKFLOW`, `jobProcesses`, `postWithToken`, `runDetail`, `eventsOfRun`, `jobRecordOf` in `packages/dashboard/test/support.ts`; name such a test `*.process.test.ts`.
