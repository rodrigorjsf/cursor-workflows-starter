## What was built
- When a MED or HIGH `implement-issue` run that proposed seams (or a test command) is resumed with `approveSeams: true`, the workflow posts one comment on the issue through the forge seam: heading `Seams approved for the implement-issue run <runId>`, the stored plan's seams (name, interface, why), and "The run goes on with exactly this plan."
- A resume with `seams: [...]` posts the same comment as `Seams replaced`, listing the given seams as code spans, and "The run plans again with these seams."
- A resume that ends in `seams-not-proposed` posts nothing. A fresh run given `seams` posts nothing (no proposal to replace).
- A decision is posted once. The progress records it (`seamsDecision`) after the comment is on the issue, and before posting the run also reads the issue's comments, so a crash between the post and the record does not make the resume post it again.
- Works on GitHub and GitLab (every new test runs on both fakes). The text goes through the same redactor, secret guard and sanitizers as the proposal comment.

## Decisions & deviations
- **Only a run that holds a proposal posts.** The trigger is `progress.data.proposedPlan`. A fresh run given `seams` replaces nothing, and two existing tests already asserted zero comments there. LOW never proposes, so it never posts.
- **A replacement is posted even when the resume stops again at `test-command-proposed`.** That is the dashboard's normal replace (no `testCommand`); the decision comment comes first, then the command's own comment.
- **An approval after a `test-command-proposed` stop posts `Seams approved`** with the stored plan's seams (the seams a person gave in the first run). Matches the ticket's literal rule ("resumes with `approveSeams: true` and a proposed plan exists").
- **Same args resumed after a `test-command-proposed` stop posts `Seams replaced`** (a resume with `seams`, a proposal on record). I first recorded-without-posting to avoid this; both reviewers flagged that record-only state (Spec: the ticket says a resume with `seams` posts; Standards: Speculative Generality), so I dropped it and followed the ticket literally. One existing test changed for it.
- **Dedupe in two layers:** the progress field `seamsDecision` ({decision, seams}), recorded after the post (the ticket's "progress records that it was posted"), plus a comment-equality check against the issue's comments inside `postOnce` for the crash window between post and record. A different decision on the same run (replace after approve, approve after replace) posts again and replaces the record.
- **New marker** `<!-- wf:implement-issue:seams-decision -->`, apart from the proposal's marker, so the proposal's own dedupe (marker + run id) never sees it.
- **Refactor beyond the ticket:** `prose`, `redactOutbound` and `seamLine` moved from the stop block to the top of `run()`, and a closure `postOnce(text, isPosted)` (redact, secret guard, read the issue's comments, post unless present) now serves both the proposal and the decision comment (review finding "Duplicated Code"; the proposal's behaviour is unchanged and its tests stay green).
- **Existing tests changed, only as far as the new comment requires:** `implement-issue.workflow.test.ts` "MED: primeiro run propõe..." (proposal comment once, total 2, second is the approval); `implement-issue.exec.test.ts` "the next line approves the stored plan..." (2 comments, second `Seams approved`), "a run that proposed seams and is then resumed with seams still posts the test command..." (3 comments: seams, replacement, test command), "the same stopped run resumed with the same args stops again and posts the command once" (one test-command comment, plus the replacement).
- **Texts updated per "a behaviour change updates every text that describes it":** `CHANGELOG.md` (`## Não lançado` / Adicionado), book chapters `docs/authoring/01-escrevendo-workflows.md` (checkpoint step 3) and `docs/authoring/02-convertendo-skills-e-subagents.md` (the `tdd` row), `docs/operating/03-observabilidade.md` (what the redactor covers), `SECURITY.md` (the data-recipients table, two cells), `skills/run-workflow/SKILL.md` (one word: "the block at a seams comment"), the header comment and the `Args` JSDoc of `implement-issue.ts`. No `CLAUDE.md` or `AGENTS.md` edited. The two `recipes.md` skill copies were left alone: they describe the generic checkpoint pattern and stay accurate.
- The dashboard does not comment on its own (spec); nothing in `packages/dashboard` changed.

## Learnings
- The session scratchpad is shared by every parallel ticket agent: a log named `green1.log` was overwritten by another agent's run. Log to a ticket-private subdirectory (`scratchpad/t<id>/`).
- A fixed-name scratchpad file is not yours: check `ls -la` times before trusting a log you did not just write.
- `forgeTest` registers each case per forge: a new implement-issue test file needs no `beforeEach`, and the fixture's forge state resets with every `issue(...)` call.

## Notes for dependent tickets
- New progress field `Progress.seamsDecision?: { decision: "approved" | "replaced"; seams: string[] }` (`packages/runtime/workflows/implement-issue/tdd.ts`, with its zod line).
- Comment marker `<!-- wf:implement-issue:seams-decision -->`; heading `## Seams approved|replaced for the \`implement-issue\` run \`<runId>\``. A ticket that reads or filters the issue's comments (the dashboard's seam approval, the Backlog) can tell a decision from a proposal by the marker.
- The dashboard's approve and replace actions need no comment code: they resume with `approveSeams: true` or `seams: [...]`, and the workflow posts. Note that a replace without `testCommand` ends at `test-command-proposed`, with the decision comment already posted.
