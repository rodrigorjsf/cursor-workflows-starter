## What was built
A capped real-API measurement of the live token caps' granularity, and the cap docs rewritten to the measured bound.
- New workflow `scripts/verify/verify-turn-granularity.ts`: one long local write step through the engine, plus two direct SDK sends (token-delta counting, and a `Run.cancel()` mid-turn probe).
- Measured twice on 2026-11-14 (`composer-2.5`): one `turn-ended` per long send (31 and 24 tool calls, 267,526 and 133,969 tokens), `token-delta` totals 1.53x and 1.41x `outputTokens` (about 4% of `totalTokens`, not a sum of the usage), `Run.cancel()` mid-turn settles in 3 ms with status `cancelled`, no `turn-ended`, no `RunResult.usage`.
- Decision rule 3: the caps act between sends; inside a send only `timeoutMs` brakes. No engine behaviour change. The book, the skills, the config reference source, the event JSDoc and the CHANGELOG say so.

## Decisions & deviations
- Rule 3, not 2: "token-delta summable" read as summing to a figure of `RunResult.usage`. It does not (1.41 to 1.53 times output), and even a match would cover under 5% of `totalTokens` (input resent per model call dominates), so no estimate could track the cap. Nothing else in the SDK signals usage mid-send (`step-completed` arrives once, at the end).
- The token-delta and `Run.cancel()` measurements use the SDK directly inside the workflow (the engine does not forward `token-delta`). Those two sends are not under `--max-tokens`: each is bounded by `SEND_TIMEOUT_MS` (8 min), the README says so, and the workflow refuses to run without both caps.
- The cancel probe is a direct `Run.cancel()` at the 3rd `tool-call-started`; the token-delta total never reached its 3,000 cap in about 5 s. The engine's own cut path is read in code (`cutters`, `AttemptAbort.cut`, `RunCanceller`), not measured; the docs say which is which.
- Ran the workflow twice (repeatability). Spend: `spentCents` 0 and `chargedCents` 0 (plan-included); list price about 11 and 8.5 cents, so about 20 of the 100 cents shared with #62. `getUsage()` is `feature_unavailable` on this account, so the cents cap is blind and only `--max-tokens` protects.
- Docs edited beyond the two named chapters, because each stated the old bound (CODING_STANDARDS: a behaviour change updates every text that describes it). `## Não lançado` opens above 0.4.0 in the CHANGELOG.
- The script revision committed after review (refactor: constant rename, one `tally` helper, `atMs`, caps guard, `revertOnRetry`, header cost line) was typechecked, its helpers unit-tested and the caps guard run for free, but not re-run on the real API; both measured runs used the revision before those edits (same logic).
- Disposable probe repos, throwaway `WF_HOME` and metrics DB lived in the session scratch area and were removed.

## Learnings
- `wf whoami` prints the account e-mail: never paste its output into a handoff, issue or PR (the repo is public).
- The SDK delivers `token-delta` only as output-ish deltas (1 to 2 tokens, occasional 120) and the engine drops them: a workflow that needs them must call the SDK itself, with a lazy `await import("@cursor/sdk")` so root tests can import its helpers.
- On this account `getUsage()` is `feature_unavailable` for local agents: `--max-cents` never fires, a mid-send cancel returns no usage, and only `--max-tokens` (checked at each send's end) protects.
- Run a long real-API workflow with `run_in_background` writing stdout and stderr to files, then wait on its exit notification; a foreground `sleep` is blocked.
