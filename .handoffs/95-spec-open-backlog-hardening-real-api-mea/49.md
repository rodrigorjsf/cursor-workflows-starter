# Handoff — #49: Cancelling a frozen job leaves its ctx.exec commands running

Status: DONE
Spec: #95   Ticket: #49
Branch: spec/95-spec-open-backlog-hardening-real-api-mea--49   Base: f86a68a   Head: a70927f (code head; the handoff commit follows it)

## What was built
Cancelling a frozen job (process alive, heartbeat stale; `wf cancel`, `cancel_workflow`, the dashboard's Cancel) now takes the job's commands with it.
- Each live `ctx.exec` command's process group is recorded in `.workflows/jobs/<jobId>.exec-group.<pgid>` (written at spawn, removed when the command ends) by the new module `packages/runtime/src/runtime/job-children.ts`.
- The SIGKILL branch of `cancelJob` calls `killFrozenJob`: SIGSTOP the job, kill the recorded groups and the job's detached direct children (found in `/proc`), SIGKILL the job, kill the job's own group, delete the records the killed process cannot drop.
- A running job's cancel (SIGTERM, revert, `cancelled`) is untouched.
- A record that cannot be written is a `warning` event; the command still runs, out of the cancel's reach.

## Decisions & deviations
- **Where the groups live.** A file per group in the jobs folder, not a field of the job record and not in the run directory: the heartbeat worker rewrites the whole record from a startup snapshot (a main-thread field would be clobbered, and a frozen main thread could not update it), CODING_STANDARDS says a new record field needs an ADR, and the run directory is `RunStore`'s. One file per group means no read-modify-write between parallel `ctx.exec` calls. The module header says why.
- **SDK local agent question (answered from SDK 1.3.1 source, `node_modules/@cursor/sdk/dist/esm/305.js` and `587.js`):** the local agent is not a subprocess; it runs inside the job's process, so the job's SIGKILL ends it. What it starts: the shell commands of its tools are spawned `detached: true` (own process group, `/bin/sh -c`), and MCP stdio servers are spawned by `StdioClientTransport` with no `detached` (the job's own group; the job runs detached, so it leads one). Both survive a SIGKILL of the job pid. This change kills the first via a `/proc` scan of the job's direct children that lead their own group, and the second via a kill of the job's own group. **Not verified with a real agent shell command or a real MCP server** (no API spend is authorised in this ticket); verified with stand-ins (a `sleep` the fixture spawns detached, and one spawned in the job's group).
- **Order inside the kill** (`killFrozenJob`): SIGSTOP first because "frozen" only means a stale heartbeat (a process whose heartbeat worker died can still run its main thread); a stopped process spawns nothing and reaps nothing, so the groups read are the groups killed and their numbers cannot have been reused. Children are signalled before the job dies because a child that loses its parent is no longer found through it. `kill(-pid)` on the job's own group is safe: a group id equal to the job pid exists only if that process leads it, and `cancelJob` already checked the pid is the job's process (`isJobProcess`).
- **Platform limits, documented, not fixed:** where `/proc` is missing (macOS) detached SDK children are not found (recorded `ctx.exec` groups and the job's own group still are); on Windows `runCommand` has no process groups (`OWN_GROUP`), so nothing is recorded there. The kit is tested on Linux only (`docs/usage/01-instalacao.md`).
- **Not changed:** the cancel note text (its prefix is quoted by skills and dashboard tests); the dead-job path (no signal, as the spec says). A job that dies by crash, OOM or a second signal while a command runs leaves its `<jobId>.exec-group.*` files; they are never read for a dead job (job ids are unique) and are tiny.
- **Docs updated** (CODING_STANDARDS "a behaviour change updates every text that describes it"): CHANGELOG `### Corrigido` under `## Não lançado`; book chapters `docs/internals/01-arquitetura.md`, `docs/operating/03-observabilidade.md`, `docs/usage/03-invocacao-no-cursor-ide.md`, `docs/vision/03-conceitos.md` (Travado, and the on-disk table), `docs/contributing/01-contribuindo.md` (module map); `skills/run-workflow/SKILL.md`; MCP `cancel_workflow` description, `wf cancel` usage line, comments in `cli.ts`, `run-cancel.ts`, `job-state.ts`. ADR-0003 is untouched: ticket #50 writes ADR-0010, which should list "a frozen job is killed with its `ctx.exec` groups, its detached children and its own process group, after a SIGSTOP".

## Learnings
- A fresh worktree under `.git/run-spec/...` needs `mise exec -- npm ci --prefer-offline` before any test (already an Applied Learning bullet of the repo).
- A grandchild of a test's child (e.g. the `sleep` a job started) becomes a zombie until PID 1 reaps it: a test that asserts "process gone" must treat state `Z` in `/proc/<pid>/stat` as gone, and poll with `waitFor`.
- Start a job-process fixture with `detached: true` (as `spawnJob` does) so it leads its own group and the test can clean up everything with one `kill(-pid)`.
- `process.kill(pid, "SIGSTOP")` before reading `/proc` freezes the child table of a process that is only "frozen" by heartbeat.
