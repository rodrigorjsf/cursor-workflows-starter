## What was built
Every MCP tool of `packages/runtime/src/mcp-server.ts` now has a strict zod input schema (`z.strictObject`), so an argument the tool does not list, or one of the wrong type, comes back as `isError: true` with the SDK's text naming the property, and no job is created. `tools/list` now advertises `additionalProperties: false` on every tool. `start_workflow` checks the workflow's `args` against `meta.argsSchema` with the engine's own validator (`argsError`) before the config, the dashboard and `spawnJob`, so a bad `args` is refused at once as `{ "error": "invalid args: ... <field>" }` and not on a later `wait_workflow`. `wait_workflow` keeps accepting a numeric string, `null` and a number outside 1..50 for `timeoutSec`. A repo test fails if a `registerTool` call has a schema that is not strict.

## Decisions & deviations
- **`timeoutSec` stays `z.unknown().meta({ type: "number", minimum: 1, maximum: 50 }).optional()`.** The AC keeps a numeric string accepted, and `wait-timeout.test.ts` pins the handler's JSON message for `"30s"`; a union (`number | string | null`) put an `anyOf` next to `type: number` in `tools/list` (contradictory for a validating client) and a vaguer SDK message for `true`. The object around it is strict; the handler (`waitSeconds`) owns the value. The `advertised()` helper of #58 is gone.
- **`args` is `z.record(z.string(), z.unknown()).optional()`; `resumeRunId` is `z.string().optional()`; `overrides` is `z.record(z.string(), z.unknown()).meta(limitOverridesSchema()).optional()`.** `overrides` keeps its nested check in `parseLimitOverrides`, because `skills/run-workflow/SKILL.md` quotes the `unknown override: ` message and `config.process.test.ts` pins the `start_workflow.overrides ... concurrency` message; a nested strict zod object would replace both with the SDK's text. `tools/list` for `args` and `overrides` gains `propertyNames: { type: "string" }` (additive, valid JSON Schema).
- **New refusals beyond the three named cases, all because the advertised type says so:** `args` or `resumeRunId` as `null` (before: read as absent), `args` that is not an object (a string, an array), a `resumeRunId` that is not a string (before: silently ignored, so a fresh run started instead of the resume), `overrides` that is not an object. `timeoutSec: null` stays accepted because its documentation says so. Recorded in the CHANGELOG entry.
- **`list_workflows` got `inputSchema: z.strictObject({})`** so it also refuses an unlisted argument ("every tool"); a call with no `arguments` at all still works (probed: the SDK parses `args ?? {}`).
- **The args check goes right after the workflow lookup**, before the kit check, the config and `ensureDashboard`, the same place `startRun` (dashboard door) and the engine put it.
- **History:** commit `71073e6` is the red test commit (CODING_STANDARDS "Fix a defect test-first, with its own red commit"), `086712d` the change with its docs, `3ac7870` the review fixes. I split my own first commit with a soft reset before any review; nothing outside this branch moved.

## Learnings
- A fresh worktree has no `node_modules`: `mise exec -- npm ci --prefer-offline` before the first test (already an Applied Learning of the repo).
- A test that must prove "X is not called" over a request that returns at once reads its counter only after a later call's reply that waits for X itself; reading it right after the refused reply passes vacuously (the in-flight probe has not landed). Mutation-check such a test.
- zod 4: `z.union([...]).meta({ type, ... })` emits `anyOf` beside `type`; use `z.unknown().meta(schema)` when the handler owns the value. `z.record(z.string(), z.unknown())` adds `propertyNames` to `tools/list`.
- A coding-standards exemplar (`file` `symbol`) breaks when the symbol is deleted: `test/coding-standards.test.ts` reports it (here `advertised`).

## Notes for dependent tickets
- `start_workflow` in `mcp-server.ts` is the MCP door; the dashboard door is `startRun` (`packages/runtime/src/runtime/run-start.ts`); both call `argsError` (`runtime/args-schema.ts`). A ticket that adds an argument to a tool adds it inside `z.strictObject({ ... })`, or the repo test fails.
- `test/mcp-tools.process.test.ts` has `call(client, name, args)`, `freshRepo()` and `mcpServer(repo, env)`; the `TOOLS` table there lists each tool's properties and must change with a new argument.
- Over MCP the replies have two shapes (JSON `{ error }`, and the SDK's plain `MCP error -32602: ...`): a client parses after reading `isError`.
