## What was built
The MCP server (`packages/runtime/src/mcp-server.ts`) is now an `McpServer` with one `registerTool` call per tool (`list_workflows`, `start_workflow`, `wait_workflow`, `get_workflow_status`, `cancel_workflow`), each with a zod 4 input schema. The SDK checks a call's arguments before the handler runs and answers a failure with `isError: true`. `tools/list` returns the same five names, descriptions and advertised schemas. The accepted values did not change, with one exception: a missing or non-string `name` or `jobId` is now refused by the SDK. The step-guard server (`nested-mcp-guard.mjs`) moved to `McpServer` too, because it imported the deprecated `Server`. The SDK range is `^1.32.2`, the lockfile is updated.

## Decisions & deviations
- **zod schemas accept what the handlers took before; `tools/list` still shows today's schema.** The ticket says the zod schema "matches today's advertised schema" and that stricter validation is #59. Today's advertised schema is stricter than what the handlers accept (`timeoutSec` is advertised `number 1..50` but a numeric string, `null` and out-of-range numbers are accepted and documented; `overrides` null and numbers are checked by the config resolver with `start_workflow.overrides` messages that tests pin; `args` and `resumeRunId` are unchecked). A strict zod schema would have broken `wait-timeout.test.ts` and the documented clamp. So `args`, `resumeRunId`, `overrides` and `timeoutSec` use a small helper, `advertised(schema)`: `z.unknown().meta(schema).optional()` (zod 4 merges the meta keys into the JSON Schema; measured through the SDK). `name` is `z.string().meta({ enum: [...workflows.keys()] })` (enum listed, any string accepted, the handler keeps its `unknown workflow: X` message, which `skills/run-workflow/SKILL.md` quotes). `jobId` is a plain `z.string()`. #59 turns these strict and the helper goes away.
- **The one new refusal:** a missing or non-string `name` or `jobId` fails in the SDK (`MCP error -32602: Input validation error: Invalid arguments for tool X: ...`, plain text, `isError: true`, names the property). Before, `String(...)` turned them into `unknown workflow: 7` / `job not found` (still `isError`). This follows from the ticket's own gain (the SDK validates input) and overlaps part of #59's AC (`jobId: 7`); the header comment, CHANGELOG and book say so.
- **Error shapes recorded** in the header comment of `mcp-server.ts` (ticket requirement): handler failures stay `{ "error": "..." }`; what the SDK finds first is its plain, non-JSON text: schema failures and a call to an unregistered tool (`MCP error -32602: Tool X not found`; the old server answered `{ "error": "unknown tool: X" }`). A throw inside a handler is now an `isError` reply (it was a JSON-RPC error).
- **Nested mode.** `McpServer` with `capabilities: { tools: {} }` and no tool registered lists no tools (SDK 1.32.2 installs the handlers in the constructor). To keep the refusal text `workflows cannot be started from inside a workflow step`, the nested branch replaces the SDK's `tools/call` handler through `server.server.setRequestHandler(CallToolRequestSchema, ...)` (the `server` property McpServer documents for custom handlers; no import of the deprecated `Server`).
- **SDK floor `^1.32.2`, measured.** Validation into `isError` exists since 1.22.0 and zod 4 schemas since 1.23.0, but the nested/guard design needs tools/list to answer for a server with no tool registered. Measured with the guard script: SDK 1.23.0 failed the nested tests, and SDK 1.32.1 (isolated install in the scratchpad) answers `tools/list` with `Method not found`; only 1.32.2 installs the tool handlers from constructor capabilities. 1.32.2 is also the lockfile version (within the ticket's "at most 1.32.2"). A repo test pins the floor with `semver.minVersion`.
- **`tools/list` differences, all additive:** each tool with properties also carries `$schema` (draft-07), every tool an `execution: { taskSupport: "forbidden" }`, and the `tools` capability advertises `listChanged: true`. Names, required properties, descriptions and property schemas are equal (verified against the old file).
- **Standards and docs updated** (CODING_STANDARDS "a behaviour change updates every text that describes it"): `CODING_STANDARDS.md` MCP section rewrote the bullet that said "the MCP server uses the low-level Server ... zod never imported" (a documented standard the ticket reverses; the ticket and spec did not name it), the "A tool answers one JSON text" bullet, the exemplar of "Tool schemas and descriptions come from code", the "Translate errors only at process and transport boundaries" bullet and the enforced-by-tooling list; `CHANGELOG.md` (`### Mudado`); `docs/usage/03-invocacao-no-cursor-ide.md` (error shapes); `docs/usage/01-instalacao.md` (dependency table). No `CLAUDE.md`/`AGENTS.md` edit.
- Startup of the guard server did not regress (3 runs each, time to first `initialize` reply: old 178-213 ms, new 181-188 ms; a measurement, not a test bound).

## Learnings
- `npm install --no-save <pkg>@<old>` at the repo root puts the root copy at the old version but npm nests the range-satisfying copy under `packages/runtime/node_modules`, so a probe runs the wrong SDK: test an old SDK in an isolated scratch dir (`npm install` there, copy the script), then `npm ci` in the worktree.
- `mise exec -- npm pack` outside the repo uses Node 22.11 and crashes: use `mise exec node@22.23.4 -- npm pack`.
- A zod 4 schema can accept any value and still list a JSON Schema: `z.unknown().meta({ type, minimum, ... }).optional()`; the SDK's `tools/list` merges the meta keys.
- `McpServer` with `capabilities: { tools: {} }` lists no tools only from SDK 1.32.2; the SDK `Client.listTools` hides nothing (older versions answer `Method not found`).
