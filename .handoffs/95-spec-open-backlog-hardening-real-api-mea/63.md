## What was built
`wf doctor` now tells a user when the GitHub token behind `gh` holds scopes the kit does not need.
- New doctor status `warn`: a check that passed but names something to fix. It prints as `[warn]` with its `how to fix:` hint, `report.ok` stays `true`, the exit code stays 0, and the last line counts warnings (`All 9 checks passed, 1 with a warning.`). `--json` shows `"status": "warn"`.
- After `gh auth status` succeeds on a GitHub forge, the `forge` check runs `gh api [--hostname <host>] -i --silent user` and reads only the `X-OAuth-Scopes` header. A token listing any of `admin:public_key`, `write:public_key`, `admin:ssh_signing_key`, `write:ssh_signing_key`, `admin:gpg_key`, `write:gpg_key`, `admin:org`, `admin:repo_hook`, `delete_repo`, `workflow` gives a `warn` that names those scopes, with `gh auth refresh --remove-scopes <list> --hostname <host>` (or, for a token from `GH_TOKEN`/`GITHUB_TOKEN`, a fine-grained token in that variable).
- No header (a fine-grained token) passes; with `GH_TOKEN` set the message says a scoped token is in use. A `gh api` call that fails warns ("could not read the token's scopes") and never fails the doctor.
- The token is never asked for, printed or logged: the doctor calls neither `gh auth token` nor `--show-token`, and nothing of the response but the scopes header is read.
- SECURITY.md has the section "O token do GitHub" (what a leak exposes, how the doctor warns, the recommended fine-grained token).
- Verified end to end with the real gh against this machine's own token: `listed`, scopes `admin:public_key, gist, read:org, repo, workflow`, broad `admin:public_key, workflow`.

## Decisions & deviations
- **`checkGh` is now `checkForge`.** The ticket was written at `fece6b7`; since then ADR-0009 made the check a forge seam (GitHub and GitLab). The scope probe is `checkForgeToken` in `packages/runtime/src/doctor.ts`, and runs only for a forge whose `loginOf(...)` carries a `token` (GitHub). It stays inside the `forge` check (no tenth check id, so the id list, counts and docs keep their shape).
- **The CLI text lives in the forge module.** `packages/runtime/test/forge-seam.test.ts` forbids a literal `gh` outside `forge.ts` (ADR-0009), so `ForgeLogin.token` (new `ForgeToken`: `scopesArgs`, `envNames`, `printCommand`, `removeScopesCommand`) is built in `loginOf`. `github-token-scopes.ts` (new) holds the scope policy (`BROAD_SCOPES`), the header parser and the runner, and takes the arguments it is given. ADR-0009 got a dated `**Amended:**` line (a clarification that keeps the decision).
- **`--silent`:** the call is `gh api -i --silent user`, not `gh api -i user`. Checked on the real gh: headers still print, the body does not, so the account's profile (name, e-mail) never reaches the process or the recording.
- **Scope list adds `write:public_key`, `write:ssh_signing_key`, `write:gpg_key`** to the ticket's seven. GitHub's docs: `write:public_key` is "Create, list, and view details for public keys", which is all the threat needs, and the header lists only the scope granted, not the ones it implies (docs, fetched this run). A token with only a `write:` scope would otherwise pass.
- **Env tokens:** with `GH_TOKEN`/`GITHUB_TOKEN` (github.com, `*.ghe.com`, `github.localhost`) or `GH_ENTERPRISE_TOKEN`/`GITHUB_ENTERPRISE_TOKEN` (any other host; `gh help environment`, fetched this run) set and broad scopes listed, the hint is "replace it with a fine-grained token in <variable>": `gh auth refresh` cannot narrow a token from the environment. This goes beyond the ticket's single `GH_TOKEN` line.
- **A failed `gh api` is a `warn`**, not a failure or a pass: the login itself is fine, but the scopes could not be checked. The message shows the stderr lines (never the response headers).
- **Hint wording:** the hint appends a pinned link to the SECURITY.md section (`kitFileUrl`), like the other hints that point at the guide.
- **Unrequested but needed by the standard "a behaviour change updates every text that describes it":** the book (2.3 doctor chapter, 5.1 security table and checklist, 9.4 recorder row), the setup skill, INSTALL-AGENT.md, CHANGELOG, CODING_STANDARDS (Testing and Security pins), the CLI usage comment, and `scripts/verify/validation-report.ts` (the issue body said "All checks passed." with a warning present; it now counts warnings through the shared `withWarnings`).
- GitLab: the token is not read. The ticket and user story 6 name GitHub; I found no evidence of an equivalent exposure and filed nothing (SECURITY.md, the book row and the skill say it).
- No `CLAUDE.md` or `AGENTS.md` edited.

## Learnings
- `gh api --silent -i user` prints the response headers only (status line, then headers, a blank line, no body); the real output mixes `\n` after the status line with `\r\n` after the headers, and the header is spelled `X-Oauth-Scopes`: parse case-insensitively and split on `\r?\n`.
- `packages/runtime/test/forge-seam.test.ts` scans string literals of `doctor.ts`, `cli.ts` and the `implement-issue` helpers for `gh`/`glab`: put any CLI-named text (commands, hints) in `forge.ts` and pass it through `ForgeLogin`.
- `test/forge-docs.test.ts` fails a guidance block (book, skills) that names `gh` as the forge CLI without `glab` in the same block: say what the GitLab side does, or "the forge's CLI".
- A test that reads a job process's records right after another process's pid file races under load: poll with `waitFor`.
- `npm run check` takes several minutes: run it in the background with output to a file in the scratchpad, and read only the `# tests/pass/fail` and `not ok` lines.
- `gh help environment`: `GH_TOKEN`/`GITHUB_TOKEN` serve github.com, `*.ghe.com` and `github.localhost`; `GH_ENTERPRISE_TOKEN`/`GITHUB_ENTERPRISE_TOKEN` serve every other host.
- The gitleaks pre-commit hook flags a full 40-character SHA in a handoff as `generic-api-key`: write the 7-character SHA.
- This machine's gh token has `admin:public_key` and `workflow`: `wf doctor` in this repo now warns, which is correct.
