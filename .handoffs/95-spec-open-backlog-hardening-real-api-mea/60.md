## What was built
A MED or HIGH run started with `seams` and no `testCommand` no longer runs the command the planner (or the HIGH judge) wrote.
- It stores the plan, posts the command on the issue (inline code span, sanitized and redacted like the seams comment) and stops with the new status `test-command-proposed`, before any worktree exists.
- Its `next` line is `{...args, approveSeams: true}` without `seams`, so the existing `approveSeams` branch runs the stored plan with no planner call, and the command that runs is the one shown.
- Unchanged: an explicit `testCommand` runs as typed; the plan approved with `approveSeams` runs as shown; LOW keeps the kit's `npm test`.
- `test-command-proposed` counts as pending (`outcome.ts` `PENDING`), so the Board puts it in "Awaiting approval", not "Failed".
- Docs: header comment of `implement-issue.ts`, `skills/run-workflow/SKILL.md`, book chapters 5.1 (security table row, MED/HIGH paragraph), 5.3 (two pending lists) and 4.1 (`docs/authoring/01-escrevendo-workflows.md`: side-effects table, checkpoint recipe), CHANGELOG `### Mudado`.

## Decisions & deviations
- **Where the gate sits.** After the planner/judge, in the existing "propose and stop" block: `proposesSeams` (old rule) or `proposesCommand` (`seams` given, `testCommand === undefined`, planner proposed a non-blank command). One `stop` descriptor holds what differs (status, marker, heading, intro, relaunch args, approve text, chat text, result extras).
- **`seams` + `approveSeams: true` together** re-run the planner (as before) and now stop at the new gate; only `approveSeams` alone, with a stored plan, runs a stored plan. The ticket says the stored-plan path is the approval.
- **The comment** is a new comment with its own marker (`<!-- wf:implement-issue:test-command -->`), not the seams comment: a run that already posted its seams and is resumed with `seams` still posts the command (test pins it). Dedupe is per marker plus run id.
- **`test-command-proposed` result** carries `testCommand` (raw plan text; the engine's result redaction applies) so the chat skill can show it word for word.
- **No silent fallback to `npm test`** on the relaunch: it uses the stored plan. `npm test` only for LOW, for a blank proposal, and when nothing else is set.
- **Language.** New comments are English (CODING_STANDARDS "New comments are English"), in a file whose older comments are pt-BR; book, CHANGELOG stay pt-BR.
- **History.** The review fixes were folded into the fix commit (`1839e40`) after splitting a red test commit (`dc6cd34`) from it, to follow the "own red commit" rule. No separate `address review findings` commit exists.
- Not changed: `skills/*/references/*.md` list `seams-proposed` only as an example of a pending status, "or one added to `PENDING`" (two byte-identical copies; not false); `docs/authoring/02-convertendo-skills-e-subagents.md` describes the unchanged seams checkpoint.
- Limit: a command with invisible or bidi Unicode characters still shows as it looks; the comment shows what a code span can show.

## Learnings
- The fixture's `run()` helper injects `testCommand: "node --test"`; a test of the no-`testCommand` path passes `testCommand: undefined`, and a resume with the args of a `next` line must call `runWorkflow` directly (the helper would add the default back).
- `exec-start` events carry no arguments; the command line is in the `content` event with `kind: "tool-call"` and `tool: "exec"` (JSON `{command, args, cwd}`). A test that asserts "this command never ran" reads those.
- `python3` replace scripts must end a replaced block with its own newline: one swallowed it (`undefined);/**`) and `tsc` did not complain.
- The pre-commit gitleaks hook flags a full 40-character SHA after `Base:` in a handoff (`generic-api-key`): write the 7-character SHA.
- The repo's CODING_STANDARDS says new comments are English even in pt-BR files; `workflows/implement-issue.ts` has a pt-BR header, so new header lines are English.
