## What was built
- **GitLab is gated.** Before its first agent call, `implement-issue` on GitLab reads the issue's author id (`glab issue view N --output json`, `author.id`), then asks `glab api projects/<project>/members/all/<id>` (`projects/:fullpath/...` for the cwd, `projects/<encoded path>/...` plus the host for a `repo` argument). An `access_level` of Developer (30) or above runs as before. A 404 (`glab: 404 Not found (HTTP 404)`, GitLab's answer for an account that is no member) or a level below 30 (Minimal access, Guest, Planner, Reporter) stops the run with `status: "untrusted-author"` and no agent call, with the same `next` line that carries `allowExternalAuthor: true`. Any other failure of the lookup fails the run. With `allowExternalAuthor: true` no lookup happens.
- **The result says it in GitLab's words.** `authorAssociation` is `Developer (30)`, `Reporter (20)`, `not a member`...; the `reason` names who the forge trusts (`Forge.trusts`: GitHub "the repository's owner, a member of its organization or a collaborator", GitLab "a member of the project with Developer access or above").
- **The route is recorded from a real GitLab CE** (`scripts/verify/record-glab-fixtures.ts`, run through `scripts/verify/gitlab-e2e.sh`, image gitlab/gitlab-ce:19.5.5-ce.0, glab 1.130.0): the recorder seeds a Developer, a Reporter and a stranger (a Reporter who opened an issue and was then removed from the project), each with an issue made as them, and records `author-owner` (root, 50, inherited from the group), `author-developer` (30), `author-reporter` (20), `author-stranger` (exit 1, 404) and `author-owner-repo` (named project, `GITLAB_HOST` form). The fake `glab` plays them.
- Docs: governance row (5.1), CHANGELOG, ADR-0009 (a new dated amendment, 2026-11-15), `skills/run-workflow/SKILL.md`, the maintainer-scripts chapter row, the header of `implement-issue.ts`. The Enterprise gap is cited as #103 everywhere.

## Decisions & deviations
- **Re-read of the issue instead of state.** `GitlabForge.authorStanding` runs `glab issue view --output json` again to get `author.id` (the `issue-view` recording already covers that command line) instead of keeping the id from `issue()`; `Forge` holds no state between calls and `ForgeIssue` stays forge-neutral. Cost: one more local read per GitLab run. A reviewer suggested carrying the id on `ForgeIssue`; dismissed for the reason above.
- **Trust rule.** Developer (30) and above is trusted (Agent Brief). Unknown levels fail closed: `access_level >= 30`, so a level GitLab adds between 20 and 30 is a stranger. The member's `state` (the user's account state, `active` in every recording) is not read: the brief's rule is the access level alone, and no evidence says a blocked account should change it.
- **404 pattern.** `/\b404 Not found\b/i` over the stderr tail (stdout goes to a file), exit code 1: the text of the recorded answer. `404 Project Not Found` and any other status fail the run. The first version matched any `404`; the Spec review pointed at the over-reach.
- **`Forge.trusts`** (a readonly member beside `name`) carries who the forge's rule trusts, so `reason` is right on both forges; `AuthorStanding` stays `{ association, trusted }`. `Forge.authorStanding` no longer returns `undefined`, so the "could not check the author" log branch is gone, together with its test.
- **Recorded levels.** The fake plays `author-owner`, `author-developer` or `author-reporter` by the level the test sets (50, 30, 20); any other level plays the developer's recording with `access_level` set (the field the test controls). The named-project form plays `author-owner-repo` the same way. A stranger plays `author-stranger` (exit code, stderr and stdout as recorded).
- **Existing tests changed.** `implement-issue.forges.test.ts` "the issue is read with `glab issue view --output json`, and its notes through the REST API ..." looked for "the first `api` call" and now finds the members lookup; it looks for the notes route. `test/typescript-strictness.test.ts`: the allowlist entry of the recorder's `JSON.parse` follows `calls.at(-1)!`. Four GitHub-only gate tests became `["github", "gitlab"]` tests ("the untrusted-author result says why...", "allowExternalAuthor lifts the gate...", "the relaunch of a stopped run...", "a failed lookup ..."); `failForge("api --hostname", ...)` became `failForge("author", ...)` (both fakes name the lookup `author`).
- **ADR-0009.** The 2026-11-14 amendment keeps its history (it says GitLab answered nothing "at that point") and a new `**Amended:** 2026-11-15` line records the GitLab gate, as CODING_STANDARDS asks (an ADR is not rewritten in place).
- **The recorder rewrote the whole `recordings.json`** (new timestamps, ids), as in earlier tickets that re-recorded; its new users are `wf-developer`, `wf-reporter`, `wf-stranger` with `example.com` addresses, and no token or password reaches an output (`refuseLeaks`, and the new entries read by hand).

## Learnings
- GitLab gives a new project member access in the background: an API call as them gets `404 Project Not Found` for a few seconds. Poll with `until(...)` before acting as a freshly added member.
- `GitLabApi.call` reads JSON: a DELETE answers 204 with no body, use `api.remove`.
- `scripts/verify/gitlab-e2e.sh` with `GITLAB_E2E_NAME=<ticket> GITLAB_E2E_PORT=<free port> GITLAB_E2E_STAGES=references` takes about 5 minutes and rewrites the whole `recordings.json`; run it in the background with logs in a ticket-private scratchpad directory.
- `test/typescript-strictness.test.ts` allowlists a trusted `JSON.parse` cast by its exact call text: changing the expression in the recorder needs the allowlist line changed too.
- `npm run check` runs the root suite only if the workspace suites pass: a first failure in the runtime suite hides the root failures behind it, so rerun the whole check after each fix.
- `Commands.read` sends stdout to a file: the tail of a failed forge call holds the stderr only, so match a CLI's error text on what it prints to stderr.
