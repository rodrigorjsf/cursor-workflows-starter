## What was built
A capped real-API probe of the SDK sandbox, and the default it decided.
- New workflow `scripts/verify/verify-sandbox.ts`: one local write step in the SDK sandbox (all tools, engine default `settingSources`, `composer-2.5`) with a `.cursor/sandbox.json` of `readBoundary: "workspace"` and a network allowlist of one host. It reports PASS (blocked) or FAIL (got through) for `curl` to a host outside the allowlist, a write outside the repository, and `cat ~/.cursor/sdk/auth.json`, with controls, so a blocked verdict needs proof the attempt ran and that the machine could have done it without the sandbox. `{"readBoundary":"unset"}` runs a baseline.
- Measured 2026-11-14 (Linux x64 WSL2, SDK 1.3.1): all three attempts blocked in every run with `readBoundary: "workspace"`; without it the key read goes through; the edit tool did not create a file outside the repo; Landlock (not bubblewrap) enforced the rules on this kernel.
- Gate opened, so `templates/global-config.json` sets `caps.requireSandbox: true` (schema example, installer guide, setup skill updated), `wf doctor` has a ninth check `sandbox`, and SECURITY.md, the book, the skills and the CHANGELOG say the measured result instead of "not tested".
- Report posted on the issue: https://github.com/rodrigorjsf/cursor-workflows-starter/issues/62#issuecomment-6880829894

## Decisions & deviations
- **Gate opened, but `requireSandbox` alone does not protect the key.** Baseline run 3 (no `readBoundary`): `cat auth.json` exit 0. The sandbox blocks network and out-of-repo writes by itself, which cuts "read the key and send it away", but not the read. The kit does NOT write a `sandbox.json` (`wf init` writing one into every repo, or the installer touching `~/.cursor/sandbox.json`, changes the user's other Cursor surfaces and is the owner's call). Instead SECURITY.md and the book say it, and `wf doctor` reports whether `readBoundary` is `workspace` (status stays `pass`: a fresh install must not fail the doctor).
- **Landlock, not bubblewrap, enforced the rules here.** Run 4 and 6: `CURSOR_SANDBOX_LANDLOCK_STATUS=fully_enforced`; run 5 (only a `bwrap` that exits 1 on PATH, the real one off PATH) was fully blocked. The helper `cursorsandbox` has both backends. The ticket's rules stay as written: the probe stops when `bwrap` is not on PATH, and the doctor fails when `requireSandbox` is true and `bwrap` is missing. I kept them because the doctor cannot test Landlock (`cursorsandbox --preflight-only` needs a `--policy` file of undocumented format), and the failure message says a kernel with Landlock 6.2+ may run without it. A user on such a kernel is asked to install bubblewrap or to set `requireSandbox` to false. Revisit if that friction shows up.
- **Disposable repo:** a local `git init` repo with a `package.json`, not `setup-sandbox-repo.sh`. The probe uses no remote, and the gh token here has no `delete_repo` scope (`gh auth status`: admin:public_key, gist, read:org, repo, workflow), so a GitHub repo could not be deleted afterwards. The README says any disposable repo works and mentions the script.
- **The user-level `~/.cursor/sandbox.json` was not measured** (reviewer finding). Docs and the doctor say so; the recommendation is the repository's `.cursor/sandbox.json`, the measured file. The doctor reads repo then home (`??`), matching Cursor's documented precedence; the home-only case reports "not measured".
- **Extras, not in the gate:** `readBoundary: "unset"` baseline, the allowlisted-host control, the edit-tool write (with a control edit inside the repo), the `CURSOR_SANDBOX_*` backend variables. Each is reported separately; only the three attempts decide `allBlocked`.
- **Verdict rules:** "blocked" needs the attempt's marker in a tool call, the control (outside-the-sandbox curl, readable key, writable home, in-repo write) and, for network, write and read, the command's own `exit=` line. A call refused before it ran, or an agent that skipped a step, is INCONCLUSIVE.
- **Run history:** run 1 discarded (verifier looked up content lines by step label; they carry `attemptId`; no verdict; its raw log showed the same outcomes). Runs 2 to 5 ran earlier revisions (same three attempts; no `exit` check on the write, no home or edit controls). Run 6 ran the final script. Disclosed in section 16 and in the issue comment.
- **`findOnPath` extracted** to `packages/runtime/src/find-on-path.ts` (doctor and the probe); the old private copy in `doctor.ts` lacked the `isFile` check, so a directory named like a command now no longer counts there.
- **Doctor check id:** `sandbox`, appended last, so the order of the eight existing ids is unchanged (setup skill, install guide, book 2.3 table, README.en and five test counts updated).
- **Existing installs unchanged:** the installer writes the global config only when none exists. A step that downloads packages needs its hosts in `.cursor/sandbox.json`; stated in SECURITY.md, 2.2, 5.1 and the CHANGELOG.
- No `CLAUDE.md` or `AGENTS.md` edited.

## Learnings
- Content events in `events.jsonl` carry `attemptId`, not the step label: find the attempt through the `step-start` event, then filter. Events of `ctx.exec` commands have attempts of their own.
- The SDK sandbox helper `node_modules/@cursor/sdk-linux-x64/bin/cursorsandbox` has Landlock and bubblewrap backends; inside a sandboxed step `CURSOR_SANDBOX_LANDLOCK_STATUS` says which enforced. `--preflight-only` needs `--policy <file>` (format undocumented).
- `~/.cursor/sdk/auth.json` is readable inside the sandbox unless a `sandbox.json` sets `readBoundary: "workspace"`; the repo's `.cursor/sandbox.json` is honoured by local SDK runs with the default `settingSources`.
- The gh token here has no `delete_repo` scope: `gh repo delete` would fail. The cloud tickets (#47, #45) that create a throwaway repo must check this first.
- `wf stats` on a throwaway `WF_METRICS_DB` prints the list-price cents of a set of real runs.
- A failing `assert.match` on a long document prints all of it: pipe test output through `cut -c1-200`.
- `npm run check` skips the root tests when a workspace test fails (`&&`): after fixing, rerun `npx tsx --test test/*.test.ts`.
