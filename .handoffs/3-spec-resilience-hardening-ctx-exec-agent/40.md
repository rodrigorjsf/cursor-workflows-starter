## What was built
- The test "the run's token cap works through the backend: the turn that crosses it aborts every active attempt" no longer depends on `setImmediate` timing between its two parallel attempts.
- A new test helper `turnsInOrder(order, tokens, seen)` makes each attempt emit its turns in an order the test sets, each turn waiting on the previous turn's promise. The test uses `["a", "b", "a"]`: attempt `a` emits, then `b`, then `a` emits the crossing turn (300 of 250). Both agents exist (each emitted an event) before the crossing, so the cut applies to both at once and the run total is exactly 300.
- Test-only change (`packages/runtime/test/backend.test.ts`). No engine, doc or CHANGELOG change: the engine was not at fault, and a test-only fix is not user-facing.

## Decisions & deviations
- **Order `a b a`, one test.** The ticket allows `a b a` or `b a b`. The engine treats the two attempts symmetrically, so one order is enough; a second would only repeat the assertions.
- **Two failure shapes, one cause.** The ticket describes `400 !== 300`. Under load the old test also failed with `assert.ok(reason instanceof BudgetExceededError)`: attempt `a` never started (`turns 0`, no reason) because `b` alone crossed the cap before the engine began `a`, and the engine does not start a step after the run's cap is crossed (the deliberate rule). Measured on the old test: 18 of 200 failures, a mix of both shapes. The lockstep order removes both, since `b` cannot emit until `a` has emitted, so `a` is running before any crossing.
- **No engine change.** Confirmed from the ticket's investigation and my reproduction: both shapes follow from the engine's deliberate rules (held-back cut until the agent exists; no step starts after a run breach).
- **A hang rather than a failure if the engine stops running `b` while `a` is active** (for example a concurrency of 1): the attempts wait on each other, and the step timeout (20 min) would eventually end them. The old test had the same dependency (`bHanded`). Not worth guarding in a test helper.
- **Test files are not covered by `npm run typecheck`** (see Learnings), so the new helper was checked by running the test and by `tsc -p packages/runtime/tsconfig.test.json`: no error reported in my lines. That config reports 72 errors that exist without my change (the fake SDK mapped as `@cursor/sdk`, and `Promise.withResolvers` missing from the lib), including at the older `withResolvers` call sites in this file.

## Learnings
- Under RTK, `gh issue view <n> --comments` prints nothing; use `gh issue view <n> --json title,body,comments`.
- A fresh worktree has no `node_modules`: `cp -a <main>/node_modules <worktree>/node_modules` works and keeps `git status` clean.
- Default node is 22.11, below the repo's `>=22.13`: run everything with `mise exec node@22.23.4 --`.
- Run one test file with `mise exec node@22.23.4 -- npx tsx --tsconfig tsconfig.test.json --test --test-name-pattern "<name>" test/<file>` from `packages/runtime` (about 1 s).
- A stress script that writes a failing run's output must write it outside the worktree; it ran from `packages/runtime` and left untracked `fail-*.out` there (removed).
- `npm run typecheck` does not cover test files, and `packages/runtime/tsconfig.test.json` reports 72 errors on its own (fake SDK as `@cursor/sdk`, `Promise.withResolvers` lib): it is a `tsx` config, not a type gate.

## Notes for dependent tickets
- `turnsInOrder(order, tokens, seen)`, `whenAborted(signal)` and the `Seen` type are local to `packages/runtime/test/backend.test.ts`, next to `stubBackend`, `streamsUntilAborted` and `Behaviour` (not shared). Lift them to a fixture file if another suite needs ordered parallel attempts.
- Rule for any new test that runs several stub attempts under a run or step cap: do not order their turns with `setImmediate`; hand the order to the test through promises, and let each attempt emit at least one event before the crossing turn.
- The engine rules these tests rely on are unchanged: a token cap's abort waits for the attempt's first event, and no step starts after the run's cap is crossed.
