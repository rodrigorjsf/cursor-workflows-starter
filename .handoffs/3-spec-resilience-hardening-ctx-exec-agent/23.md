## What was built
- The engine no longer talks to the Cursor SDK. Every attempt of a step goes through `AgentBackend.run(prompt, options, signal, onEvent)` in `packages/runtime/src/runtime/backend.ts`; it settles with an `AttemptResult` (how the attempt ended, agent id, resolved model, usage reading).
- The local execution (create the agent, send with `AgentBusyError` tolerance, wait, structured result through `submit_result` with re-prompts, delta translation, usage read with retries, dispose) is now `localBackend`, behaviour unchanged.
- Live token caps (per step and per run), the step timeout and run cancellation reach the backend as the abort of the attempt's signal, with the cause in `signal.reason`. The backend cancels the run in flight, waits for it to stop, reads the usage, disposes the agent and reports `{ kind: "aborted", reason }`.
- `RunOptions.backend` swaps the backend (default `localBackend`); new tests use it to run the engine against a stub backend with the SDK untouched.
- Docs: new section "O `AgentBackend`: quem roda a tentativa" in `docs/internals/01-arquitetura.md` (diagram and step-cycle intro updated), `docs/contributing/01-contribuindo.md` file tree, `CHANGELOG.md`.

## Decisions & deviations
- **Interface shape.** `run(prompt, options: StepOptions, signal, onEvent): Promise<AttemptResult>`. The callback carries more than turn events (`agent`, `text`, `step`, `tool-call`, `tool-output`, `summary`, `reprompt`, `turn`) because counting steps/tool calls and writing the content log are engine concerns fed by the backend. The result is a report for every way an attempt can end (`finished`, `run-error`, `schema`, `aborted`, `error` classified `account | usage-limit | rate-limit | other`); it rejects only on a backend bug, which the engine turns into a failed, uncharged attempt.
- **What stayed in the engine:** policy and orchestration (nested-workflow MCP guard, `requireSandbox` cap, retries and rate-limit backoff, error-kind mapping, spend/ledger accounting, journal, memo, live-cap arithmetic, timeout timer, revert on cancel). **What moved to the backend:** `Agent.create` options, the `submit_result` structured-output mechanism and re-prompts (ADR-0005 says a cloud backend does this differently), SDK delta translation, `shellOutput`, `sendWhenFree`, usage reading, disposal.
- **One abort signal per attempt, cause in `signal.reason`.** The engine aborts it for run cancellation (`RunCancelledError`), timeout (`StepTimeoutError`, a timer armed per attempt) and token caps; `AttemptAbort` replaces `AttemptCut`.
- **A token cap never abandons a creation; cancel and timeout do.** An existing test (`live-caps.test.ts`, "a step the run's cap cuts while its agent is still being created never sends...") pins the old behaviour (the cut step's agent is created, stopped, its usage read and charged as 0). To keep it unmodified, the engine holds a cap's abort until the backend emits `agent` (any later event also counts) and applies it then. Contract documented in `backend.ts` and the book chapter. A backend that never emits `agent` still has caps applied from its first event.
- **Added `RunOptions.backend`** (not in the ticket). Needed to test the interface without the SDK; ADR-0005 and the old `backend.ts` header already say spec #3 makes the seam an extension point.
- **After an abort, any other SDK error is a consequence of it:** the backend reports `aborted` with the signal's reason whenever `signal.aborted` at the catch (old code matched the reason by identity). Safer against SDK errors raised by the cancellation itself.
- **`send()` grace (found in review, see below).** An abort waits up to `SEND_GRACE_MS` (1000 ms) for an in-flight `send()` to hand back its run so the run is cancelled and awaited. Creation gets no grace (cancel must be immediate). Cost: a timeout or cancel that lands on a hung `send()` ends the attempt up to 1 s later than before.
- The warning text `getUsage() failed (...)` stays in the engine unchanged: docs/usage/02-configuracao-inicial.md documents it.

## Learnings
- A fresh worktree has no `node_modules` (gitignored): `cp -a <main>/node_modules <worktree>/node_modules` works (relative workspace symlinks stay valid) and keeps `git status` clean.
- Default node is 22.11, below the repo's `>=22.13`: run everything with `mise exec node@22.23.4 --`.
- Under RTK, `gh issue view <n> --comments` printed nothing; `gh issue view <n> --json title,body,comments` works.
- `tsc` with `types: ["node"]` but default DOM lib: `setTimeout(resolve, ms)` where `resolve` takes an argument picks the DOM overload (returns `number`); write `setTimeout(() => resolve(undefined), ms)`.
- Test files are not covered by `npm run typecheck` (root tsconfig includes `src`, `workflows`, `scripts` only); tests run through tsx.

## Notes for dependent tickets
- Public surface in `packages/runtime/src/runtime/backend.ts`: `AgentBackend`, `StepOptions`, `AttemptEvent`, `AttemptResult`, `AttemptOutcome`, `UsageReading`, `AttemptErrorReason`, `StepLocation`, `localBackend`. Engine: `RunOptions.backend`.
- A new backend must: honour `signal` (cancel the run, wait for it, read usage, dispose, report `aborted` with `signal.reason`), emit `agent` as soon as the agent exists and check `signal.aborted` right after, emit `turn` events (the live caps run on them), report `reprompt` events if it re-prompts, and settle with an `AttemptResult` instead of throwing. It owns the structured-output mechanism. Contract text: top of `backend.ts` and the book section "O `AgentBackend`".
- Cloud spec (#5): the engine picks the backend once per step (`opts.backend ?? localBackend`, in `runStep`); per-role selection by location goes there. The `agent` event is not logged by the engine yet (the id reaches the log in `step-end`); ADR-0005 wants it stored as soon as it exists for reattach.
- Stub backend helper for tests: `stubBackend` and `Behaviour` live inside `packages/runtime/test/backend.test.ts` (not shared); lift them to a fixture file if another suite needs them.
- `ctx.exec` / CommandRunner tickets: not touched. The engine's `process.env[INSIDE_WORKFLOW_ENV]` and the sync `repoIdentity` git call are unchanged.
