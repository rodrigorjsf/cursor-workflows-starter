## What was built
- Every command `implement-issue` runs (the TDD loop's test runs, `git`, `gh`) goes through `ctx.exec`. Nothing in the workflow files calls `execFileSync`/`execSync`/`spawnSync` any more, so status queries and cancel stay responsive during a suite, and cancelling kills the suite at once.
- The suites of the TDD loop are command nodes in the event log, labelled `suite:baseline`, `suite:red:<n>`, `suite:green:<n>`, `suite:fix:<n>:<round>`, `suite:refactor`, `suite:final` (and `setup`), each with its own output.
- `git push` and every `gh` call have a timeout (new workflow arg `networkTimeoutSec`, default 120 s); local `git` has a fixed 5 minute limit; the suites keep `testTimeoutSec`. A hung push fails the step with `git push … timed out after Ns`; the run is resumable and the resume delivers.
- A `gh` failure in the existing-PR lookup fails the run with gh's own message. Only exit code 1 with "no pull requests found" means "no PR".
- A suite killed by a signal (OOM killer, say) is no longer a valid red: `tests-killed` (absorbed, see below). `overflow` is gone: output no longer goes through a buffer.
- New module `packages/runtime/workflows/implement-issue/commands.ts` (`Commands`, `CommandError`); `tdd.ts` git helpers and `runTests` are async and take a `Commands`.

## Decisions & deviations
- **`git`/`gh` answers are read from a file, not from `ExecResult.tail`.** `tail` is the last 32768 characters of stdout and stderr mixed. A diff, a file list or an issue with comments is longer (the secret scan would have missed a key at the top of a long diff), and a warning on stderr would corrupt a parsed value. `Commands.read` runs `bash -c 'exec "$@" >"$WF_STDOUT"' read <cmd> <args…>` with the file path in `env` and returns the whole stdout (64 MiB limit, as `maxBuffer` was). Consequences: for these reads the node's `command` is `bash` (the `label` says `git diff`, `gh pr view`, …) and the stdout is not in the event log (stderr, the exit and the command line are). Calls that only have to succeed (`git add`, `commit`, `push`, `worktree add`, `read-tree`…) run directly and their output is logged. Documented in the CHANGELOG. Spec text says "its output streamed into the run's event log"; I kept data the code parses (diffs, issue JSON) out of the log on purpose. If the dashboard spec wants it, `read` can `tee`.
- **New arg `networkTimeoutSec`** (default 120) instead of a hard-coded value: the hung-push test needs a short limit, and a slow link needs a knob. The local git limit is a constant (`LOCAL_GIT_TIMEOUT_MS`, 5 min, hooks included). #26 (config limits) can move both into the config if it wants; `execTimeoutMs` (default 10 min) was not reused because #22 left short git/gh limits to this ticket.
- **Error model.** `Commands` throws `CommandError` (command line, exit/timeout/spawn reason, last 1000 chars of output) when a command that had to succeed does not; `gitIs` turns exit 0/1 into a boolean (`diff --quiet`, `rev-parse --verify --quiet`) and throws for anything else; `ghOrNothing` is the PR lookup. `runnerConfigChanged` still reads "no package.json" from a git that exited with an error, but a timeout, a spawn failure or a cancel now propagate.
- **Suite output.** `runTests` returns the last 4000 chars of the merged stdout+stderr tail (before: stdout on success, stdout then stderr on failure). Kinds: `passed | failed | timeout | killed`.
- **Write-step undo on cancel.** In `writeStep`, if the agent step throws and the undo cannot run (a cancelled run's `ctx.exec` throws at once), the original error is thrown and `inFlight` stays, so the resume undoes the step. The engine reverts the step's cwd on cancel anyway (test: "cancelling in the middle of a write step…"). A cancel in the middle of a suite that follows a write step also leaves `inFlight` set, so the resume redoes that write step (before, the cancel waited for the suite).
- `MIGRATION_PENDING` was deleted whole (nothing is pending), not left empty.
- `runTests` is no longer exported from the workflow module; `findStagedSecret` still is, now `async (cmd, worktree, knownSecrets?, base?)`.
- Docs touched: CHANGELOG ("Mudado"), architecture chapter (cancel row, heartbeat row), authoring book chapter and the recipes reference (both skill copies, identical), `heartbeat-worker.mjs` comment, header comment of the workflow.
- A LOW run now has about 45 command nodes (`git ls-files`×5, `git add`×8, `git write-tree`×5, `git diff`×7, `git show`×4, …); `wf status` progress lines show them.

## Learnings
- The worktree has no `node_modules`: `mise exec node@22.23.4 -- npm ci`, then prefix every command with `mise exec node@22.23.4 --`.
- `gh issue view N --comments` prints nothing through the RTK rewrite; `gh issue view N --json title,body,comments` (or `/usr/bin/env gh …`) works. Same as #22's learning; the global RTK deny-list edit was not done (outside the worktree; hard rule).
- `ctx.exec` returns only the last 32768 characters of stdout and stderr mixed. A workflow that parses a command's output needs the stdout whole: see `Commands.read`. A platform-level `stdout` in `ExecResult` (opt-in, capped) would remove this workaround; not done here to keep `engine.ts`/`command-runner.ts` untouched while other tickets of the spec edit around them.
- Stress probes: start busy loops with `timeout`, then kill by PID from `ps -eo pid,comm,args | awk` — `pkill -f` can match the calling shell.
- `pre-push` hooks in the main repo's `.git/hooks` also run for pushes from a linked worktree: a handy way to simulate a hung push.
- In the fixture, the first `exec-start` of a run is now `gh issue view`: tests that look for "the first command" must pick by `label`.
