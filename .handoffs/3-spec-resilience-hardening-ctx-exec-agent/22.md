## What was built
- `ctx.exec(command, args?, { label, phase, timeoutMs, cwd, env })` runs a command as an asynchronous child process (no shell, no stdin, no controlling terminal) and returns `{ ok, exitCode, timedOut, tail, error? }`. A non-zero exit, a timeout and a program that cannot start are results; a cancelled run kills the command and throws `RunCancelledError`.
- The command is killed at its timeout (SIGTERM to its whole process group, SIGKILL 2 s later). The default timeout is the new workflow preference `workflows.<name>.execTimeoutMs` (config files; 600000 ms when unset), recorded in the `run-start` config with its provenance. A call's own `timeoutMs` wins.
- Output streams into the event log while the command runs: `content` events of kind `command-output` (`tool: "exec"`, `stream: stdout|stderr`, `callId` = the call's `attemptId`), plus a `tool-call` content event with the command line. Same redaction, 32768-char event cut and retention as agent content; the log keeps at most 262144 chars per command (`outputTruncated` on `exec-end`).
- Each call is a step node: new events `exec-start` / `exec-end` carry `stepId` (`x-…`), `parentId`, `groupId`; the next step or command continues from it, also inside `parallel`/`pipeline`. `wf status` progress lines show `▶ label [command]` and `✓/✗ label (exit 0, 1.2s)`.
- Status queries and cancel stay responsive: nothing blocks the job's event loop. Cancel and a second SIGTERM kill the command and what it started; nothing outlives the call.
- A repo-level lint in `npm test` fails on `execFileSync`/`execSync`/`spawnSync` in workflow files. The authoring skill (and its shared copy in skill-to-workflow), the pt-BR book chapters, the generated events and config references and the CHANGELOG document `ctx.exec`.

## Decisions & deviations
- **Separate event types, not `step-start`/`step-end`.** `exec-start`/`exec-end` carry `StepRef`, so views get a node, and the metrics recorder (`attempts` table, one row per agent attempt with cost and tokens) stays untouched. Output reuses `content` (`command-output`, `tool-call`) so redaction, cut and retention come for free; `ContentEvent` gained the optional `stream` field and `ExecEndEvent` the optional `outputTruncated`. Additive: `EVENT_SCHEMA_VERSION` stays 1.
- **Result, not exception**, for non-zero exit, timeout and spawn failure (the workflow decides); cancel throws like an agent step does. `tail` is the real output (not redacted); only the log's copy is. The tail is the last 32768 chars, stdout and stderr in arrival order across the two pipes (the relative order between pipes is not guaranteed).
- **One config default, `execTimeoutMs`, a workflow preference** (`workflowPrefs`), outside the `LIMITS` table (no global cap, no env var, no flag, no MCP override). It is a new top-level field of `EffectiveConfig` (`config.execTimeoutMs`), so `config.limits` and its existing tests are untouched. Default 10 min, the value `implement-issue`'s test runner already used. Short timeouts for `git`/`gh` network calls are meant to be passed explicitly per call by #24 (its AC "a hung git push fails at its timeout"); spec story 4's "default timeouts for git and gh" is delivered there, not by a second default here.
- **Credential prompts** need no extra env (`GIT_TERMINAL_PROMPT`): the child runs in its own session (`detached`) with stdin `/dev/null`, so there is no terminal to prompt on. Verified: `git ls-remote https://github.com/<no such repo>` failed in 462 ms with "could not read Username … No such device or address"; pinned offline by the test "a command has no stdin and no terminal…".
- **Process groups.** Each command is its own group (not on Windows, where `child.kill` is used and tree kill is untested). A `process.on("exit")` hook SIGKILLs commands still running, so a second SIGTERM leaves nothing behind. If the leader exits while a leftover process holds the pipes, after 1 s the group is killed and the call ends.
- **Output log shape.** Whole lines flushed every 250 ms (a partial line waits; a private key block waits for its END line; a batch over 32768 chars is cut at a line break), so redaction, which sees one event at a time, cannot be defeated by a read boundary. Cap of 262144 chars per command in the log.
- **Node ids** `x-<hash12>.<n>`: hash of the branch path (`flow.prefix`), command, args and cwd; `n` counts repeats per execution, so a resume numbers them alike and parallel branches cannot swap ids. `exec` is not journaled: a resume runs the commands again.
- **Lint with a temporary allowlist** (`MIGRATION_PENDING` in `test/workflow-lint.test.ts`): `implement-issue.ts` and `implement-issue/tdd.ts` still call `execFileSync` until #24. The test fails when an allowlisted file stops calling it, so #24 must delete the two entries.
- `env` accepts `undefined` to remove a variable (absorbed after review: `tdd.ts` `runTests` deletes `NODE_TEST_CONTEXT`, which #24 needs to reproduce through `ctx.exec`).
- Docs: the architecture chapter (3.1) got a section "Comandos do workflow (`ctx.exec`)"; its sentence about synchronous calls delaying cancel is kept for the calls `implement-issue` still makes (#24 should update it).

## Code review
Two `ticket-reviewer` subagents (Standards, Spec), fixed point BASE_SHA.
Fixed:
- Spec 1: a private key block split across flushes leaked its body (only the first piece was redacted) — now held until its END line.
- Spec 2: a batch longer than 32768 chars was cut at a fixed offset, possibly inside a token — now cut at the last line break that fits.
- Spec 3: exec numbering depended on parallel branch completion order — now keyed by branch path.
- Standards 1: a process left holding the pipes escaped cancel and the exit hook — the group is killed when the call stops waiting for the pipes.
- Standards 2: "256 KiB" in the book was in bytes, the limit is 262144 characters — fixed.
- Standards 3: `"stdout" | "stderr"` spelled three times — one `OutputStream` type in `events.ts`.
- Standards 4: the in-flight tracking wrapper was duplicated in `agentCall` and `execCall` — extracted to `inNode`.
- Standards 5: `config/resolve.ts` imported a value from `command-runner.ts` (pulling `node:child_process` into config) — the default constant now lives in `resolve.ts`.
Dismissed:
- Spec 4 (a timeout firing in the instant the command exits reports `timedOut`): the command had used its whole allowance, a command that exits on SIGTERM gets the same outcome, and a zombie still accepts the signal, so no discriminator exists.
- Spec 5 (no git/gh-specific default): see Decisions; prompts fail fast, short network timeouts are #24's per-call values.
- Spec 6 (scope: `cwd`/`env`/`phase`, exit hook, progress lines): reviewer judged them justified by the ticket's intent.
- Spec 7 (`ctx.exec` does not check the run's cap): a command spends no tokens or cents, and a crossed cap still ends the run at its next step or at the end.
- Standards 6 (a `WORKFLOW_PREFS` row table like `LIMITS`): one preference does not make a table; #26 adds six workflow preferences and owns that shape.
- Standards 7 (doc literals repeat constants): each literal (262144, 32768, 2 s, 600000) is pinned by a behaviour test, so a change fails a test and prompts the doc edit; a test comparing a constant with itself would be tautological.

## Learnings
- Default Node here is 22.11 (below the 22.13 floor) and the worktree has no `node_modules`: `mise exec node@22.23.4 -- npm ci`, then prefix commands with `mise exec node@22.23.4 --`.
- Red tests that start real long commands hang the run when the feature is missing: run them as `timeout 150 … --test --test-timeout=60000`, and clean strays with `pgrep -x sleep`. `pkill -f '<pattern>'` also matches the calling shell and kills it (exit 144): use `pkill -x`.
- `gh issue view N --comments` printed nothing through the RTK rewrite in this session; `/usr/bin/env gh issue view N --json title,body,comments` worked. The global RTK deny-list edit that rule would trigger was not done (outside the worktree; hard rule).
- A test that returns the `ctx.exec` result from the workflow puts the raw `tail` into `run-end.result`, which is only redacted by shape: return a flag instead when the output holds secrets.
- Output of two pipes arrives in no fixed order: tests that depend on the interleaving of stdout and stderr need a pause between the writes.
