## What was built
- Every `implement-issue` run owns its branch (`wf/issue-<n>-<run>`) and its worktree (`.workflows/worktrees/wf-issue-<n>-<run>`), recorded in the run's `tdd-progress.json`. A fresh run starts from the current local head of the default branch and never reuses another run's worktree.
- One active run per issue: a second run gets `status: "issue-locked"` with the `activeRunId` of the first (reason and lock detail included), and creates no branch, worktree or agent. The lock is released when the run ends, however it ends.
- Delivery after a resume works when the PR already exists: the resume rewrites the commit and pushes with `--force-with-lease=<branch>:<commit the origin has>`, only on `wf/` branches.
- The push is refused (`status: "push-refused"`) when the origin's branch holds a commit the run did not push (a reviewer's fix, say). Nothing is overwritten; the work stays in the worktree.
- A run begun before this change resumes on its old fixed branch and worktree.

## Decisions & deviations
1. **One branch and one worktree per run, named after the run id** (the ticket and spec do not name the branch). A fixed `wf/issue-<n>` cannot satisfy "a fresh run never reuses another run's worktree" while worktrees are never removed: git refuses a second worktree on a branch that is checked out in the first. Consequences: a second run on the same issue after the first finished opens its own PR on its own branch (before it would have reused the old branch); `#27` (`wf gc`) can map branch to run to PR directly. The run id is the part after `implement-issue-`; characters a branch cannot hold become `-`, and a short hash of the whole id is added when that changed it, so `release 1.0` and `release-1-0` get different branches. Documented in the CHANGELOG, the governance doc, the install doc, the authoring chapter and both recipes copies.
2. **Base commit = the local head of the default branch, not fetched.** The default branch is the one `origin/HEAD` names (a clone records it), else the branch checked out in `ctx.cwd`; the local branch wins over `origin/<name>` so unpushed local commits stay in the base, as they did when runs started from HEAD. No network call. Limits, both stated in the CHANGELOG: a local default branch that is behind the origin gives an older base (run `git pull` first), and a repo without `origin/HEAD` that has a feature branch checked out uses that branch. The review's Spec finding 1 asked for a fetch; I did not add one (network at run start, fixtures without a `main` on the origin, and it would drop unpushed local commits from the base).
3. **The lock** is `.workflows/locks/issue-<n>.lock`, written by `acquireNamedLock` in `run-store.ts`; it reuses the `run.lock` machinery (atomic link, pid and process identity, stale takeover), which became `takeLock`. The lock content now also records `runId` (run.lock too). It is held for the whole `run()` (`try/finally`; the process-exit hook covers a crash). The refusal is a returned status, like `secret-blocked` or `baseline-red`, not a thrown error: `{ status: "issue-locked", issue, activeRunId, reason, lock }`. The metrics recorder classes it as `failed` (the workflow decided not to deliver), like the other refusals. The lock is per `ctx.cwd`, because the run store is: two runs of one repo from different directories do not see each other (Spec finding 5, dismissed: the spec puts the lock in the run store).
4. **Push.** `pushDelivery` asks the origin for the branch head (`git ls-remote`, network limit) and pushes only when the head is absent, equal to the delivered commit, or a commit in `progress.pushed` (written before each push, so a crash right after a push is still recognized). Then `Commands.pushOwned` runs `git push --force-with-lease=<branch>:<head> -u origin <branch>` and throws for a branch outside `wf/`. The explicit ownership check is what protects against foreign commits (mutation-checked: the lease alone, set to the head just read, lets the push through); the lease covers a push that lands between the check and the push. A lease rejection of that kind surfaces as a `CommandError` and fails the run (the resume then finds the foreign commit and answers `push-refused`).
5. **A run that began before this change** (progress has `baseCommit` but no `worktree`) keeps `wf/issue-<n>` and `.workflows/worktrees/wf-issue-<n>`.
6. **Never reuse, never delete another's.** A worktree path or branch that exists while this run has recorded nothing makes the run fail with "was not created by this run". The run records branch and worktree before `git worktree add`, so a crash inside the add is still the run's: if the recorded path exists but is not a worktree root (`rev-parse --show-toplevel` differs), it is removed and made again; without that check git would have run in the repository around the directory. Found by the Spec review.
7. The big whitespace-only diff in `implement-issue.ts` is the body of `run` moving one level into the `try/finally`: read it with `git diff -w`.
8. Metrics: `issue-locked` and `push-refused` are not added to `PENDING`.

## Learnings
- A fake-SDK handler can hold a run: make it `async` and `await` a promise the test controls. Gate only the first call (`held` flag), or a second run that reaches the same step waits for the gate too and the test deadlocks; release in a `finally` for the same reason.
- `git remote set-head origin main` (after `git push origin main`) gives a test repo the `origin/HEAD` a clone has.
- A `pre-push` hook runs after git has read the remote's refs, so it cannot simulate a push that lands between the lease read and the push.
- `--force-with-lease=<ref>:` with an empty expected value means "the ref must not exist".
- `git rev-parse --show-toplevel` run in a directory tells whether it is a repository root or only a directory inside another repository.
- A full `npm test` on a loaded machine trips timing tests (#40, #41); `--test-concurrency=3` on the runtime workspace gives a clean run.
- `gh issue view N --comments` prints nothing through the RTK rewrite; `gh issue view N --json title,body,comments` works.
- The worktree has no `node_modules`: `mise exec node@22.23.4 -- npm ci`, then prefix every command with `mise exec node@22.23.4 --`.
