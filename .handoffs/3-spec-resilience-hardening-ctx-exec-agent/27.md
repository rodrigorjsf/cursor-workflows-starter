## What was built
- `wf gc [--dry-run]` cleans up after `implement-issue` runs. For a run whose PR was merged or closed, or that failed more than `gcFailedAfterDays` ago (new `implement-issue` setting, default 14), it removes the run's worktree, its local branch and its branch on the origin.
- It prints the plan on stderr first (what goes, what stays and why, what is lost with a failed run), then removes; stdout is one JSON object (`dryRun`, `repo`, `failedAfterDays`, `remove`, `kept`, `errors`, each action with its `result`). `--dry-run` stops after the plan and changes nothing, not even the state directory. Exit 1 when something could not be read or removed.
- A run a process is executing is never touched (decided from the run's lock, and the lock is taken again during the removal). Nothing outside `wf/` branches or `.workflows/worktrees/` is touched, and a commit on the origin that the run did not push is never deleted.
- The origin branch of a run that merely failed stays when its PR is open (deleting it would close the PR). A `wf/` branch on the origin that no run of this repo owns (made in another clone) goes once its PR is merged or closed.
- The run's own state (`.workflows/runs/<runId>/`) stays. A resume of a run whose worktree and branch are gone now fails with a clear message instead of pushing an empty tree over the work.

## Decisions & deviations
1. **Where the runs come from.** The repo's own `.workflows/runs/*/tdd-progress.json` (branch, worktree, base commit, pushed commits) and event log, not the global runs index (`~/.cursor-workflows/runs.jsonl`) that the spec's `wf gc` bullet names. The index's own header says it exists for tools outside a repo; `wf gc` runs in one, and the run directory is the authority (the index is only written best-effort). Deviation from the spec text; no ADR touched.
2. **AC "remote refs … with no active run".** Read literally (every `wf/` ref on the origin that no active run owns) it would delete the branch of every delivered run whose PR is still open, which closes that PR; user story 11 says "remote refs of runs whose PR was merged or closed, or that failed more than N days ago". So: the origin branch of a run goes with the run when its PR is merged or closed; for a run that merely failed it goes only when no PR is open and the branch points at a commit the run pushed (`progress.pushed`); a `wf/` branch that no run of this repo owns goes only when its PR is merged or closed (an open PR or no PR keeps it, since nothing says whether the run behind it is still going); the old shared name `wf/issue-<n>` is never swept. "No active run" holds in every case: owned branches are decided with the run's lock, unowned ones have no run here.
3. **What "failed" means.** `outcomeClass` (the metrics' own definition, moved to `src/runtime/outcome.ts` so both read one) says `error` or `failed`, or the latest execution never wrote its end (the process died; `wf status` calls that failed too, at its last event). A cancelled run does not count (it is resumable on purpose); a run that finished without a delivered status and without failing does not count.
4. **The setting.** `gcFailedAfterDays` in `workflows.implement-issue.settings`, integer ≥ 0, default 14 (the content-retention default). `wf gc` reads it through the effective config of the `implement-issue` workflow. Added to `SETTINGS`/`Settings`, the schema, the regenerated reference, CHANGELOG ("eight settings").
5. **PR state** comes from `gh pr view <branch> --json state -q .state` run in the repo (checked against the real `gh`: a merged PR answers `MERGED`, a branch without PR answers `no pull requests found for branch "…"` with exit 1). Asked only for a run that pushed. Not `args.repo`: a run's `--repo` is not recorded in its state, so `gh` resolves the repo from the checkout. A `gh` failure other than "no PR" keeps the run, is listed in `errors` and makes gc exit 1 (story 16's rule, applied to gc).
6. **Runs begun before #25** (state has a base commit but no branch and worktree) are kept and listed: nothing in their state says which branch and worktree are theirs (the issue number is not recorded), and `wf/issue-<n>` is shared between runs. Removed by hand.
7. **Locking.** Planning reads `run.lock` (`isRunExecuting`); applying takes it (`tryAcquireRunLock`) per run, so a resume cannot start in the middle of a removal and a run that started since the plan is skipped (`result: "skipped"`, not an error).
8. **Removal.** `git worktree remove --force`, falling back to deleting the directory when git does not know it, then `git worktree prune`; `git branch -D`; the origin branch with `git push --force-with-lease=<branch>:<head> origin :refs/heads/<branch>` (a push since the plan is not deleted), only for `wf/` (`Commands.deleteOwned`). A failed action does not stop the others.
9. **Data loss is announced, not prevented.** The AC asks for failed runs' local branches to go. The plan notes, for a failed run, uncommitted files in its worktree and commits on no remote.
10. **`gc.ts` lives in `workflows/implement-issue/`** (it knows that workflow's progress file, naming and prefix) and `src/cli.ts` imports it and names `implement-issue`. A second workflow with leftovers would need its own command or a generic cleanup hook; not built (one workflow).
11. **gc uses the workflow's timeouts for git and gh** (local git 5 minutes, network 120 s), moved to `commands.ts` as `LOCAL_GIT_TIMEOUT_MS` and `NETWORK_TIMEOUT_SEC` and run through `runCommand` (the async runner `ctx.exec` is built on) via an `Exec` adapter, so gc reuses `Commands`.

## Learnings
- A run can be held mid-execution without a fake-SDK gate: resume a delivered run with a `testCommand` that touches a marker file and waits for a gate file; the final suite runs through `ctx.exec`, the run lock is held by the test's process, and a child process sees a live holder.
- To make a run look old, rewrite the `ts` of every line of its `events.jsonl`; `gc` reads only that.
- `git push --force-with-lease=<ref>:<sha> origin :refs/heads/<ref>` deletes a remote branch only if it still points at `<sha>`.
- `git ls-remote --heads origin 'refs/heads/wf/*'` matches across slashes, so `wf/issue-7-abc` is listed.
- `gh pr view <branch> --json state -q .state` finds merged and closed PRs; "no PR" is exit 1 with `no pull requests found for branch "…"`.
- `gh issue view N --comments` prints nothing through the RTK rewrite; `gh issue view N --json title,body,comments` works.
- The worktree has no `node_modules`: `mise exec node@22.23.4 -- npm ci`, then prefix every command with `mise exec node@22.23.4 --`.
- A mutation that survives is a test that never exercised the guard: both guard tests first passed because no rule would have removed the run they tampered with.
