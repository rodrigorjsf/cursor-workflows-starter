## What was built
- `workflows/implement-issue/forge.ts` gains the GitLab implementation of `Forge` (`GitlabForge`, name `"gitlab"`): `glab issue view <n> --output json` for the issue (labels normalized to `{ name }`); `glab api --paginate projects/<p>/issues/<n>/notes` for the notes (system notes dropped, every page read); `glab api --method POST …/notes -F body=@<file>` for the comment; `glab mr create --source-branch <b> --title <t> --description <text> --yes` for the MR (never `-H`; the URL is taken out of glab's output); `glab api …/merge_requests?source_branch=<b>&order_by=created_at&sort=desc&per_page=1` for the latest MR's URL and state (`opened`/`locked` are `OPEN`); `glab api projects/<p>` (`web_url`) for the repository URL.
- A fresh run detects its forge from the host of the `origin` remote (`detectForge`: `github.com` is GitHub, `gitlab.com` is GitLab; https, `ssh://` and scp-like URLs; case-insensitive) and records it in its progress. A resume keeps the forge its record names; a record file with no `forge` is GitHub (never re-detected).
- The card's link reads `MR !N` for a GitLab merge request URL and `PR #N` for a GitHub pull request URL (`prLabel`, now in `forge.ts`).
- Fixture: a fake `glab` beside the fake `gh`, one JSON state for both. The fake whose forge the test is not on fails the call (exit 99) and records it in `wrongCli`. `forgeTest(title, fn, forges?)` registers one test per forge, each in a fresh environment whose `origin` is `https://<forge host>/owner/repo.git` (reaching the bare repo through `url.<base>.insteadOf`).
- The delivery, robustness, config, hardening and card tests now run on both forges: every test in them that runs the workflow is registered with `forgeTest` (exceptions below). New: `implement-issue.forges.test.ts`.

## Decisions & deviations
- Test names: the fixture accessors were renamed because the state is no longer `gh`'s: `gh()` → `forgeState()`, `failGh` → `failForge`, `fx.ghState` → `fx.forgeStateFile`, env `FAKE_GH_STATE` → `FAKE_FORGE_STATE` (mechanical, across the implement-issue tests). New fixture helper `changeForgeState`.
- `setup()` stays zero-argument (node:test's `beforeEach` hands the hook a context object); `forgeTest` calls an internal `setupFor(forge)`.
- Both forges' fixtures now give `origin` a host URL (`https://github.com/owner/repo.git` / `https://gitlab.com/…`) with an `insteadOf` rewrite to the bare repo, so the GitHub variants also go through detection and #82 can make an unknown host an error without touching the fixture. The whole existing GitHub suite stayed green under it.
- Detection reads the raw `remote.origin.url` (`git config --get`), not `git remote get-url` (which applies `insteadOf` and would hide the host in the fixture; a user who cloned from a host spelled through an `insteadOf` shorthand will hit #82's unknown-host error, not a wrong CLI). Interim, per the code comment: until #82 (`forges` map, unknown host is an error, the `repo` argument's host) every other host, a local path and no `origin` are GitHub, as before.
- A fresh run is "no progress file at all" (`ProgressStore.existed`). A hand-written record in a test needs `forge` for a GitLab test (done in the "interrupted `git worktree add`" delivery test).
- `repoUrl` uses `glab api projects/<path>` (`web_url`), not `glab repo view`: I believe `repo view` has no JSON output (not verified, no glab binary here). The spec lists "repository view" among the commands glab covers; spec B's real run should confirm either.
- `glab mr create` has no body-file flag, so `openPr` reads the body file and passes the text as `--description <text>` (an argv entry, no shell). Consequences: the MR body is in the event log's command line (redacted like all events, where GitHub logs only a temp path), and a body over Linux's 128 KiB single-argument limit would fail to start (`pr-body.ts` caps a body at 60 000 characters, so only a text of mostly multi-byte characters could reach it).
- `repo` arguments reach the REST routes as a path (`group/sub/project`, or a URL of it, stripped of its host: `repoPathOf`), url-encoded; glab commands get `--repo <repo>` as given. Nested groups work in the adapter; #82 owns the run lock and same-repository check tests for them.
- Two tests stay GitHub-only on purpose: the ones that wrap `gh` to answer `repo view` (`ghKnowsTheCwdRepository`; the GitLab twin is the `--repo` test in the forges file). Three need no forge and are plain `test`: the `Commands.pushOwned` unit test and the two declaration tests in the config file.
- `CODING_STANDARDS.md`: the five `_See:_` line citations into `implement-issue.ts` re-pointed (409, 557, 587, 606, 1077), each checked against its code. No CHANGELOG entry (#90) and no book/skills edit (#87): `docs/authoring/01-escrevendo-workflows.md:240` still names only `gh repo view` for the lock.
- `implement-issue.ts` line 1 (pt-BR) and the `meta.description` now say "forge (GitHub or GitLab)".

## Learnings
- node:test passes a context object to a `beforeEach(fn)` hook: a hook function must not take its own parameters.
- A fake CLI written as a TS template literal needs doubled backslashes (`\\n`, `\\d`, `\\/`): single ones silently break the script.
- `git remote get-url` applies `url.<base>.insteadOf`; `git config --get remote.origin.url` is the raw value.
