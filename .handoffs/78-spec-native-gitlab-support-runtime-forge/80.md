## What was built
- New `packages/runtime/workflows/implement-issue/forge.ts`: the `Forge` interface (`issue`, `issueComments`, `commentOnIssue`, `openPr`, `prUrl`, `prState`, `repoUrl`) with one implementation, GitHub through `gh`. It is the only file that names `gh` for `implement-issue` and `wf gc`.
- `implement-issue.ts` and `gc.ts` call the forge instead of `Commands.gh` / `ghOrNothing` / `prState` (all removed). The `gh` argument lists are byte-identical to before, so behaviour, step labels (`gh issue view`), timeouts and `CommandError` text are unchanged.
- A run writes `forge: "github"` to its progress record (`tdd-progress.json`) as soon as it holds the issue lock, before triage. `wf gc` asks the forge the record names; a record without the field is GitHub; a record naming an unknown forge is an error (the run fails before any CLI call; gc keeps the run and lists an error), never a fall back to `gh`.

## Decisions & deviations
- Forge module lives in `workflows/implement-issue/forge.ts` (beside `commands.ts`, `gc.ts`), not in `src/runtime/`: only `implement-issue` and gc use it in this spec; the dashboard stays on its own `gh` call (spec B). ADR-0009 says only "internal to the runtime".
- `Commands` keeps its constructor and the git methods. Its three `gh` methods became forge-neutral `forgeRead(cli, cwd, ...args)` / `forgeReadOrNothing(cli, cwd, nothing, ...args)`; the two-word log label (`gh issue view`) is now `FORGE_LABEL_WORDS = 2` for any forge CLI (`glab issue view` will read the same). `PrState` moved from `commands.ts` to `forge.ts` (same shape).
- Interface takes `repo?: string` per call instead of a pre-built `--repo` flag; `openPr` takes `{ branch, title, bodyFile, repo }`. Bodies stay file-based (`withBodyFile` kept in `implement-issue.ts`), as the spec says "from a body file".
- `issueLockName` now takes the forge and still lower-cases `repoUrl` (GitHub names ignore case); #81 owns the GitLab-specific comparison.
- Progress `forge` is typed `string` (not `ForgeName`) and `createForge(name: string)` narrows: the file may hold a name a newer kit wrote. Unknown name = error with a remedy ("Upgrade the kit"), a small addition beyond the ticket, justified by ADR-0009's "never send a deletion decision's query to the wrong CLI".
- `wf gc` paths with no run record (an origin `wf/` branch no run of this repo owns; the pre-ownership shared `wf/issue-<n>` branch) use `DEFAULT_FORGE` (GitHub), built once in `planGc`. #82/#83 must decide detection for them.
- The progress record is written right after the issue lock (inside the `try`), so an `issue-locked` run leaves no progress file; a run that fails on its first forge call leaves one holding only `forge`. gc skips such runs (no `branch`).
- `CODING_STANDARDS.md`: five `_See:_` line citations into `implement-issue.ts` re-pointed to the shifted lines; the idempotency rule now says "look a branch's PR up before opening one (`forge.prUrl` before `forge.openPr`, which is `gh pr view` before `gh pr create` on GitHub)". Header comment of `implement-issue.ts` updated (one English bullet; older pt-BR text kept).
- No CHANGELOG entry: nothing changes for a user; the release ticket (#90) owns the changelog. `wf doctor` (`gh` check, #85) and the dashboard's `gh` call (#86) were left alone on purpose.

## Learnings
- A fresh run-spec worktree's `mise.toml` is untrusted: `mise exec -- npm ci` fails; use `MISE_TRUSTED_CONFIG_PATHS=<worktree>` (no persistent state), not `mise trust`.
- Bash `export` does not persist between calls here: put `export MISE_TRUSTED_CONFIG_PATHS="$PWD"` in every command.
