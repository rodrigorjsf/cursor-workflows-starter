## What was built
- `wf doctor` has one check id, `forge`, where it had `gh`, in the same position (5th of 8). It reads the cwd's `origin` with git, decides the forge the way a run does (github.com GitHub, gitlab.com GitLab, any other host from the config's `forges` map) and runs `gh auth status --hostname <host>` or `glab auth status --hostname <host>`.
- A missing CLI fails with where to get it plus the login command; a logged-out CLI fails with what it printed (first 4 lines) and `Run \`<cli> auth login --hostname <host>\``.
- Outside a git repository, or in one with no `origin`, the check passes and says why. An undeclared unknown host fails with the run's own error (names the host and `"forges"`) and a hint to declare it.
- Install guide, setup skill, book 2.1 and 2.3, both READMEs and the CLI usage line list `forge`; no doc names a `gh` check. The title of the check is "Forge CLI".

## Decisions & deviations
- **gh is asked per host too** (`gh auth status --hostname <host>`, ticket text says plain `gh auth status`). Both CLIs keep a login per host and `auth status` with no host fails for another host's expired login, so a GHE user with a stale github.com token (or the reverse) would get a wrong failure. A host-less origin (local path) is GitHub and asks without `--hostname`. Found by the Spec review.
- **Host spelling** as #82's handoff said: `host:port` for an http(s) origin with a port, bare host for ssh/scp-like (`webHost` in `forge.ts`, shared with `hostFlag`).
- **A host-less origin is GitHub** (mirrors `detectForge`; `gh` reports a missing remote itself).
- **`git` missing from the PATH fails the check** (the origin cannot be read, so it cannot say anything true); no criterion asked for it. Hint: install git.
- **git runs with `LC_ALL=C`**: the check reads git's "not a git repository", which git translates; a translated locale would have failed the check outside a repository (Spec review, test-first with a translating fake git).
- **An unresolvable config** fails the check only when the origin's host needs the `forges` map (github.com/gitlab.com resolve without it); the message then points at the configuration check, like the `models` check does. The map comes from the first resolved workflow (it is file-level, identical in every workflow).
- **Any other `git` failure** (`rev-parse` exit != "not a repository", `config` exit other than 1) fails the check with git's first lines and a hint, never a silent pass.
- `forge.ts` gained `forgeOfOrigin`, `OriginForge`, `loginOf`, `ForgeLogin`, `FORGE_CLIS` (a total `Record<ForgeName, …>`); `detectForge` now calls `forgeOfOrigin`. The CLI names stay in `forge.ts` only.
- `doctor.ts` drops its file-local `messageOf` for `errorText` (CODING_STANDARDS, error handling); same body, 11 call sites.
- CHANGELOG and version bump left to #90; README/book prose beyond the check list, `forges` documentation in the book, left to #87.

## Learnings
- git translates its messages: run it with `LC_ALL=C` before matching its text.
- The doctor process tests' PATH holds only fakes and node: put a real `git` dir on it (`gitDir`) for anything that reads a repository.
- A fresh worktree's untrusted `mise.toml` blocks `mise exec`: put `~/.local/share/mise/installs/node/22.23.4/bin` on PATH, then `npm ci --prefer-offline`.
