## What was built
In the dashboard's Run view, a step that ran as a Cursor cloud agent now shows a **☁ cloud** badge on its node. Its details (the hover tooltip and the facts above the step log) list where it ran, the **Cloud agent** as a link to it in Cursor (`https://cursor.com/agents/<bc-id>`, new tab) and its **cost**. The id comes from the `cloud-agent` event, so the link is there while the step still runs. The step log shows what the cloud agent said, as for a local agent; for a step that a resume reattached to a running agent (a run with no stream) the engine now logs the agent's final answer as its message. Local steps and commands look exactly as before.

Two runtime fixes came along (see Absorbed): the reattached answer as a message, and a snapshot branch left on the remote when a timeout or cancel arrived during the push.

## Decisions & deviations
1. **The link is built by the dashboard** from the agent id (`https://cursor.com/agents/<id>`). The format is the `url` field of the Cloud Agents API (`https://cursor.com/agents/bc-<uuid>`, read from Cursor's docs this run); the runtime does not store it, so the event schema did not change. Only an id shaped like `bc-[A-Za-z0-9-]+` becomes a link, anything else is shown as text (an event log is data, not a source of addresses). The dashboard's own doc says it writes this one outside address.
2. **`reattached` and `snapshot` of the `cloud-agent` event are not shown.** #34's notes offered them; the ticket asks for badge, link and cost, and a step with a takeover already shows `Attempts: 2`.
3. **`describeNode` returns `{ name, value, href? }` rows instead of pairs** so a row can be a link; callers and tests were updated (`StepLogPanel`, `nodes.tsx`, `node-details.test.ts`). The panel's list of facts and the cloud mark moved into `describeFacts` and `runsInCloud` (pure, tested) after review.
4. **The tooltip of a cloud step takes the pointer** (`.tip.linked`, with a 7 px bridge to its node) so the link can be clicked; the tooltips without a link still let the pointer through. The link in the tooltip is out of the tab order (`tabIndex=-1`): `:has(:focus-visible)` did not keep the tooltip open when focus moved into it (measured in Chrome), and a link inside the node's `role="button"` is not exposed to screen readers anyway. The keyboard route is Enter on the node, which opens the panel with the same link (tabbable, in the accessibility tree).
5. **The reattached answer as a message** (`converse` in `backend.ts`): see Absorbed. It changed the takeover `warning` text of `engine.ts` and four doc places (config reference source `scripts/config-reference.ts` and its generated page, architecture chapter, research chapter §14).
6. **Docs/changelog/skill edits**, all pt-BR in the book and English in the skill and wizard: `docs/operating/03-observabilidade.md` (hover, cloud steps, step log, the one outbound link in the security list), `docs/internals/01-arquitetura.md`, `docs/research/verificacoes-locais.md`, `docs/usage/03-invocacao-no-cursor-ide.md` and `skills/cursor-workflows-setup/references/validate.md` plus a `note` line in `scripts/verify/validate-cursor-ide.sh` (scenario 8: look at the badge and the link; not part of the pass), `CHANGELOG.md`, regenerated `docs/reference/config.md`. No `CLAUDE.md` / `AGENTS.md` edit.
7. **Worktree has no `node_modules`.** 28 process tests (doctor, init, install, upgrade, `copyKit`) failed on it. I symlinked MAIN_REPO's `node_modules` into the worktree for the runs (untracked, removed before the final status check); MAIN_REPO's working tree was not touched. Without it the dashboard and runtime still resolve through the parent directories.
8. **Another ticket (#35) ran its suites on the same machine** while I worked: that load is what exposed the two flakes in Absorbed.
9. **Browser validation** (`chrome-devtools` MCP, Chrome on Windows, `http://127.0.0.1:47336`, a throwaway `WF_HOME` and repo in the scratchpad, dashboard started from the worktree and stopped after): fixture = a real engine run `cloud-demo-0001` (fake SDK: 1 local step, 2 cloud steps in a parallel group, 1 command, 1 local step) and a hand-written run `cloud-demo-live` with a cloud step still running. ## Absorbed
- absorbed: a cloud step that a resume reattached to a running agent had nothing of the agent in its step log (the run found by a lookup has no `onDelta`), verified by `cloud.lifecycle.test.ts` "a reattached step's log holds what the agent answered, as a message…" (red before the one-line change in `converse`, green after) and the docs/warning text updated.
- absorbed: a timeout or cancel that arrived while the snapshot was being pushed killed the push, but a remote that already had the objects went on to accept the branch, and nothing deleted it (`pushSnapshot` promised "a failure leaves nothing on the remote"). Reproduced 5 times in 14 runs of `cloud.test.ts` under load, and deterministically with a slow `pre-receive` hook; fixed in `cloud-snapshot.ts` (the push is not cut by the abort; the caller's cleanup deletes the branch), verified by `cloud.test.ts` "a timeout that arrives while the snapshot is being pushed still leaves no branch on the remote…" (red with the leftover `wf/cloud-snapshot/…` branch, green after) and 16 parallel copies of `cloud.test.ts` ending `# fail 0` (the 2 that were still running were the next item). **Trade-off:** a cancel during a push now waits for the push (bounded by the 5 minute network timeout).
- absorbed: `cloud.test.ts` "the snapshot branch is deleted when the step ends any way it ends" hung for the step's 30 minute default timeout under load (the full suite took 1,800,649 ms on that test): its 100 ms timeout fired before the agent got its message, the case's entry of the fake SDK `script` stayed in the queue and the next case's agent took it. Reproduced deterministically (slow hook, `script` held 2 entries, `timeout after 4000 ms`); each case now starts from an empty script and the timed-out case uses 1500 ms; verified by the full suite and by the fixed test passing with a push that always outlasts the timeout. (Filed as #46 while it was a suspicion, closed the same session once the cause was found.)

## Learnings
- A ticket worktree under `.git/run-spec/…/wt/<n>` has no `node_modules`: the process tests (`copyKit`, doctor, install, upgrade) fail until you symlink MAIN_REPO's, and the symlink must go before the final `git status`.
- Other tickets' suites run on the same machine: a test with a 100 ms step timeout that starts with a git push is load-sensitive; clear the fake SDK `script` between cases.
- A step test whose abort can come before `send()` leaves its `script` entry unconsumed: the next agent takes it.
- `:has(:focus-visible)` did not keep a hover tooltip open when focus moved into it (Chrome); the page's CSP blocks an injected `<style>` in the console.
- `chrome-devtools` `take_screenshot` with a `filePath` outside the workspace roots is refused (the MCP runs on Windows); omit the path.
- `pgrep -f '<pattern>'` also matches the shell line that contains the pattern; use `ps … | grep '[p]attern'`.
- A foreground command that runs over 180 s is moved to the background; `sleep N; cmd` is blocked: use `run_in_background`.
- Candidate Applied Learning bullets: "Ticket worktrees lack node_modules: symlink MAIN_REPO's for process tests, remove before commit." / "Step tests: clear fake SDK `script` between cases; an early abort leaves entries."
