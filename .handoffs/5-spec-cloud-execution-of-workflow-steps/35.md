## What was built
A step that can write now runs on a Cursor cloud agent (a role declared `ok`; a `read-only` role still fails before spending, a `never` role is still refused by the config). The agent is created with `workOnCurrentBranch: true` on the snapshot branch and told to commit there, even when the workflow's prompt says not to run git. When its run finishes, the engine fetches the branch and fast-forwards the worktree (branch, index, working files) to it, then deletes the snapshot; commands the workflow runs afterwards with `ctx.exec` (the TDD loop's tests) see the agent's work. It is a fast-forward or nothing: the step fails, with the worktree untouched, when the agent rewrote the history, the local branch moved, the working files changed while it ran, or the agent adds a file where the worktree has a git-ignored one. A move that fails half way is put back by the engine. A role can also set `resultVia: "artifact"`: the agent saves `result.json` in its artifacts directory and the engine downloads it after the run (instead of reading the last fenced JSON block).

## Decisions & deviations
1. **"A non-fast-forward fails the step and reverts" = the worktree is left as it was.** A refusal is decided before anything is applied, so there is nothing to revert; the engine's revert machinery runs only when the move itself fails after it began (`AttemptResult.touchedWorktree`, set by the backend; tested by making `update-ref` fail with a lock file). Reverting after a refusal would undo what the person changed during the step (the reviewer proved `revertOnRetry` and cancellation did exactly that; fixed, see Code review). The refused attempt is retried like any failed attempt (`retries`); a retry takes a new snapshot, so it builds on what the person changed.
2. **The worktree is refused, never overwritten.** The working files must still equal the snapshot (tree compared with `add -A` in a temp index, like the snapshot), the local branch must not have moved, and the agent must not add a file where the worktree has a git-ignored one. The move itself is `read-tree <snapshot>` (index := snapshot), `read-tree --reset -u <tip>` (files and index := the agent's tree, like `reset --hard`), then `update-ref HEAD` last. Known tiny window between the check and the move (two git commands); not closable without a lock git does not offer.
3. **Snapshot of a clean worktree is HEAD itself** (changes #33's snapshot): no empty "wf: snapshot" commit lands in the local history. A dirty worktree keeps a snapshot commit that joins the history with the agent's commits (the agent built on it). Documented in the config reference, ADR-0005, the architecture chapter, the runtime-api copies.
4. **`cloud-agent.snapshot.commit` (optional) is logged** so a resumed write step can check the worktree against the snapshot the interrupted agent started from. A reattached write step whose log lacks it fails with a message (only possible for logs from before this ticket, which had no write steps).
5. **`resultVia: "json-block" | "artifact"`** is the switch (role preference; absent from the effective config until a layer sets it, so existing effective configs are unchanged; rejected on a `labels` glob like `location`). The prompt asks for `/opt/cursor/artifacts/result.json`; the engine accepts `result.json`, `artifacts/result.json` or `/opt/cursor/artifacts/result.json` from `listArtifacts` (never a deeper `result.json`). **Unverified against the real API** (the doc says paths are relative to the workspace's `artifacts/` dir and rejects the absolute v0 form): rows added to research §14 as "not run".
6. **`implement-issue`'s write roles stay `cloud: never`** (their prompts forbid git; nothing verified on a real cloud agent): follow-up #45. The backend's write instruction overrides prompts that forbid git.
7. **An agent whose run says it pushed only to another branch fails the attempt, naming it** (the first version adopted that branch; the Spec review called it scope creep that leaves a branch behind).
8. **Engine: a cloud step is reverted only when `touchedWorktree`** (not by `revertOnRetry`, not by cancellation), because the agent's edits live in the VM.
9. `converse` takes an async `check` and runs it only for a run that finished (an errored run must not call the artifacts API); `AttemptResult.touchedWorktree` and `StepOptions.resultVia` added to the backend seam.

## Learnings
- This machine's global git config has `core.autocrlf=true`: test repos must set `core.autocrlf=false` and clone with `-c core.autocrlf=false`, or a checkout writes CRLF.
- `git read-tree -m -u` verifies "uptodate" by stat only: an index rebuilt with `read-tree <tree>` has no stat data and fails "Entry not uptodate"; use `read-tree --reset -u` once the working files are known to equal the tree.
- `RunGitInfo` is not exported by `@cursor/sdk`: use `NonNullable<RunResult["git"]>`.
- Cursor cloud API docs: `workOnCurrentBranch: true` pushes to the starting ref, pushed branches are in `git.branches[]`, artifact paths are relative to the workspace's `artifacts/` dir and artifacts are agent-scoped.
- One combined run of the cloud test files hung once for 180 s during development and did not reproduce (single files and the full suite were always fine); if it shows up again, run the files one at a time with `timeout`.
- Candidate Applied Learning bullets: "Test git repos: set `core.autocrlf=false`; this machine's global value is true." / "`git read-tree -m -u` needs stat-fresh index; use `--reset -u` after verifying files."
