## What was built
`wf gc` now also lists `refs/heads/wf/cloud-snapshot/*` on the remote that the resolved `cloud.remote` names (default `origin`) and removes the branch of a run of this repo that no process executes and whose last event is older than a grace period (new `implement-issue` setting `gcSnapshotGraceHours`, default 24). A snapshot is kept, with a reason line in the plan, when its run is executing, is not in this repo (another clone), is inside the grace period, when its name is not one a cloud step builds, when several run ids map to the same name segment, or when the run has no event log. A run cut off in the middle of the cloud step that owns the branch keeps it for `gcFailedAfterDays` days (a cancelled run, without limit, like gc keeps the run itself): the resume reattaches to that agent and a write step's work is on that branch. A snapshot never reaches the PR lookup, is listed once, and a remote that refuses a deletion lands in the plan's `errors` without stopping the sweep. `--dry-run` shows removals and keeps with reasons.

## Decisions & deviations
1. **Grace period**: `gcSnapshotGraceHours`, an `implement-issue` setting next to `gcFailedAfterDays` (the existing gc config), default 24 hours, `number >= 0` (0 = no grace). The reason is documented in the schema, the config reference, the operating chapter and `SNAPSHOT_GRACE_HOURS` in commands.ts: a cloud agent may still start from the ref after the process died, and nothing has measured how late it reads (research §14).
2. **"Last event"** is the last event of the whole log (every execution). A run with no event at all is kept (the log is the only source, ADR-0002; a review finding removed an mtime fallback).
3. **The cut-off hold** (honouring #34/#35's record): `interruptedCloudSteps` over the run's log finds a `cloud-agent` with no `step-end` naming this branch; it holds for `gcFailedAfterDays` after the last event (the horizon after which gc already gives up on a failed run and removes its worktree), and without limit for a run whose last end is `cancelled` (gc keeps such a run for ever as resumable; a forced second-signal stop writes `run-end` cancelled with no `step-end`). Only the branch name is compared, not the recorded remote (the names carry a random id).
4. **Only the configured remote is swept** (criterion 3). A snapshot on `origin` while `cloud.remote` is another remote is kept with a reason and never looked up as a PR. Consequence, accepted: leftovers on an old `cloud.remote` after the setting changed are not swept until it is set back. The event-log record (`snapshot.remote`) could widen this later; not done (the ticket says the configured remote).
5. **Ambiguous run ids** (two run directories whose ids sanitize to the same segment, only possible with hand-chosen ids; generated ids are `<workflow>-<8 hex>`): kept, with a reason, instead of locking several runs.
6. **No re-check under the lock.** `applyGc` takes the run's lock like the existing sweep and does not re-evaluate grace or the hold; the window is plan to apply, as for every other cleanup (the lease on the deletion covers a moved branch).
7. **API changes**: `planGc` takes `snapshots: { remote, graceHours }` (required); `GcReason` gains `"snapshot"`; `GcAction.remote`, `kept[].remote`; `Commands.remoteOwnedHeads(cwd, remote, prefix)` and `deleteOwned(cwd, branch, expected, remote)` default to `ORIGIN`; `cloud-snapshot.ts` exports `snapshotRunSegment` and `snapshotBranchSegment` (and `snapshotBranch` uses the first). The sweep covers every run directory of the repo, not only `implement-issue` runs (cloud steps run in any workflow).
8. **Docs** (pt-BR book, generated reference regenerated by `npm run docs:config`): operating chapter 5.1 (the rules), usage 3.x pointer, architecture pointer, config reference and schema, CHANGELOG. The ADR-0005 text was left as it was (convention: a decision changes by a new ADR); the rules are not in the ADR.
9. No `CLAUDE.md`/`AGENTS.md` edit.

## Learnings
- `abortOpenRuns(() => "…", "cancelled")` in a test writes a real forced-stop `run-end` to the log of an execution still open in the process: a cheap way to make a cancelled run with a cut-off step.
- `git push --force-with-lease=<branch>:<sha> <remote> :refs/heads/<branch>` deletes on any remote; a bare remote's `hooks/pre-receive` (exit 1 when `new` is all zeros) makes a deletion refuse in a test.
- `tsc` here does not typecheck `packages/runtime/test`: a changed signature breaks a test only at run time.
- Candidate Applied Learning bullets: "Tests are not typechecked; change a signature, then grep its test callers." / "Bare-remote pre-receive hook simulates a refused branch deletion."
