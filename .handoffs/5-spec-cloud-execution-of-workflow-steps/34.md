## What was built
A cloud step now survives the machine. The engine writes the cloud agent's id to the event log (`cloud-agent` event, with the snapshot branch the agent starts from) the moment the agent exists. A resume of a crashed run takes the interrupted agent over (`Agent.resume`, `Agent.listRuns`): it waits for the run the agent already has, without sending the prompt again, pays for the agent's usage once, and deletes the snapshot branch the crash left. A cloud agent the cloud no longer knows is replaced by a new one with a warning; one that cannot be reached is never replaced (the attempt fails, the next one reattaches again). Cancelling a run cancels its cloud runs, the reattached one and one still being looked up included. The SDK client's two-hour wait limit no longer fails the step: the backend asks the cloud (`Agent.getRun`) and waits again for a run that goes on. `scripts/verify/verify-cloud.ts` is the real-API verification workflow and the wizard has an optional scenario 8. The workflow was **not run against the real API** (Decisions 1).

## Decisions & deviations
1. **The real-API run did not happen.** The run needs a GitHub repo that Cursor can reach (`setup-sandbox-repo.sh` creates one), pushes and deletes a throwaway branch on its `origin`, uses the account's API key and spends quota. This autonomous run's rules forbid pushing any branch, and creating a repository or spending on the maintainer's account was not authorised. So criterion 5 is half met: the workflow, its README (procedure, what to look at, manual reattach/cancel checks) and §14 of the research chapter exist; the measured results do not. **Whoever merges should run it and fill §14** (`scripts/verify/README.md`, section `verify-cloud`) before treating #34 as fully done; I did not file an issue for this (it is a deferred run, not a suspicion).
2. **New event `cloud-agent`** (not a reuse of `step-end.agentId`): `{ attemptId, agentId, reattached?, snapshot? }` plus `StepRef`; only cloud steps emit it. The snapshot ref is in it so a resume can clean up after a crash. pt-BR interface docs in `events.ts` (the generated reference is pt-BR); `docs/reference/events.md` regenerated.
3. **Reattach matches by `stepId`** (`RunStore.interruptedCloud`, projection `interruptedCloudSteps`: a `cloud-agent` with no `step-end`). The first attempt of the step gets `StepOptions.reattach`; the backend resumes the agent, picks the run still going (else the newest by `createdAt`: the API's list order is undocumented), and `converse` starts from that run's answer (`Exchange.attach`, `converse({ running })`); schema re-prompts go to the resumed agent. A run that already finished while no one watched hands over its answer at once.
4. **SDK fact that shaped "gone"**: `Agent.create` for a cloud agent only mints the `bc-` id client-side; the server creates the agent at the first `send()`. A crash between the logged id and the send leaves an id the server never saw, so a 404 from `listRuns` (a `ConfigurationError` with `status: 404`, or code `agent_not_found`) means "start a new agent", not an error. Read from `node_modules/@cursor/sdk/dist/esm` (`Zr`, `M.send`/`createServerAgent`); unconfirmed against the real API (§14).
5. **Unreachable is not gone.** Any other failure to reach the agent returns `AttemptResult.reattachFailed`; the engine keeps handing the same agent to the next attempt. Nothing is closed in the log until an attempt actually has an agent (the `agent` event), so if every attempt fails the next resume still finds the step interrupted.
6. **Closing the dead attempt and the budget.** When an attempt has an agent, the engine writes a `step-end` for the dead attempt (`errorKind: "exception"`, `chargedCents: 0`). Same agent taken over: no usage on that `step-end` and the budget stops counting the turns the dead attempt had reported (`spentTokens`, totals), because the reattaching attempt reads the whole agent's usage (`getUsage`). Agent lost and replaced: the dead attempt's `step-end` carries its reported tokens, which were real spend nothing else will count.
7. **Wait limit.** `settleCloudRun` (SDK 1.3.1 `448.js`: `Date.now()+72e5`, then `setWaitDeadlineError`, which fails *that handle* while the run goes on): on any `error` answer it asks `Agent.getRun`; a run still going, or ended meanwhile, is waited on again; only a run the cloud calls failed is an error. A floor between waits (`waitFloorMs`, default 1 s, injectable for tests) keeps a failing client from spinning on the API. The step's `timeoutMs` still bounds a long step.
8. **Cancel.** The existing `runAttempt` path already cancels the in-flight cloud run for a run that is executing (tests added). Added: an abort while the backend looks the interrupted agent up gets a short grace for the list and cancels the run it names. **Not done: cancelling a run whose process already died** (`wf cancel`, `cancel_workflow`, the dashboard button find no process to signal) does not call the Cursor API, and so does a resume that never reaches the step. Doing it needs the SDK and the API key in the cancel path, which ADR-0002 and CLAUDE.md keep out of the dashboard's `observe` graph (a design decision for the maintainer, not a small fix). Documented in the config reference, the architecture chapter, ADR-0005, CHANGELOG and the authoring skill: resume the run with the same `runId`, then cancel.
9. **A reattached run has no stream.** A handle from `listRuns`/`getRun` is created without `onDelta`, so no `turn`/`text` events for what it does after the takeover and the live token caps act only when its run ends. The warning at takeover says so.
10. **`AgentBackend` seam grew** (backend.ts): `StepOptions.reattach`, `AttemptEvent` `agent` carries `snapshot`/`reattached`, `AttemptResult.reattachFailed`, `Exchange` (with `attach`), `SettleRun`, `runAttempt(..., settle?)`, `converse({ running })`; `within`, `classifyError`, `SEND_GRACE_MS` exported for the cloud backend; `deleteSnapshot` takes `Pick<PushedSnapshot, "top"|"remote"|"branch">`. The local backend is unchanged (the existing tests pass untouched, apart from one assertion that now expects the `snapshot` on the cloud `agent` event).
11. **Wizard scenario 8** is optional: after scenario 7 the wizard asks yes/no; a "no" records nothing. It prints the config keys the person merges into `~/.cursor-workflows/config.json` and writes nothing itself (only the machine owner may allow the cloud); it then prints the `cloud-agent` events of the sandbox's runs and `git ls-remote` for leftover snapshot branches. `validation-report.ts` marks scenarios past the seventh `optional: true`; the summary, the title and `releaseCriterionMet` count the first seven only. `smoke`'s role `ping` (cloud `ok`, `tools: []`, read-only) is the workflow used.
12. **Edits outside code**, all required by the change: `docs/reference/events.md` and `docs/reference/config.md` regenerated from their generators; ADR-0005, architecture chapter, CHANGELOG, IDE doc (2.3), maintainer scripts doc (9.4), both copies of `runtime-api.md` (identical), `cursor-workflows-setup/references/validate.md`. No `CLAUDE.md`/`AGENTS.md` edit.

## Learnings
- `( cmd ) &` inside a background Bash call returns at once, so the completion notice is false: run the command itself in the background.
- A test helper that starts an execution and then fails must abort it: an abandoned engine holds a 30-minute step timer and hangs the test process.
- SDK 1.3.1: cloud `Agent.create` mints the `bc-` id locally and the server learns the agent at the first `send()`; cloud `wait()` gives up after two hours with `status: "error"` on a handle that stays failed, while `Agent.getRun` gives a fresh one.
- `mise exec node@22.23.4 -- npm test` takes about three minutes; the fake SDK's `crashWhileTheAgentRuns` pattern simulates a crash without a child process.
- Candidate Applied Learning bullets: "Background `( cmd ) &` inside run_in_background ends instantly; run the command directly." / "Cloud `Agent.create` mints its id locally; the server learns it at first `send`."

## Notes for dependent tickets
- **#35 (write steps):** a write step that is interrupted also reattaches: `StepOptions.reattach` and `cloud-agent` are location-wide, not read-only specific, but the engine's `location === "cloud" && writes` guard in `runStep` still rejects such steps before any attempt. After lifting it, a reattached write attempt must fetch the agent's commits from `reattach.snapshot.remote` like a fresh one; `closeInterrupted`/the budget netting need no change. The snapshot branch is also where the agent's own branch starts, so deleting it at the end (as now) must happen after the fetch.
- **#36 (dashboard):** the `cloud-agent` event gives the agent id (`bc-…`) as soon as it exists, while the step is still running, plus `reattached` (a step that was taken over) and `snapshot`. `step-start`/`step-end` carry `location`. A step may show two `step-end`s of a crashed attempt and its takeover (`errorKind: "exception"`, `uncharged`).
- Fake SDK controls and the crash pattern are in the Seams section; `createCloudBackend({ remote, runId, waitFloorMs })` through `RunOptions.backend` is how a test shortens the pause between waits.
