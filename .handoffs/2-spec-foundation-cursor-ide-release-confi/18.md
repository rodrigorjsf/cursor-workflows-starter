## What was built
- `wf doctor [--json] [--cwd <repo>]` runs eight independent checks and reports each as pass or fail, every failure with a fix hint: `node`, `dependencies`, `login`, `models`, `gh`, `mcp-server`, `config`, `kit-version`.
  It exits 1 when any check fails. `--json` prints `{ ok, checks: [{ id, title, status, message, hint? }] }`; without it, a text report with `como corrigir:` under each failure.
- The checks follow the IDE: they read the repo's `.cursor/mcp.json` and `.mcp.json` (`${userHome}`, `${workspaceFolder}`, `${HOME}`, `${env:X}` substituted), resolve `node` on the PATH the entry gives the server, look for the command and script the entry runs, and start the server as the IDE would (command, args, env, cwd = repo) to ask for `tools/list`.
- `models` compares every model id the workflows end up using (roles, label globs, the workflow's `defaults.model`, env `WF_MODEL_*` shortcuts included) with `Cursor.models.list()`, ids and aliases alike. `login` is `Cursor.me()` and shows the key name only.
- The repo config's `kit` is a semver range. `wf doctor`, `wf run`, `wf start` and the MCP `start_workflow` refuse a kit outside it with the kit version, the range, "mais antigo / mais novo" and what to do; a `kit` that is not a semver range is refused too. Reads that only look (`wf list`, `wf config show`) still work.
- `wf doctor` on a Node older than 22.13 still delivers a report (the `node` failure alone, text or JSON) instead of the plain exit message. The whole report goes through the run logs' redactor.

## Decisions & deviations
- **Node resolution.** A doctor cannot see the IDE's own PATH. It resolves `node` the way `env node` (the `tsx` shebang) does, on `env.PATH` of the `mcp.json` entry when the entry sets one (the usual workaround for an IDE with an old node), else on the PATH of the process running `wf doctor`. The book tells users to run it from a terminal the IDE opened. This is a best effort and the docs say so.
- **An eighth check, `kit-version`.** The ticket lists seven checks plus the refusal; the range check needed a place in the report. It tests the kit running `wf` and the kit each MCP server reports in `initialize` (what `start_workflow` would actually refuse), grouped by version.
- **`semver` dependency** (`^7.8.6`, runtime package) and `@types/semver` (root dev). Hand-rolling `^`, `~`, `x`, `||` and hyphen ranges was the riskier option; `wf init` keeps writing the `>=a.b.c <d.e.f` form. Version below/above the range is told apart with `semver.ltr`/`gtr`.
- **The refusal also covers `wf run` and `wf start`**, not only `start_workflow` (the ticket names `wf doctor` and `start_workflow`): story 10's purpose is "an old kit never runs against a newer config", and `start_workflow` has the CLI as its twin. The `kit` range is read as plain JSON, without the schema, so a config written for a newer kit shows the version error and not a pile of "unknown key" schema errors.
- **Login check = `Cursor.me()`**, an authenticated call (not `Cursor.auth.status()`, which only reads the stored login), so a revoked key fails here. The report prints `apiKeyName`, never the e-mail or the key.
- **`WF_DOCTOR_TIMEOUT_MS`** (default 20 s for `Cursor.me()`, the catalog, `gh auth status`, MCP `connect` and `tools/list`) exists so the hang test does not wait 20 s; same precedent as `WF_HEARTBEAT_MS`. Documented in the book.
- **`mcp-server` starts the servers in parallel with the other checks** and the `kit-version` check reuses their answers: one spawn per config file.
- **Runtime messages pt-BR**, code comments and tests English (repo convention).
- **TDD honesty.** Slices went red -> green one at a time (config + JSON/exit code, node, dependencies, login, models, gh, MCP server, kit-version + refusals, then the review findings). The "healthy setup" and "text report" tests, the models "defaults/labels" test and the `guarded` wrapper were written after the code they exercise; I mutation-checked them (always-`ok`, exit 0, `process.execPath` instead of the PATH node, aliases dropped, key not redacted, `assertKitCompatible` removed from the MCP server and the CLI, relative args not resolved, entry PATH ignored, `node-check` doctor branch off, server versions ignored, labels/defaults not collected, gh guard off, dependency check always found): each failed at least one test. `guarded()` has no regression test (no realistic way to make a check throw); I verified it once by hand (a `throw` injected into `checkGh`: the other seven checks reported, exit 1) and then removed the injection.
- **Real-world checks** (not committed): `wf doctor` against the real SDK on this repo: 8/8 pass, login shows the key name, the catalog contains `composer-2.5` and `grok-4.7`, `gh` authenticated, both MCP servers answered `tools/list`; under the real Node 22.11.0 (mise) `wf doctor --json` prints the single `node` failure and exits 1, `wf list` keeps the old plain message.

## Learnings
- `gh issue view <n> --comments` prints nothing under the RTK hook; `gh issue view <n> --json title,body,comments` works.
- A symlinked `node_modules` makes `npm install` write into the main checkout; to add a dependency in a worktree, `cp -a` main's `node_modules` first, then `npm install -w …`.
- `HOME=…` on the command line breaks `mise exec` (it cannot trust its config): `mise exec node@22.23.4 -- env HOME=… node …`.
- `Object.defineProperty(process.versions, "node", { value: "22.11.0" })` in a `--import` preload fakes an old Node for `node-check.ts`; the machine also has the real 22.11.0 under mise.
- Shell builtins only on a test PATH: `sleep` is not there. `while read line; do :; done` is a server that reads and never answers.
