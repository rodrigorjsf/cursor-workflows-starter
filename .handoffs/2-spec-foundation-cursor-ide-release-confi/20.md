## What was built
- `smoke` (built-in workflow, `packages/runtime/workflows/smoke.ts`): one structured step, role `ping` (`composer-2.5`, no tools, `settingSources: []`, `retries: 0`), run cap 50,000 tokens. The agent must call `submit_result` with `answer: "pong"`; the schema (`enum`) refuses anything else, so a finished run really went through the SDK. Result `{ status: "ok", answer: "pong", tokens }`. Measured against the real API on 2026-11-12 (`wf run smoke`, composer-2.5): `finished`, 21,628 tokens, 25 s.
- `scripts/verify/validate-cursor-ide.sh`: a wizard built on the `/wizard` skill's `template.sh` (library part unedited). It checks `wf`, `gh`, the kit's dependencies; creates a private sandbox repo with the existing `setup-sandbox-repo.sh` (+ two more `complexity:low` issues) and runs `wf init` on it; runs `wf doctor` (scenario 1); for scenarios 2 to 6 prints exactly what to type in the Cursor chat, asks pass/fail/skip and a one-line note; writes `validation-report.json`; shows the issue body and files it on the kit's repo only after a `y`.
- `scripts/verify/validation-report.ts`: builds `validation-report.json` and `issue-body.md` from the wizard's progress file and `wf doctor --json`; anonymizes paths, sandbox repo/owner, account, host, emails; redacts known credential formats with the runtime's redactor; prints the issue title.
- The wizard survives scenario 5 (quitting Cursor kills Cursor's terminal): answers live in `~/.cursor-workflows/validation/progress.env`; a second run keeps earlier answers (Enter) and continues at scenario 5. A finished report archives the progress file, so the next validation starts clean.
- Docs/skill: book 2.3 "Validar no Cursor IDE", 2.1 §5 (starts with `smoke`), 9.1 tree, 9.4 scripts table (two rows), 1.1 status row, `scripts/verify/README.md`, `skills/cursor-workflows-setup` (`SKILL.md` + `references/validate.md`), CHANGELOG.

## Decisions & deviations
- **Wizard text is English**, like the unedited `template.sh` library (stage text shares its screen); installer/runtime messages are pt-BR. The report and the issue are English (durable artifacts). Pick the other way by translating library and stages together.
- **Library kept verbatim** (the `/wizard` skill's rule); the wizard's own helpers and stages sit below the STAGES marker. Unused library helpers (`set_secret`, `set_var`, `finish`, `ask_secret`) stay; `shellcheck -x` is clean.
- **Scenario 1 is derived, not asked**: pass only if `wf doctor --json` exits 0 and the person says the terminal is Cursor's; outside Cursor it is `skipped` with the reason (a terminal outside the IDE proves nothing, as `validate.md` already said). `wf doctor` runs twice (text for the person, `--json` for the report).
- **Scenarios 5 and 6 each get their own sandbox issue** (2 and 3, `multiply`, `negate`), created by the wizard after the script's issue 1. Scenario 5 needs a run that takes minutes; scenario 6 only needs a started one. Cost: roughly 800k tokens for scenarios 3 to 6 (smoke 22k + two LOW runs ~340k each, measured 339k in the research doc + a cancelled one), on included models.
- **Inside Cursor's terminal the wizard exits at scenario 5** (quitting Cursor ends it) after printing how to run it again; outside, it waits for Enter. `IDE_TERMINAL` is an answer, not a detection (no verified Cursor env variable to key on).
- **Report builder in TypeScript, called through the kit's `tsx`** (`TSX_TSCONFIG_PATH` pointed at the root tsconfig so a target repo's tsconfig cannot interfere): reuses `createRedactor`, produces valid JSON whatever is typed. Checked under Node 22.11 (the version in the spec evidence) with `mise exec node@22.11.0`; a PATH node of 18 crashes tsx, and the wizard's error then says to run `wf doctor`.
- **Anonymization**: literals first, longest first (sandbox repo slug, sandbox dir, kit dir, `$HOME`), then bare repo name / owner / host / user (whole words, four characters or more), emails, Windows paths, and absolute paths of two segments or more (`/tmp` and `/run-workflow` survive). Applied to what people and machines wrote (notes, Cursor version, doctor messages and hints), not to the wizard's own titles.
- **`releaseCriterionMet` needs all six on record** (`SCENARIO_COUNT = 6`); a scenario with no answer is `skipped`, never `pass`. Report states are `pass | fail | skipped`; the wizard's answers are `pass | fail | skip`.
- **Issue target**: `WF_KIT_REPO`, else the GitHub origin of the kit checkout; with neither, the wizard says to send the JSON to the maintainer and asks nothing.
- **smoke cap 50,000** (measured 21,628; the first guess of 30k left no room for one correction). `retries: 0`, `schemaRetries: 1`. The prompt, meta and role text are pt-BR like the other built-in workflows; comments English.
- **Sandbox setup is resumable** (repo, issues and `wf init` are separate steps with markers in the progress file); the script's own failure prints `gh repo delete <repo>` and the folder to remove.

## Learnings
- A test PATH that lists `/usr/bin` ahead of the test's own node picks up a Node 18 there, and `tsx` crashes in `register-*.cjs`: put `dirname(process.execPath)` first.
- `gh issue view <n> --comments` prints nothing under the RTK hook; `gh issue view <n> --json title,body,comments` works (cwd in the main repo).
- `mise exec node@22.23.4 -- npm ci` in a bare worktree takes 3 s and gives the `tsx` the tests need; no copying from the main checkout.
- `read -s` and `read -r` work on a piped stdin, and the `/wizard` library's `_clear` is a no-op off a TTY, so a wizard can be driven by a scripted stdin in tests.
- A `.mjs`/`tsx` helper beats printf-built JSON in a shell wizard: notes are free text.
