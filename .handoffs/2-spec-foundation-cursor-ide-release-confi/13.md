## What was built
- The job record (`.workflows/jobs/<jobId>.json`) holds only `jobId`, `runId`, `pid`, `heartbeat`. `wf status`, `wf jobs`,
  `wf wait`, `get_workflow_status` and `wait_workflow` return a state projected from the run's event log on every read:
  status, workflow, phase, start/finish time, `recent`, `result`, `error`, spend and usage. Reading writes nothing.
- `recent` holds at most 20 one-line summaries (labels, models, costs, `ctx.log`, warnings; collapsed to one line, cut at
  200 chars), never prompt, agent or tool text.
- Step content is written to the log as `content` events (`prompt`, `agent-message`, `tool-call`, `command-output`, tied to
  `stepId`/`attemptId`, cut at 32768 chars with `chars`/`truncated`). They go to the log only: not to the metrics recorder,
  not to `onEvent` listeners, not to `recent`. `WF_METRICS_STORE_PROMPTS` is gone.
- Every event string is redacted before it is written or delivered (known credential formats; values of env vars named
  like KEY/TOKEN/SECRET/PASSWORD with >= 8 chars; the `apiKey` option), then content is cut.
- At run start, content of the repo's other runs outside the last 30 runs or older than 14 days is pruned (`text` removed,
  event kept). Locked runs, the current run and the journal are left alone.
- The run's spend is replayed from the log when the run opens, failed attempts included; a resume's cap is the new total.

## Decisions & deviations
- **Job view fields.** `workflow` and `startedAt` come from the `run-start` of the job's execution, not the record (the record is identity only). A job whose process has not started the run yet shows `status: running` with no `workflow`.
- **Which execution a job shows.** `run-start` has a new optional `jobId`; a job projects the events from its own `run-start` to the next one. A resumed run has one job per execution; each shows what it ran, with spend cumulative up to its end.
- **`refused` exception.** A job refused before its run starts (invalid args, `já está em execução`) cannot write to a log that may belong to another execution, so the record carries an optional `refused` reason. A normal record has exactly the four identity keys.
- **`result`** is projected from a new `run-end.result` (the workflow's return value, redacted). It is not step content and is not pruned; skills tell authors to return structured facts. Dismissed as a review finding.
- **Retention semantics.** A run is pruned when it is outside the newest N runs (the starting run counts) OR older than D days; either limit alone is enough; `null` turns a limit off. Age = modification time of the log, restored after a rewrite so a pruned log stays old. Limits come from `RunOptions.retention` only (no env var): the config file is #14.
- **Redaction scope.** Applied to every event (log, recorder, listeners get the redacted event), not just content. Env values < 8 chars are skipped (`KEYBOARD_LAYOUT=us` would wreck ordinary words). Distinctive prefixes (`ghp_`, `xox`, `eyJ…`) match without a word boundary. Cursor-specific key shapes are not listed (unverified): the Cursor key is covered through `CURSOR_API_KEY` and the `apiKey` option. Redaction runs before the 32768-char cut.
- **Content kinds.** `command-output` is recorded for the `shell` tool only (stdout/stderr/exit code); other tools record their args only (results such as file reads would bloat the log). Thinking deltas are not recorded.
- **Heartbeat.** Written at job start and every 5 s (unref'd timer) and exposed in the view; staleness is still pid-based. Turning heartbeat age into the failure rule is #16.
- **Crash handler.** `uncaughtException` now appends a failed `run-end` (`crash: …; relance com resumeRunId="…"`) to the log of every run the process executes (`abortOpenRuns`), since job state is read from the log.
- **Metrics DB.** `prompt_text` column stays (schema compatibility), never written; migration 3 (`SCHEMA_VERSION` 3) nulls what older versions stored.
- **Language.** New runtime messages stay pt-BR; new code comments are English (the review flagged this); `events.ts` comments stay pt-BR (they generate the pt-BR reference page).
- Worktree note: the worktree had no `node_modules`, so root tests that spawn `node_modules/.bin/tsx` failed at baseline (28 of 58). I created `node_modules/` as a directory of symlinks into the main checkout's `node_modules` (ignored by `node_modules/`, untracked).

## Learnings
- A worktree under `.git/run-spec/…` has no `node_modules`; root tests that spawn `<ROOT>/node_modules/.bin/tsx` fail until `node_modules/` is a real directory of symlinks to the main checkout's entries (a symlink named `node_modules` is not ignored by `node_modules/`).
- `git checkout <file>` on an untracked file is a silent no-op under `|| true`: do not use it to undo a mutation of a new file; keep a `cp` backup.
- `utimesSync` with float seconds drifts by about 1 ms; compare file times with a 1 ms tolerance.
