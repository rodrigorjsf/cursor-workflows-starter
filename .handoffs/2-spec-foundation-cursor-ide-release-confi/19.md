## What was built
- `scripts/install.sh --tag vX.Y.Z [--repo <url>]` installs the kit for the user: clones the tag into `~/.cursor-workflows/kit`, runs `npm ci`, writes the `wf` shim to `~/.local/bin/wf`, links every skill of the kit into `~/.claude/skills/` (symlinks through the fixed kit path), and copies `templates/global-config.json` (the agreed caps) to `~/.cursor-workflows/config.json` when there is none. Safe to run again.
- `scripts/install.sh --dev` makes the kit location a link to the working copy that holds the script (no `npm ci` there, only `npm install` when `node_modules/.bin/tsx` is missing). `--refresh` redoes dependencies, shim, links and config for the kit in place.
- `wf upgrade` fetches the tags of the installed clone's origin, picks the newest stable `vX.Y.Z` (pre-releases ignored), checks it out and runs **that tag's** `install.sh --refresh`: a new skill gets a link, the link of a skill that left is removed, the user's config is not touched. stdout is `{ upgraded, from, to, tag }`. It refuses a dev install, a `wf` that does not run from the installed kit, and an unreachable origin, leaving the kit as it was.
- `INSTALL-AGENT.md` (English, public, pinned to `v0.2.0`, the package version) drives check machine -> install -> `wf whoami` -> `wf init` -> `wf doctor` -> hand over.
- New distributed skill `cursor-workflows-setup` (English; init, doctor, upgrade, validate, config; `references/config.md`, `references/validate.md`), dogfood link in `.agents/skills/`.
- Book 2.1 (install, upgrade, dev mode), 2.3 (form B, global skills row, doctor), 9.1 tree, 9.4 scripts table, both READMEs' quickstart, CLAUDE.md and CHANGELOG describe the flow.

## Decisions & deviations
- **Installer in bash, not TypeScript.** It runs before any kit exists. `wf upgrade` therefore does only the git part and hands the rest to the new tag's `install.sh --refresh`, so install and upgrade share one implementation and a new tag can add steps. The script runs inside `main() {…}; main "$@"` so a half-downloaded `curl | bash` does nothing and `git checkout` can replace it under a running `--refresh`. Messages pt-BR (runtime convention), header and comments English.
- **Locations.** Kit `${WF_HOME:-$HOME}/.cursor-workflows/kit`, shim `~/.local/bin/wf`, skills `~/.claude/skills/`. No flags for the last two (YAGNI). The PATH is never edited: the installer warns with bash/zsh/fish instructions. Skill links point at the fixed kit path, not the real path, so they survive tag <-> dev switches.
- **Dev mode is a flag with no path:** the working copy is the one holding the script (`scripts/install.sh --dev`). A dev install is recognised by the kit location being a link (`-L`), also for `--refresh`. Tag and dev installs never replace each other; the message asks the user to move the other one.
- **User files are never overwritten:** a skill folder or a foreign link in `~/.claude/skills`, a `wf` without the shim marker, an existing global config. Each gets a warning.
- **Node check in the installer** (reads `engines.node` from the kit's `package.json` with `sed`, compares with `sort -V`): the spec evidence was a Node 22.11 left on the PATH; failing before `npm ci` is cheaper than the doctor finding it after.
- **`wf upgrade`:** acts on `${WF_HOME:-~/.cursor-workflows}/kit` only; the running kit must be that clone. No rollback when the refresh fails (npm ci already emptied `node_modules`); the error prints the repair command. Already newest: reports and does nothing.
- **Tag pin = package version, enforced.** One literal tag in the guide, the two READMEs and 2.1; `test/install-guide.test.ts` fails if any differs from `package.json`. **Known consequence:** `v0.2.0` already exists and does **not** contain the installer, so the guide cannot work until the next version is bumped and tagged. That is #21's release step (the test forces the guide, READMEs and 2.1 to follow the bump). Until then, validation uses `scripts/install.sh --dev` from a clone.
- **README quickstart rewritten** (installer, `wf login`, `wf init`, `wf doctor`); the old hub test (`npm run <script> exists`) became "commands exist": npm scripts, `wf` commands (from the CLI's usage line) and the installer's flags (from `install.sh --help`). Still within the slim-hub and no-duplication tests.
- **Cursor docs fact relied on, not re-fetched:** user-level skills are read from `~/.agents/skills`, `~/.cursor/skills` and, for compatibility, `~/.claude/skills` (taken from the spec's "Further Notes"; cited as the existing `cursor.com/docs/skills` [DOC] without an access date).
- **The skill's `validate` section** is a six-scenario checklist (spec scenarios 1–6) with what to observe; scenario 3 says "when `wf list` shows `smoke`" because the workflow arrives with #20. No wizard is mentioned.
- `templates/global-config.json` is byte-for-byte the first `examples` entry of the config schema (tested), so the schema's documentation and the installer cannot drift.

## Learnings
- The main checkout's `node_modules` can lag a merged ticket's dependency (here `semver` from #18): `cp -a` it into the worktree, then `npm install` there.
- A global `core.autocrlf=true` (this user's) turns a cloned shell script into CRLF unless the repo's `.gitattributes` says `eol=lf`; a test origin must copy `.gitattributes`.
- `git clone --branch <tag> --quiet` still prints detached-HEAD advice: pass `-c advice.detachedHead=false`.
- `gh issue view <n> --comments` prints nothing under the RTK hook; `gh issue view <n> --json title,body,comments` works (cwd in the main repo).
- `HOME=… mise exec …` breaks mise; use `mise exec node@22.23.4 -- env HOME=… <cmd>` (or set HOME only in a spawned child's env).
