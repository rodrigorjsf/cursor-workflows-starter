## What was built
- Every `turn-ended` of a running step is checked against two token caps: the step's `maxTokensPerStep` (role / label / workflow / global, already clamped by #14; all attempts of the step together) and the run's cumulative `maxTokens` (the log's ledger from #13, resumes included, plus the turns of every attempt in flight). Strictly above a cap = crossed.
- Crossing a cap cancels the SDK run at once (`Run.cancel()`), the wait on it fails immediately, and the attempt ends with the new `errorKind: "budget"` and is not retried. The turn that crossed is still in the log (`turn` event) and in the spend.
- A step over its own cap fails alone (`StepBudgetError`, message `Teto de tokens da etapa "x" atingido: 300 de 250.`): in `parallel` it becomes `null` plus a `warning`.
- The run's cap cancels every active step, no queued or later step starts, and the run ends `failed` with `Teto de tokens atingido: 500 de 450.` after the cancelled steps close their accounting (up to 30 s), so `run-end` is the last event. This holds even when the workflow code swallows the step's error.
- Overshoot is at most one turn per active step. A step that already used its whole cap in a failed attempt gets no further attempt.

## Decisions & deviations
- **Strictly above = crossed (`>`), start gate stays `>=`.** A step that ends exactly on a cap is not cut; the next step / attempt is refused (`assertBudget`, and the same rule for a step's own cap before each attempt, so a cap of 0 lets no step run).
- **Step cap counts all attempts of the step**, not each attempt: a retry gets no fresh allowance. A resume starts a step's count again (the journal keeps no partial step state); the run cap does accumulate across resumes (review finding 4, dismissed).
- **Run cap wins over the step cap** on the same turn (it ends the run). The run-level live total is `spentTokens` (ledger + committed attempts) + the `turn` totals of attempts in flight; an attempt leaves the in-flight set in the same synchronous block that adds it to `spentTokens`.
- **A budget cut is `errorKind: "budget"` for every cut attempt**, including the steps cancelled by another step's turn. Not retried either way.
- **Run ends failed even if the workflow swallowed the error** (review finding): once `runBreach` is set, a `finished` outcome is replaced by `failed` with the budget message.
- **The cents cap is not live**: cost arrives after the step. Out of the ticket.
- **Engine design**: `AttemptCut` class (cancel + reject + `throwIfCut`) per attempt; `cutters`, `live` and `running` sets in `executeRun`; `waitWithTimeout` takes the cut promise first in its race and now catches the late rejection of the abandoned `run.wait()`. Messages pt-BR, comments English.
- **Existing test changed**: `budget-resume.test.ts` "the token cap is a total across resumes too" used `maxTokens: 150` to let two 110-token steps finish; with live caps step b is cut on its turn. Cap moved to 220 (a and b finish, c is refused); the test's point is unchanged.
- **TDD honesty**: slice 1 (per-step cut) and the three review-driven behaviours (swallowed error, exact-cap retry, rate-limit double count) went red -> green. For the other tests the mechanism was written in one pass, then mutation-checked (see Code review).

## Learnings
- A worktree under `.git/run-spec/…` has no `node_modules`: make `node_modules/` a real directory of symlinks to the main checkout's entries (including `.bin`); it is ignored by `.gitignore`.
- `gh issue view` / `gh search issues` print nothing through the shell wrapper: redirect to a file (`> file`) and read the file.
- A mutation that makes a wait never settle leaves a 600 s `timeoutMs` timer alive: run mutants with a subprocess timeout and restore the file in a `finally`.
- The Cursor SDK's `turn-ended` is a whole agent loop (1 send = 1 turn in the recorded probes): "per turn" caps are coarse until #37 is answered.

## Notes for dependent tickets
- **#16 (detached jobs, cancel):** reuse the same mechanism for cancellation. `AttemptCut` (`engine.ts`) cancels the run in flight and rejects the wait; a `cancel_workflow` / SIGINT path can call `cut(err)` on every entry of `cutters` with a new error type, and add `cancelled` to `run-end.status`. `errorKind` has `budget` now; a cancelled attempt will want its own kind.
- **Any ticket that touches the engine's attempt loop:** the order inside `catch` matters: `await attemptCut.stopped()` -> `chargeUsage` -> `endEvent` -> rethrow, and `live.delete(turnUsage)` must stay in `chargeUsage`.
- **Fake SDK:** `live: true` runs stream after `send()` returns and honour `cancel()`; `rejectWait` / `stuckAfterCancel` simulate failing and hung runs; `stats.cancels` / `stats.turnsDelivered` count them. Plain runs behave as before.
- `StepContext.tokenCap` comes from `resolved.stepOverrides(role, label).maxTokensPerStep`; the recorded config / `run-start` already carry it from #14.
