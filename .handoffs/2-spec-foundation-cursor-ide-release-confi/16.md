## What was built
- `start_workflow` (MCP) and `wf start` (CLI) both go through `spawnJob`: every run is a detached process (`wf run <wf> --job <id>`, new session, stdio to the job log). The MCP server only starts it, reads state and asks it to cancel. Killing or restarting the server leaves the run going; a new server finds it through the job files.
- A running job keeps a heartbeat in its record, written every 5 s by a worker thread (so a main thread blocked in `execFileSync`, like an `implement-issue` test run, does not look dead). A job whose process is gone, or whose heartbeat is older than 30 s, projects as `failed` with `resumeRunId="<runId>"`.
- New `cancel_workflow` MCP tool and `wf cancel <jobId>` send SIGTERM to the job's process (only if its command line carries the job id) and wait up to 20 s (MCP) / 30 s (CLI) for the job to leave `running`. SIGINT and SIGTERM on a run process do the same; a second signal exits at once with the run closed as `cancelled` in its log.
- The engine takes `RunOptions.signal`. On abort it cancels the active agent runs, reverts the in-flight write step to its state before the step, ends the run with `run-end.status = "cancelled"` and releases the lock. The job shows `cancelled`; the run resumes with the same run id (finished steps come from the journal, the spend of the cancelled attempt stays in the budget).
- `run-workflow` skill documents cancel and calls it only on the user's request.

## Decisions & deviations
- **Revert design (the ticket says "revert the in-flight write step", the engine had no notion of one).** A "write step" is an `agent()` call whose `tools` are not all read-only (`isReadOnly`, as `memo` uses). Before such a step the engine records, via git, the exact bytes of every non-ignored file under the step's cwd plus the tree of the index (`worktree-snapshot.ts`). On cancel the files the step created are deleted, changed/deleted ones are written back, and the index is restored (`read-tree`). Chosen over `snapshotTree`/`revertTo` of `implement-issue` because those stage everything in the real index at snapshot time (unacceptable in the user's own tree) and go through git's clean/smudge filters (the machine's global `core.autocrlf=true` turned a restored `original\n` into `original\r\n` — found by the first test run). Files are hashed and restored with `--no-filters`/`cat-file blob`, so autocrlf, `.gitattributes` text rules and LFS cannot change a byte. One snapshot per step (before the attempts), so a revert goes back to the start of the step, not of the attempt.
- **Revert limits (documented in the architecture chapter):** commits the step made, files outside the step's cwd, and git-ignored files are not undone; two write steps in the same cwd at once each revert to their own start (the authoring rule "parallel writes only with isolation" already forbids that); outside a git repo nothing is reverted and the log gets a `warning`. `step-end` carries `reverted: true` when it worked.
- **Cancel vs failed.** New `run-end.status` / `RunOutcome.status` / job status `cancelled`; new `ErrorKind` `cancelled`; metrics `outcome_class` `cancelled`. One `RunStatus` type (events.ts) replaces the repeated unions. `wf run` exits 130 when cancelled. A run whose step was cut short ends `cancelled` even if the workflow code swallowed the error and returned; the run waits for every in-flight step (other `parallel` branches) to stop and revert before writing `run-end`.
- **Heartbeat in a worker thread** (`heartbeat-worker.mjs`, plain JS): the spec's own out-of-scope list defers async commands to the resilience spec, so until then `implement-issue` blocks the main thread for up to 10 min in `runTests`; a main-thread timer would make every such job look dead. Falls back to a main-thread timer if the worker cannot start. The worker rewrites the whole record, so it never drops a field. `WF_HEARTBEAT_MS` (5000) and `WF_HEARTBEAT_STALE_MS` (30000) exist as test knobs.
- **Cancel of a frozen job.** A process that is alive with a stale heartbeat cannot handle SIGTERM and holds the run lock (a resume would be refused). `cancelJob` kills it with SIGKILL, frees the run for a resume, and says it could not revert the step. Pid-reuse guard: no signal unless `/proc/<pid>/cmdline` carries the job id (platforms without `/proc`: assumed ok).
- **`--overrides '<json>'`** on `wf run`/`wf start` is how the MCP server hands the chat's tighten-only overrides to the detached child (#14's note); `parseLimitOverrides` moved from `mcp-server.ts` to `config/index.ts`.
- **Absorbed spec defaults:** creation of the agent and `send` are now bounded by the attempt's `timeoutMs`, and schema re-prompts share it (a deadline per attempt, raced with the cancellation in `within()`); a late-created agent/run is disposed/cancelled. No ticket of the spec claimed these two items.
- Messages stay pt-BR, code comments English (cli.ts / mcp-server.ts header lines I added are English).
- The worktree had no `node_modules`; I created it as a directory of symlinks into the main checkout's `node_modules` (ignored, untracked), as the #13 handoff recorded.

## Learnings
- `git hash-object --stdin-paths` follows a symlink and hashes its target's content; a link's blob is its target string, so hash it through `--stdin`.
- A global `core.autocrlf=true` makes `git add` + `git checkout` change bytes on restore; any snapshot/restore through git must bypass filters (`hash-object --no-filters`, `cat-file blob`).
- `Promise.all` inside `parallel` rejects on the first branch: a cancelled run must `allSettled` the in-flight steps before writing `run-end`, or later branches end after the run.
- `gh issue view <n>` printed nothing in this environment (RTK rewrite); `gh issue view <n> --json title,body` works.
- Tests whose cwd sits inside this repo (`test/.tmp`) would make a cancelled write step revert the project's own index; cancel tests use a `mkdtemp` directory outside any repo.

## Notes for dependent tickets
- **#15 (live caps):** a step is cancelled by racing against the attempt's deadline and the run's cancellation in `within()` / `waitWithTimeout(run, deadline)` in `engine.ts`. For a budget cancel, call `run.cancel()` the same way and throw a non-`RunCancelledError` (`BudgetExceededError`); `RunCancelledError extends FatalRunError`, so `parallel`/`pipeline` already propagate it. `ErrorKind` has `cancelled`; add `budget` next to it. `step-end.reverted` is only set on the cancel path: decide whether a budget kill of a write step should revert too (it is not resumable-unsafe: the step is not journaled).
- **#22 (`ctx.exec`):** commands should observe the run's abort signal. Today `RunOptions.signal` is not exposed on `ctx`; add `ctx.signal` (or have `ctx.exec` take it from the engine) so a long command is killed on cancel. While a command still blocks the main thread (`execFileSync` in `implement-issue`), SIGTERM is handled only when it returns; `wf cancel` then answers "ainda está encerrando" after 30 s. The heartbeat is unaffected (worker thread).
- **#17/#18/#19 (init, doctor, installer):** the detached child is spawned with `process.execPath` + `process.execArgv` + the sibling `cli.ts` of `jobs.ts` (`new URL("../cli.ts", import.meta.url)`), so the kit must keep `src/cli.ts` next to `src/runtime/` and be runnable by the same Node + loader the MCP server runs under. `wf doctor` can reuse `inspect()`'s liveness idea and `WF_HEARTBEAT_*` are test-only knobs, not config.
- **Dashboard (#28+):** a job's status can now be `cancelled`; `run-end.status` has three values (`RunStatus` in `events.ts`); `step-end` has `reverted` and `errorKind: "cancelled"`; `spawnJob`/`cancelJob`/`readJob` in `jobs.ts` are the doors for start/cancel/read.
- Test helpers: `cancel.test.ts` shows the pattern for aborting at the first step (`abortOnFirstStep`) and for a throwaway git repo outside the project (`makeRepo`).
