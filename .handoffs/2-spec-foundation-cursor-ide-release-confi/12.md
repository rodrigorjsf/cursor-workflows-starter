## What was built
- Every event of a run is appended to `<repo>/.workflows/runs/<runId>/events.jsonl` (one JSON object per line). Each event has
  `v` (schema version, 1), `ts` and `runId`. A resume appends to the same file; each execution opens with its own `run-start`.
- Step events (`step-start`, `turn`, `step-end`) carry `stepId`, `parentId` and `groupId`. `parallel`/`pipeline` emit
  `group-start` (kind, size, parent) and `group-end` (ok), so the structure of a run can be rebuilt from the log alone.
  `stepId` derives from the journal key, so a step keeps its id across executions of the run.
- Steps served from the journal or memo now emit `step-start` (with `cached`) as well as `step-end`.
- A torn last line in the log or the journal no longer blocks a resume. A run lock (`run.lock`) refuses a second execution
  of the same run id with `já está em execução: ...`; a dead holder, or a recycled pid, is a stale lock and is taken over.
- Job records, memo entries and the `implement-issue` progress file are written atomically (temp file + rename).
- Each new run adds one line (run id, repo, workflow, start time) to `~/.cursor-workflows/runs.jsonl` (`WF_HOME` moves the dir).
- Resuming a run whose workflow hash changed records a `warning` event.
- `docs/reference/events.md` is generated from the event interfaces (`npm run docs:events`); `npm test` fails if it drifts.

## Decisions & deviations
- **`parentId` means "the node this one continues from"**, not the container: the previous step in the sequence, the previous stage of the same pipeline item, the group at the head of a branch, or the group's join after it (`group-end`). `groupId` is the innermost enclosing group. This gives a DAG with fan-out/fan-in from the ids alone (#31 needs that). Implemented with an `AsyncLocalStorage<Flow>` per run; no workflow code change.
- **Ids.** `stepId = s-<12 hex of the journal key>.<occurrence>` (stable across resumes). `groupId` = path of the group in the code: `g1`, `g2`, nested `g1.0.g1` (branch index inside); also stable across resumes. `stepKey` (the full journal key) stays on the step events because the metrics recorder stores it.
- **Group events** `group-start`/`group-end` are new event types (the ticket says groups must be identifiable; a join node is needed for fan-in). `group-end.ok=false` when a fatal error (cap, account) aborts the group; branches still running can emit events after it (the pre-existing fail-fast of `Promise.all` is unchanged, documented in the event comment).
- **`step-start` has `cached: false | "journal" | "memo"`** like `step-end`. The job projection (`jobs.ts describe`) ignores a cached `step-start` so `recent` lines stay as before.
- **Torn lines.** Readers skip any line that is not a valid record; `appendJsonl` closes a torn tail with a newline before appending; nothing is truncated. The resume emits one `warning` when the *last* line was torn (not on every later resume).
- **Lock.** `run.lock` = `{pid, token, startedAt, identity}` created complete via write-aside + hard link (atomic, fails if it exists). `identity` = boot id + process start time from `/proc` (a review finding: a pid recycled after a crash/reboot would otherwise lock the run forever); without `/proc` it falls back to pid liveness. Released on close and on process `exit`. Known limit (commented in code): two processes finding the same stale lock at the same instant can both take it over. A refused run returns `status: "failed"` with the message and writes nothing to the log.
- **Runs index** lives in `userDir()` = `$WF_HOME` or `~/.cursor-workflows`; one line per run id on its first execution (a duplicate is possible only if the very first `run-start` line was torn; readers dedupe by `runId`). It has its own `RUNS_INDEX_VERSION`. A failing append warns and never fails the run.
- **`WF_HOME`** also moves the default metrics database path (`defaultDbPath`), so one variable sandboxes all per-user state.
- **Language.** New runtime messages are pt-BR (the `run-workflow` skill states the runtime's messages are Portuguese and matches them verbatim); new code comments are English, except `events.ts` whose comments are the source of the pt-BR reference page.
- **Absorbed beyond the criteria**, see Absorbed. The ticket text and the run rules clash on nothing else.
- Recorder load failure (`métricas desligadas`) is now reported after `run-start`, and now also goes to the log (before, `onEvent` only).

## Learnings
- `import.meta.resolve("tsx")` passed to `node --import` starts a tsx child from a test; set `TSX_TSCONFIG_PATH` to the test tsconfig to get the fake SDK.
- A python `str.replace` between two anchors silently deletes everything in between; review `git diff HEAD` after scripted edits (I deleted and restored the budget/usage helpers once).
- `ps`-style liveness (`process.kill(pid, 0)`) is not enough for a lock file that outlives a reboot; compare `/proc/<pid>/stat` start time + `boot_id`.
