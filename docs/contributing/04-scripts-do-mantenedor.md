# 9.4 · Scripts do mantenedor

Um procedimento que se repete vira um script em `scripts/`, e não uma sequência de passos que cada agente deduz de
novo. Dois requisitos valem para todo script:

1. **Um cabeçalho WHAT/WHY/WHEN/HOW** nas primeiras linhas, em comentário: o que faz, por que existe, quando rodar e
   como. O cabeçalho fica em inglês, como o resto do texto escrito para agentes.
2. **Uma linha na tabela abaixo.** Os módulos de apoio em `scripts/lib/` (hoje, `scripts/lib/markdown.ts`,
   `scripts/lib/cli.ts` e `scripts/lib/scrub-recording.ts`) não são procedimentos e ficam fora da tabela, mas também levam o cabeçalho.

O `npm test` confere os dois (`test/scripts-conventions.test.ts`): um script sem cabeçalho ou fora da tabela reprova.

| Script | O que faz | Quando usar | Como |
|---|---|---|---|
| `scripts/check-docs.ts` | Confere links relativos, âncoras, índice, H1 e rodapés do livro | Sempre: roda no `npm test`. Avulso, depois de editar a documentação | `npm run docs:check` |
| `scripts/check-mermaid.ts` | Renderiza cada bloco Mermaid com o `mermaid-cli` e falha em erro de sintaxe | No CI (job `mermaid`). Localmente só com `--list`, porque o `mermaid-cli` trava | `npm run docs:mermaid` (CI); `npm run docs:mermaid -- --list` |
| `scripts/events-reference.ts` | Gera `docs/reference/events.md` (6.1) a partir dos tipos em `packages/runtime/src/runtime/events.ts` | Depois de mudar um evento, um campo ou um comentário em `events.ts`; o `npm test` falha se a página divergir. O número e o rodapé da página vêm do índice do livro: não há o que ajustar ao inserir capítulos ao redor | `npm run docs:events`; `npx tsx scripts/events-reference.ts --check` só compara |
| `scripts/config-reference.ts` | Gera `docs/reference/config.md` (6.2) a partir do esquema JSON `packages/runtime/schema/config.schema.json` | Depois de mudar um campo, uma descrição ou um exemplo do esquema, ou de criar uma definição nova (ela precisa de um título em `SECTIONS`); o `npm test` falha se a página divergir. O número e o rodapé da página vêm do índice do livro: não há o que ajustar ao inserir capítulos ao redor | `npm run docs:config`; `npx tsx scripts/config-reference.ts --check` só compara |
| `scripts/dev/dash-fixtures.ts` | Monta um `WF_HOME` descartável com runs de fixture feitos pelo engine de verdade e pelo SDK falso: um terminado (fases, grupos paralelos, cards e uma etapa na nuvem, com custo), um que falhou, um cancelado e um interrompido (processo morto no meio da etapa). Com `--live`, também um job só de comandos que fica rodando por 10 minutos. Imprime o caminho e os ids dos runs em JSON, também gravado em `<home>/fixtures.json` | Antes de olhar o dashboard, a olho ou com o `dash-shots.py`, depois de mudar o Run view, o Board, a tabela de runs, a página de métricas ou os eventos do engine. Não toca em `~/.cursor-workflows` nem gasta cota da Cursor | `npx tsx scripts/dev/dash-fixtures.ts [--home <diretório-novo>] [--live]`; depois `WF_HOME=<home> WF_DASH_PORT=<porta> npm run dash`. O `--live` deixa um processo: pare com o botão Cancel ou com o comando `liveJob.cancel` do JSON |
| `scripts/dev/dash-shots.py` | Captura, de um dashboard no ar, as páginas Runs, Board e Metrics e o Run view de cada run listado, em 360 e 1440 px, nos temas claro e escuro, numa pasta; imprime, por página, o estouro horizontal e os erros e avisos do console (e grava tudo em `probes.json`). Com `--fixtures`, nomeia os arquivos pelo papel do run (estáveis entre montagens) e captura cada Run view de novo com foco num nó: a etapa na nuvem, o comando que falhou, a etapa onde o run parou | Depois de mudar o dashboard, contra os runs do `dash-fixtures.ts`: a mesma bateria de capturas para cada revisão | `uvx --with playwright==1.65.1 python -I scripts/dev/dash-shots.py <url> <pasta> [--fixtures <home>/fixtures.json] [--strict] [--browser <chrome>]`. Uma vez por máquina: `uvx --with playwright==1.65.1 playwright install chromium`. Não entra no `npm`: o Playwright vem do `uvx` |
| `scripts/install.sh` | Instala o kit para o usuário: clona a tag em `~/.cursor-workflows/kit`, instala as dependências, escreve o comando `wf`, liga as skills em `~/.claude/skills/` e grava a configuração global padrão (`templates/global-config.json`) se não houver uma | Uma vez por máquina (o `INSTALL-AGENT.md` conduz); `--dev` num clone faz do kit instalado a sua cópia de trabalho; `--refresh` refaz tudo para o kit que já está no lugar e é o que o `wf upgrade` roda | `bash install.sh --tag vX.Y.Z`; `scripts/install.sh --dev`; `scripts/install.sh --refresh`. Ao lançar, a tag do `INSTALL-AGENT.md`, dos READMEs e de [2.1](../usage/01-instalacao.md#3-instalar) tem de ser a do pacote: o `npm test` confere |
| `scripts/link-claude-skills.sh` | Liga `.agents/skills/*` em `.claude/skills/` para o Claude Code | Uma vez por clone, se o time usa o Claude Code neste repositório | `scripts/link-claude-skills.sh` |
| `scripts/probe-sdk.ts` | Faz um `send` curto contra a API real e mede eventos, uso e custo | Ao atualizar o `@cursor/sdk`, numa conta nova, ou para ver se o `getUsage()` passou a informar custo | `npx tsx scripts/probe-sdk.ts --model <id> --mode smoke` |
| `scripts/verify/setup-probe-repo.sh` | Monta o repositório descartável dos workflows `verify-*` | Antes de rodar os três `verify-*` | `scripts/verify/setup-probe-repo.sh <diretório-novo>` |
| `scripts/verify/setup-sandbox-repo.sh` | Cria um repositório GitHub descartável, com uma issue `complexity:low`, para o teste ponta a ponta do `implement-issue` | Antes de um run real do `implement-issue` | `scripts/verify/setup-sandbox-repo.sh <dono/repositório-novo>` |
| `scripts/verify/gitlab-e2e.sh` | Sobe um GitLab CE de verdade no Docker, com configuração para pouca memória (imagem `gitlab/gitlab-ce:19.5.5-ce.0`; `GITLAB_E2E_IMAGE` troca), espera ele responder, cria um token de acesso do root dentro do container e roda, contra ele, o `record-glab-fixtures.ts` e depois o `prove-gitlab.ts`. No fim, também quando uma etapa falha ou o script é interrompido, remove o container e os volumes que ele mesmo criou. Nunca reinicia nem reconfigura o Docker, e recusa rodar com um container ou um volume de mesmo nome, com um `glab` diferente do fixado no `mise.toml` ou com menos de 4 GiB no Docker | Depois de mudar o `glab` fixado no `mise.toml`, um comando ou rota de API do `forge.ts` ou o filtro de texto do modelo (`pr-body.ts`), e para experimentar uma imagem nova do GitLab. Fica fora do `npm run check` e do CI: o GitLab pede cerca de 2,5 GB e minutos para subir, e a última prova gasta tokens da API da Cursor (exige `wf login`) | `GITLAB_E2E_MAX_TOKENS=600000 GITLAB_E2E_MAX_CENTS=100 mise exec -- scripts/verify/gitlab-e2e.sh`; `GITLAB_E2E_PORT` (padrão 8929) e `GITLAB_E2E_NAME` (padrão `wf-gitlab-e2e`) mudam a porta local e o nome do container e dos volumes; `GITLAB_E2E_TIMEOUT_SECONDS` (padrão 1800), `GITLAB_E2E_POLL_SECONDS` (padrão 10) e `GITLAB_E2E_MIN_MEMORY_MB` (padrão 4096) são a espera pelo GitLab, de quanto em quanto tempo olhar e a memória mínima do Docker; `GITLAB_E2E_IMAGE` troca a imagem; `GITLAB_E2E_MAX_TOKENS` (padrão 600000) e `GITLAB_E2E_MAX_CENTS` (padrão 100) são os tetos do `implement-issue` (`--max-tokens` e `--max-cents`); `GITLAB_E2E_STAGES=closing,quick-actions,references` roda só as provas que não gastam tokens |
| `scripts/verify/record-glab-fixtures.ts` | Roda o `glab` de verdade contra o GitLab que o `gitlab-e2e.sh` subiu: cria o grupo `owner`, o projeto `repo`, duas issues e um MR, e executa, pelo próprio módulo de forge do runtime, cada comando e rota de API do `forge.ts` e o `glab auth status` do `wf doctor`. Grava o que o `glab` imprimiu, com o token, a senha do root e o host local trocados por placeholders fixos, em `packages/runtime/test/fixtures/glab/recordings.json`, de onde o `glab` falso dos testes offline lê. Se uma gravação ainda guarda um segredo, não escreve nada | Chamado pelo `gitlab-e2e.sh`; à mão só contra um GitLab descartável, porque cria um grupo nele | `GITLAB_E2E_URL=<url> GITLAB_E2E_TOKEN=<token> GITLAB_E2E_PASSWORD=<senha> GITLAB_E2E_IMAGE=<imagem> GITLAB_E2E_SCRATCH=<diretório-vazio> npx tsx scripts/verify/record-glab-fixtures.ts` |
| `scripts/verify/prove-gitlab.ts` | Prova num GitLab de verdade o que decide se o `implement-issue` é seguro nele, num projeto `owner/proof` que ele mesmo cria: quais frases fecham uma issue quando o MR é mergeado (inclusive `Implement(s\|ed\|ing) #N`), se um `/close` no texto do modelo roda depois do `sanitizeModelText` (como nota numa issue e como descrição de MR), se `!12`, `~label` e `%milestone` ainda viram link atrás do espaço de largura zero, e um `implement-issue` de verdade com etapas locais cujo MR, mergeado, fecha a issue por `Closes #N`. Cada prova tem um controle que tem de acontecer (o `Closes #N` fecha a issue, um `/close` solto roda, as referências viram link), senão um "não aconteceu nada" não prova nada, e todo texto é postado como está e depois do filtro, lado a lado. Imprime a evidência em Markdown, sem token, senha, host local nem caminho desta máquina, para a descrição do PR; sai com 1 se uma prova não valeu | Chamado pelo `gitlab-e2e.sh`, depois do gravador; à mão só contra um GitLab descartável com o ambiente daquele script, e com `wf login` feito: a última etapa gasta tokens | `GITLAB_E2E_URL=<url> GITLAB_E2E_TOKEN=<token> GITLAB_E2E_PASSWORD=<senha> GITLAB_E2E_IMAGE=<imagem> GITLAB_E2E_SCRATCH=<diretório-vazio> GITLAB_E2E_MAX_TOKENS=600000 GITLAB_E2E_MAX_CENTS=100 npx tsx scripts/verify/prove-gitlab.ts`; `GITLAB_E2E_STAGES` escolhe as provas (`closing`, `quick-actions`, `references`, `workflow`) e `GITLAB_E2E_WORKFLOW_TIMEOUT_SECONDS` (padrão 2700) é quanto o `implement-issue` pode levar |
| `scripts/verify/validate-cursor-ide.sh` | Assistente guiado dos sete cenários de validação no Cursor IDE (e de um oitavo, opcional, a etapa na nuvem): cria o repositório descartável (com o `setup-sandbox-repo.sh`), roda `wf init` e `wf doctor` nele, diz o que digitar no chat em cada cenário, registra o que a pessoa viu, escreve `validation-report.json` e oferece abrir uma issue com ele | Antes de um release, numa máquina ou conta nova e a cada versão nova do Cursor. No terminal do próprio Cursor: o cenário 1 só vale ali | `scripts/verify/validate-cursor-ide.sh [diretório-do-relatório]`; [2.3](../usage/03-invocacao-no-cursor-ide.md#validar-no-cursor-ide) descreve o roteiro |
| `scripts/verify/validation-report.ts` | Transforma o arquivo de progresso do assistente (e o `wf doctor --json`) em `validation-report.json` e no corpo da issue, trocando caminhos locais, repositório, conta e máquina por marcadores e redigindo formatos conhecidos de segredo | Chamado pelo assistente no último estágio; à mão só para refazer um relatório de um progresso salvo | `tsx scripts/verify/validation-report.ts --progress <progress.env> --out-dir <dir> [--doctor <doctor.json>] [--kit <dir>]` |
| `scripts/verify/verify-structured.ts` | Workflow: saída estruturada (`submit_result`, correção, re-prompt) | Conta nova ou SDK novo | [`scripts/verify/README.md`](../../scripts/verify/README.md) |
| `scripts/verify/verify-context.ts` | Workflow: o que `settingSources` carrega e a guarda contra recursão | Conta nova ou SDK novo | [`scripts/verify/README.md`](../../scripts/verify/README.md) |
| `scripts/verify/verify-cache.ts` | Workflow: cache de prompt entre agentes irmãos | Conta nova ou SDK novo | [`scripts/verify/README.md`](../../scripts/verify/README.md) |
| `scripts/verify/verify-cloud.ts` | Workflow: uma etapa de leitura num cloud agent (snapshot com arquivo não commitado, resultado em bloco JSON, uso, limpeza da branch) | Conta nova ou SDK novo, e antes de confiar na configuração de nuvem de um time | [`scripts/verify/README.md`](../../scripts/verify/README.md) |

Os quatro `verify-*` custam tokens: rode sempre com `--max-tokens` e `--max-cents`, e veja a
política de custo em [9.1](01-contribuindo.md#testes-contra-a-api-real-política-de-custo).
